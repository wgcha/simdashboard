# SPDM 기존 업무의 결과 등록·검수·가시화 개선

- 기준일: 2026-09-28
- 상태: 사용자 합의로 계획 확정, 소스 구현 및 관련 격리 검증 완료. 운영 배포는 미실행이며 검증 범위와 남은 제약은 8절에 기록한다.
- 출처: [GitHub #32 결과등록 개선](https://github.com/wgcha/simdashboard/issues/32)
- 이번 사용자 지시가 #32의 최초 「대상 폴더 선택·생성 개선 계획」보다 우선한다.

## 1. 목적과 역할

SPDM에서 생성한 프로젝트·의뢰·하중경우 등 기존 업무를 선택하여 결과를 업로드하고, 자동 검사와 사용자 검수를 거쳐 DB에 정식 등록한 뒤 Case 결과에서 가시화한다.

- SPDM: 업무 항목과 프로젝트·의뢰 상위 폴더 생성·관리.
- 본 프로그램: 기존 업무 탐색, 결과 저장 위치 확인·준비, 업로드, 자동 검사, 사용자 검수, 결과 DB 확정과 가시화.
- 결과 등록 화면에서 새 프로젝트·의뢰·하중경우 생성 UI를 제거한다. 기존 업무·과거 결과와 다른 관리 기능의 저장 데이터를 삭제하지 않는다.
- 업무가 없거나 경로 연결 근거가 없으면 SPDM 선행 등록 또는 관리자 연결 안내를 제공한다. 이름으로 임의의 업무를 만들거나 연결하지 않는다.
- 폴더 생성은 이미 존재하는 업무의 결과용 하위 폴더 준비다. Project/WR 폴더 생성은 금지하며, 새 폴더가 새로운 업무 엔티티를 자동 생성해서는 안 된다.
- 사용자가 요청한 「하중경우·Scene 등의 폴더가 없으면 생성」은 결과용 물리 폴더 준비에 적용한다. 환경 계층의 Case·LOAD_CASE·Run·Scene 폴더 역할은 SPDM 업무 테이블의 신규 등록과 구분하며, 화면에서도 결과용 하위 폴더임을 표시한다.

## 2. 사용자 흐름과 데스크톱 UI

1. **등록 대상 선택**: 기존 프로젝트·의뢰와 환경을 선택한다. 사용환경은 Case·평가 항목, 유통환경은 Case·하중경우·Run Case·선택적 Run Option·Scene 문맥을 유지한다. 사용환경에 불필요한 하중경우·Run 선택을 요구하지 않는다.
2. **결과 위치 확인**: 기존의 확정된 폴더 연결과 실제 디렉터리를 조회한다. 후보가 여러 개면 사용자가 선택한다. 연결 정보 없음, 실제 폴더 없음, 접근 실패, 다른 업무 소유 충돌을 구분한다. 경로는 읽기 전용으로 표시한다.
3. **폴더 준비·업로드**: 결과용 폴더가 없으면 생성할 경로를 보여주고 명시적으로 확인받는다. 결과 파일과 영상·이미지를 업로드한다. 업로드는 검수 대기 상태이며 정식 결과를 게시하지 않는다.
4. **자동 검사·검수**: 결과 항목, 읽은 값, 단위, 원본 파일·필드, 검사 상태와 미디어 연결·미리보기를 제시한다. 사용자가 오류를 해결하거나 허용되는 누락을 명시적으로 확인한다.
5. **등록 확정**: 사용자가 「검수 완료·DB 등록」을 실행한다. 서버가 권한, 업무 관계, 자료·설정의 버전을 다시 확인한 뒤 승인한 자료로 수집 버전을 만든다.
6. **완료·가시화**: DB 등록 완료, 수집 버전, 결과·영상 수와 제외·오류 내역, 「Case 결과 보기」를 제공한다. 선택한 프로젝트·의뢰·환경·Case·수집 버전을 유지해 이동한다.

기존 컴포넌트와 디자인을 활용한다. 업무 생성 폼과 기술 설정을 주 흐름에서 제거한다. 경로·규칙 관리가 필요할 때만 관리자 고급 기능을 사용한다. 모바일 전용 개선·검증과 새 외부 서비스 도입은 범위 밖이다.

## 3. 자동 검사와 사용자 승인 계약

- 업무·파일 형식·결과 항목·값 자료형·단위·누락·복수 원본 충돌·중복 등록·미디어 형식 및 대상 연결을 검사한다.
- 자동 검사는 형식과 정합성 확인이다. 공학적 타당성을 보증하지 않으며, 별도 판정 기준 없는 값에 합격·불합격을 만들어 붙이지 않는다.
- 필수 오류는 게시를 차단한다. 허용 가능한 누락·제외는 이유와 사용자의 명시적 확인을 기록한다. 오류를 빈 값이나 성공으로 바꾸지 않는다.
- 원본 값을 임의 변경하지 않는다. 잘못된 파일은 교체하고, 지원하는 매핑 수정은 출처·설정 버전을 남긴다.
- 검수 결과는 업로드 바이트·업무 문맥·읽기 설정과 결합한다. 검수 후 어느 하나라도 바뀌면 승인을 무효화하고 다시 검사한다.
- 파일 제외는 사유를 입력하고 재검사한 뒤 승인한다. 제외 후 바뀐 값·미디어·건수를 먼저 보여주며, 승인 요청의 제외 목록은 해당 검사 버전과 일치해야 한다. 인식된 결과값과 연결 가능한 지원 미디어가 모두 없으면 부분 등록으로도 게시하지 않는다.
- 검수 초안과 업로드 이력은 DB에 저장할 수 있지만, 정식 Case 목록·수집 이력과는 구분한다. 등록 전 자료를 기존 자동 수집기가 먼저 게시하지 못하도록 격리한다.
- 일부 평가 항목만 올리는 경우 이번 승인 파일 범위의 독립 수집 버전으로 게시한다. 과거 버전의 값을 암묵적으로 합치지 않으며 누락 항목과 부분 등록 확인을 제공한다. 과거 수집 버전은 그대로 보존한다.

## 4. 저장·경로·권한 계약

- Case 결과의 기존 `dashboard_cases`, `dashboard_captures`, `dashboard_assets`와 원본 검수 기능을 우선 재사용한다. SPDM 기존 `load_cases`와 Case/Run/Scene 식별자를 동일시하지 않는다.
- 기존 폴더 연결·규칙에서 확정된 업무·경로 관계를 우선 재사용한다. `spdm_storage_*_parents`만 전제로 하여 실제 명명 규칙을 지원한다고 가정하지 않는다.
- 하나의 하중경우에 Scene 경로 하나만 연결하는 기존 SPDM 1:1 모델을 여러 Scene에 그대로 적용하지 않는다. 환경별 계층과 선택적·임의 이름의 Run Option을 유지한다.
- 확정 결과값과 미디어 바이트를 DB에 보존한다. 정식 화면은 승인된 수집 버전을 읽으며 원본 폴더의 현재 내용으로 과거 결과를 대체하지 않는다.
- 업로드 원본은 검수 전 정식 수집과 분리한다. 기존 파일을 덮어쓰거나 삭제하지 않는다. 재시도와 중복 클릭은 동일 승인 결과를 중복 등록하지 않는다.
- 경로 생성은 root identity, Windows 이름·대소문자, 루트 이탈, reparse/symlink, 기존 소유권을 검사한다. 같은 업무에서 읽기/저장 연결이 공존할 수 있는 경계를 명시하고, 다른 업무의 조상·자손 경로를 무조건 허용하지 않는다.
- 조회와 생성·업로드·등록은 구분한다. 서버가 대상 프로젝트의 `result.import`와 업무 관계를 매 변경 시 확인한다. 조회 전용 사용자는 게시된 결과만 조회한다.
- 실패 시 이번 작업에서 생성한 빈 폴더만 안전하게 보상 정리한다. DB와 파일시스템이 하나의 트랜잭션이라는 가정을 하지 않는다. 외부 프로세스가 만든 파일은 삭제하지 않는다.
- 게시 실패와 수집 실패는 성공으로 표시하지 않는다. 재시도 시 기존 성공 결과를 보존하고 권한과 검수 일치 여부를 다시 검사한다.
- 초안 상태·승인을 위해 영속 스키마가 필요하면 additive migration을 허용한다. 「신규 테이블 없음」을 강제하지 않는다. 신규 의존성 없이 기존 구조를 우선 활용한다.

### 확정 구현 경계

- 결과 등록 전용 API는 `/api/result-registration` 아래에서 대상·폴더 조회, 하위 폴더 준비, 초안 생성·파일 업로드, 자동 검사, 승인, 게시를 분리한다. 기존 SPDM 즉시 ingest API를 새 UI에서 호출하지 않는다.
- 초안 원본은 DB 바이너리로 격리한다. 기존 Case 수집 한도(파일당 32 MiB, 작업당 256 MiB)를 재사용하고 업로드 화면에 알린다. 검수 대기 원본도 DB 백업 대상이며 배포 릴리스 교체로 사라지지 않는다.
- 승인한 파일 목록·내용 해시와 바이트만 capture 게시에 사용한다. 주변 폴더의 미검수 파일을 추가 수집하지 않는다.
- DB 게시 후 선택한 결과 폴더에 원본을 덮어쓰기 없이 저장한다. 같은 내용은 재사용한다. 다른 내용의 동명 파일이 있거나 원본 폴더 저장에 실패하면 DB 게시 성공과 폴더 저장 실패를 구분하고, 성공한 capture는 보존한 채 복구 상태를 제공한다.
- additive migration `0031_result_registration`을 사용한다. 기존 `0030_folder_environment_profiles`에서의 업그레이드와 빈 DB 설치, 기존 프로젝트·의뢰·수집 버전·영상 바이트 보존을 격리 PostgreSQL로 검증한다.

## 5. 상태와 감사 기록

폴더 준비 상태와 등록 작업 상태를 별도로 관리한다. 등록 작업은 업로드/검사 대기, 검수 필요, 등록 중, 등록 완료, 실패를 구분한다. 기술적 내부 상태명을 사용자에게 그대로 노출하지 않는다.

등록 대상, 파일별 검사 결과, 업로드·검수·등록 수행자와 시각, 내용 해시, 읽기 규칙 버전, 제외 사유, 수집 ID를 추적할 수 있어야 한다. 완료 화면에서 내부 Run ID를 찾아야만 등록 여부를 알 수 있게 하지 않는다.

## 6. 구현·검증 순서

1. 기존 코드의 환경별 계층·경로·검수·수집 계약을 확인하고 API와 담당 파일 경계를 정한다.
2. 기존 폴더 대상의 업로드→자동 검사→사용자 확정→DB 저장→Case 표시 흐름을 구현한다.
3. SPDM 상위 폴더를 보존하는 결과용 폴더 생성과 환경별 하위 대상 선택을 연결한다.
4. 결과 등록 화면의 업무 생성 기능을 제거하고 단계별 UI·완료 이동·실패 복구를 검증한다.
5. 독립 Sol 검수, 파일 업로드·경로·권한 변경분 보안 검수, 고위험 변경의 독립 Astra 검수 후 최종 통합한다.

필수 수용 기준:

- 일반 권한 사용자가 허용된 기존 업무를 선택하여 폴더 경로 수동 입력 없이 결과를 등록한다.
- 결과 등록 화면에 새 프로젝트·의뢰·하중경우 생성 동작이 없고 기존 업무 데이터가 보존된다.
- Project/WR가 없거나 연결이 불명확하면 임의 생성·추정 없이 안내한다.
- 기존 결과 폴더 사용과 없는 하위 폴더의 명시적 생성이 모두 가능하다.
- 검수 전 자료는 Case 결과의 정식 수집 목록에 나타나지 않는다.
- 자동 검사에서 항목·값·출처·단위·미디어 연결을 확인할 수 있고 필수 오류가 게시를 차단한다.
- 검수 후 파일·문맥·설정 변경, 중복 클릭, 동시 등록, 실패 재시도와 권한 취소를 처리한다.
- 확정 후 결과값과 영상이 같은 수집 버전으로 DB에 저장되고 Case 결과로 바로 이동한다.
- 새 버전 등록 뒤에도 이전 버전의 값·영상이 그대로 조회·재생된다.
- 격리 임시 DB·합성 파일로 API, 마이그레이션(발생 시), 데스크톱 브라우저 흐름, 프런트 빌드 및 관련 CI를 검증한다.

## 7. 배포와 범위

`deploy.bat`, `update.bat`, Windows Server 2022 폐쇄망 패키징, 백업·기존 데이터 보존과 시작 시 schema 검사 전용 계약을 유지한다. 실제 사용자 DB·설정·서비스를 테스트에 사용하지 않는다. 실제 Server 2022 폐쇄망 신규 설치·업데이트·재부팅은 수행한 경우에만 완료로 기록한다.

이번 작업은 계획 확정과 소스 구현이다. 운영 서비스 배포, 실제 SPDM 자료 수정, Git push·PR 생성은 별도 지시 없이 수행하지 않는다. 구현·검증 결과와 남은 제약은 작업 로그에 기록한다.

## 8. 구현·검증 기록

- 격리 PostgreSQL에서 빈 DB → `0031_result_registration`, 기존 `0030` + 합성 프로젝트·의뢰·Case·capture·asset → `0031`을 검증했다. 기존 항목과 asset 바이너리 보존, 신규 네 테이블의 app 권한, app 계정의 스키마 검사 전용 시작과 DDL 거부를 확인했다. 기준 스키마는 생성기 출력과 일치한다.
- 신규 등록 API·경로의 최종 DuckDB 회귀는 20 통과·1 PostgreSQL 전용 skip이다. PostgreSQL에서는 API 10개 시나리오와 multipart 바이트 보존 1개, 폴더 준비·기존 역할 보존·평가항목 식별자 보존 3개를 별도로 검증했다. 제외 후 건수·사유 고정, 빈 결과 차단, 영상만 부분 등록, 권한 취소, 동시 등록과 재시도를 포함한다.
