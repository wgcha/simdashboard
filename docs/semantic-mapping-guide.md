# 기준 정의·읽기 레시피·결과 위젯 사용 안내

기준일: 2026-09-15. 이 문서는 CSV/JSON 읽기와 기준 정의·별칭의 계약을 설명한다. 전체 확장 목표는 [개발 계획](semantic-storage-mapping-plan.md), 모든 설치·업데이트는 [Windows 배포 정책](windows-deployment-policy.md)을 따른다.

## 사용하는 순서

폴더에서 프로젝트·의뢰·하중 경우 자체를 새로 만들려면 먼저 [폴더 조사와 업무 생성 안내](semantic-folder-discovery-guide.md)를 따른다. 아래 폴더 연결은 만들어진 업무 항목에 읽기 레시피와 결과 위젯을 연결하는 단계이며 예제 항목을 선택할 필요는 없다.

1. 관리자 권한으로 데이터 관리의 폴더/파일 스키마 화면(`/workspace/catalog/schemas`)을 열고 의미 매핑 화면으로 전환한다. 기존 manifest 스키마 편집기도 그대로 사용할 수 있다.
2. 대표 CSV·JSON·TSV·TXT 파일을 끌어 놓거나 선택한다. 내용에서 파일 형식·인코딩·표/키-값 구조를 감지하고 원본 키와 값이 바로 표시된다. 자동 감지가 다르면 고급 읽기 설정에서 수정한다. 필드를 선택하여 기존 결과 항목에 매핑하거나 새 항목으로 만들고, 뜻과 단위를 확인한다.
3. 결과 항목에는 고정 키, 표시명, 값/곡선 유형, 자료형, 기준 단위와 측정 차원을 지정한다. 예를 들어 `stress_peak`, `최대 응력`, 숫자, `MPa`로 정의한다. `node` 차원을 선언했다면 모든 매핑에 해당 위치 필드를 연결해야 한다.
4. 레시피에서 원본 필드와 항목을 연결한다. CSV `Smax`와 JSON `results.peak`가 같은 뜻이라면 서로 다른 레시피에서 동일 항목 ID를 선택한다. 새 레시피는 `#/results/peak`처럼 키를 정확히 식별하는 경로를 저장한다. 점·공백·괄호가 있는 키와 배열 좌표도 구분한다. 단위가 다르면 원본 단위와 기준 단위를 명시한다. 곡선에는 X/Y 필드와 X축 단위를 모두 지정한다.
5. 표시 템플릿에서 카드·게이지·표·막대·선·산점도 입력을 결과 항목 ID로 연결한다. 같은 종류의 위젯을 여러 개 만들 수 있다. 단일 값 위젯에 여러 관측값이 일치하면 위치 필터를 지정한다. 산점도는 행 순서가 아닌 측정 차원으로 X/Y를 짝짓는다.
6. 샘플 통합 미리보기에서 읽은 값, 정규화 단위, 경고, 실제 위젯을 확인한다. **결과 설정 저장**으로 읽기 레시피와 표시 템플릿을 함께 저장한다. 저장된 레시피를 선택하면 연결한 템플릿의 정확한 버전도 불러온다. **활성화 영향 미리보기 → 검토 후 활성화**는 운영에 적용하는 별도 단계다. 서버도 저장 샘플을 다시 읽어 모든 위젯 입력이 유효한지 확인한 뒤 두 활성 버전을 한 트랜잭션으로 변경한다. 검증 실패나 동시 관리자 변경은 일부만 적용되지 않는다.
7. SPDM 루트를 설정한 뒤 임의 이름의 실제 폴더를 기존 프로젝트·의뢰·하중 경우에 연결한다. 하중 경우 결과 폴더에는 사용할 활성 레시피와 표시 템플릿을 지정한다. 새로고침은 파일마다 확장자와 실제 읽기 검증을 모두 통과한 레시피가 정확히 하나일 때 등록한다. 단일 파일 직접 등록도 가능하다.
8. 등록한 실행의 결과 화면에서 연결된 위젯을 확인한다. 실행을 전환하면 그 실행의 관측값과 저장된 템플릿 버전으로 조회한다. 다른 실행의 값으로 누락을 채우지 않는다.

## 이슈 #23 CSV / #24 JSON으로 시작하기

1. 샘플을 끌어 놓으면 파일 형식과 입력 구조가 감지된다. 사용 가능한 값이 선택된 초안으로 표시되며, **선택 값을 결과 항목으로 연결**을 누르기 전에는 결과 항목을 생성하지 않는다. 불필요한 필드는 선택을 해제한다. 두 예제는 좌표 배열을 펼친 단일값 43개를 연결할 수 있고 `null` 12개는 기본 제외한다. 0은 정상 값이다.
2. 원본 경로·결측 처리·단위·결과 항목 연결을 각 매핑 행에서 수정한다. **수정**으로 항목 정의를 열고 **복제**, **매핑 삭제**, **삭제 되돌리기**로 연결을 조정한다. 매핑 삭제와 기준 항목 보관은 서로 다른 작업이다. 이미 저장 버전이 참조하는 항목은 표시명만 바꿀 수 있고 의미·자료형·단위 변경은 새 항목으로 정의한다.
3. `Set CG Coord. (mm)`의 세 값은 X/Y/Z 성분의 단일값으로 추천한다. 다른 배열은 성분 번호를 사용하므로 실제 의미를 확인해 표시명을 수정한다. `@0deg`, `@1deg`는 항목 이름의 조건으로 보존한다. 배열이나 조건별 단일값을 자동으로 시간 곡선으로 바꾸지 않는다.
4. **전체 항목 요약표 추가**로 값을 한 표에 표시하거나 **위젯 추가**로 개별 항목의 카드를 만든다. 연결한 항목에 맞는 표시 방식을 선택한다. 단일값에는 곡선을 선택할 수 없고, 실제 곡선은 X/Y 원본 필드를 지정한 곡선 항목을 사용한다. 소수 자릿수 2는 `12.35` 형식이며 단위 입력을 비우면 항목별 기준 단위를 유지한다.
5. 완성된 매핑·위젯을 변경하면 업로드한 샘플로 통합 미리보기를 자동 갱신한다. 여러 위치의 값이 카드에 일치하면 위치 필터를 지정한다. 원본 샘플 펼치기는 변환 전 값이고, 통합 미리보기는 서버에서 변환·검증한 실제 표시 결과다.
6. 이름을 입력하고 **결과 설정 저장**을 누른다. 파일 없이 기존 설정을 개정하면 서버에 저장된 이전 샘플을 새 버전의 검증에 재사용한다. 브라우저를 다시 열어 대화식 미리보기를 편집하려면 샘플 파일을 다시 올린다. 저장된 레시피/템플릿 선택과 과거 Run 조회는 원본 파일 재업로드 없이 가능하다.

**결과 항목 관리 · 보관 및 복원**에서는 사용하지 않는 정의를 보관하고 복원한다. 현재 편집 중인 설정에서 참조한다면 먼저 매핑과 위젯에서 제거한다. 보관한 항목은 새 연결의 선택 목록에서 제외하며 과거 버전·실행 결과와 기존 활성 설정은 보존한다. 보관은 데이터의 영구 삭제가 아니다.

레시피는 읽는 방법, 템플릿은 표시 방법이다. 일반 작업에는 통합 저장을 사용하고, 다른 읽기 규칙에 같은 표시 구성을 재사용할 때만 **고급 · 레시피/템플릿 개별 저장**을 사용한다.

## 이름·정의·경로를 구분하는 방식

프로젝트의 정체성은 기존 프로젝트 ID이며 폴더명은 식별자가 아니다. `Eagle_2026`나 한글 이름의 폴더를 선택해 동일 프로젝트에 연결할 수 있다. 파일 열 제목도 결과 항목의 정체성이 아니다. 항목 ID에 연결한 원본 필드 경로를 레시피로 저장한다.

이름 오타를 자동 확정하는 AI나 유사 문자열 분류는 사용하지 않는다. 관리자가 지정한 연결이 근거다. 폴더가 이동되면 새 실제 위치를 확인하고 재연결한다. 내용이 비슷한 다른 프로젝트 폴더를 자동으로 같은 대상으로 간주하지 않는다. 기존 SPDM이 소유한 경로를 새 수집 경로로 중복 연결할 수 없다.

## 기준 정의와 별칭 재사용

의미 매핑의 **기준 정의·별칭** 탭에서 고정 키·표시명·설명과 여러 별칭을 등록한다. 연결 종류는 폴더 역할, 프로젝트, 의뢰, 하중 경우, 결과 항목이며 실제 대상 ID를 선택한다. 예를 들어 `Eagle_2026`·`이글`을 같은 프로젝트에, `Smax`·`최대응력`을 같은 결과 항목에 연결한다.

폴더 상대 경로 옆의 별칭 찾기는 현재 경로의 마지막 폴더 이름으로 검색한다. 원본 필드 옆의 별칭 찾기는 해당 필드 문자열을 검색한다. 후보를 눌러 적용한 다음 기존 레시피/폴더 연결 저장 절차를 진행한다. 검색만으로 연결이 저장되거나 원본 단위가 변하지 않는다.

전역 또는 프로젝트별 사전을 사용할 수 있으며 레시피에서는 별칭 검색 프로젝트를 선택한다. 대소문자·공백·Unicode 표기 차이를 정규화한 정확 매칭을 사용한다. 별칭을 수정하거나 비활성화해도 이미 저장된 레시피·폴더 연결·과거 실행은 변하지 않는다. 자세한 수정/충돌/범위 규칙은 [사전 안내](semantic-vocabulary.md)를 따른다.

## 결과와 버전 계약

| 대상 | 계약 |
|---|---|
| 결과 항목 | 항목 ID가 측정 의미를 나타낸다. 최대/평균처럼 뜻이 다른 측정은 별도 항목으로 만든다. |
| 측정 차원 | 항목 하나가 여러 위치의 관측값을 가질 수 있다. 차원 없는 여러 값은 오류이며 최대/최소/평균을 명시했을 때만 집계한다. |
| 레시피 | CSV/JSON 구조와 필드→항목 연결을 저장한다. 저장 버전은 생성 당시 항목 정의의 스냅샷을 보유한다. |
| 템플릿 | 입력 항목·차원 필터·표시 단위·자릿수·게이지 기준을 정의한다. 게이지 기준은 해당 항목의 기준 단위로 입력한다. |
| 실행 | 읽기 버전, 표시 버전, 원본 이름·SHA-256, 정규화 관측값을 함께 남긴다. 과거 실행은 새 정의 활성화로 변경되지 않는다. |
| 중복 | 같은 하중 경우·레시피 버전·파일 내용은 재시도/이름 변경에도 같은 실행을 재사용한다. 내용 또는 레시피 버전이 바뀌면 새 실행이다. 동일 내용의 독립 실험 구분이 필요하면 별도 실행 식별 계약 확장이 필요하다. |
| 편집 | 기존 정의 저장 시 읽어온 `expected_version`을 전송한다. 다른 관리자가 먼저 개정했다면 다시 불러온 후 수정한다. |
| 정의 이동 | 최신 항목·레시피·템플릿 정의를 초안으로 재사용하는 기능이다. 과거 버전·활성 포인터·샘플·업무 데이터·계정·폴더 경로를 내보내지 않는다. 반입 후 샘플을 저장해 검증·활성화하고 업무 대상에 다시 연결한다. 전체 이력 복원은 DB 백업을 사용한다. |

값이 없으면 `MISSING_RESULT`, 단일 값이 필요한데 여러 관측값이면 `AMBIGUOUS_RESULT`, 형식·차원 짝짓기·단위가 맞지 않으면 `INCOMPATIBLE_RESULT`를 표시한다. 0으로 대체하거나 이름이 비슷한 다른 결과를 가져오지 않는다.

## 지원 범위와 제한

- CSV: 쉼표·세미콜론·탭·파이프 구분자, 헤더 1~100행, UTF-8/UTF-8 BOM/CP949/UTF-16. 중복 헤더와 잘린 행을 거부한다.
- JSON: 객체 또는 객체 배열, 점 표기와 배열 인덱스 경로. 중첩된 한글 필드도 지원한다. 중복 키·비유한 숫자·32단계를 넘는 중첩을 거부한다.
- 값과 곡선: 숫자·정수·텍스트·참/거짓 값, 숫자 X/Y 곡선. 같은 series의 X는 중복 없이 증가해야 한다. 결측값은 오류 또는 명시적 건너뛰기다.
- 단위: 압력·길이·시간·힘·질량·주파수·각도·온도·무차원 단위의 명시된 변환표를 사용한다. 알 수 없는 단위도 원본/대상이 정확히 같으면 보존하며 다른 단위로 추정 변환하지 않는다.
- 새 읽기 엔진(v2)은 행·열·매핑·결과 점 개수를 임의로 자르지 않는다. 파일당 64 MiB, 정규화 결과 64 MiB와 실행 시간 예산을 적용하고 초과 시 오류를 표시한다. 화면은 페이지 단위로 조회한다. CSV 표와 최상위 JSON 레코드 배열은 순회하면서 읽고, 키-값 파일과 중첩 JSON 객체는 파일 크기 한도 안에서 처리한다. 템플릿 32위젯과 폴더 새로고침 500파일·128 MiB의 운영 한도는 유지한다.
- 기존 v1 레시피의 의미와 한도(5 MiB·50,000레코드·256필드·64매핑)는 재현을 위해 유지한다. 새 자동 감지 레시피를 저장하면 v2가 적용된다. 기존 정의가 자동 변환되거나 과거 결과가 바뀌지 않는다.
- 업로드한 샘플은 소유자별 임시 ID로 미리보기·저장에 사용하며 24시간 후 만료된다. 새 업로드나 만료 샘플 접근 때 정리한다. 초기화는 현재 업로드를 해제하고 임시 사본을 삭제하며 이미 저장한 레시피 버전의 검증 샘플과 결과는 보존한다. 레시피 저장 시 샘플은 DB에 독립적으로 저장되어 이후 검증에 쓰인다. 원본 업무 파일의 관리·백업은 별도로 유지한다.
- 새 미디어 파서, 임의 실행 코드/수식, 외부 AI 의존성은 추가하지 않는다. 기존 이미지·영상 등록 및 전용 위젯은 기존 경로로 이용한다.

AI 초안 제안, 여러 파일을 한 Run으로 묶는 조인, 파생 계산, 범용 규칙 검토함·영향 분석, 파일 식별자를 이용한 이동 자동 추적과 저장소별 복잡한 상속 정책은 [계획](semantic-storage-mapping-plan.md)에 남아 있는 확장 목표다. 현재 관리자 연결과 CSV/JSON 읽기는 이 기능들을 요구하지 않는다. 전체 계획의 모든 수락 시나리오를 구현 완료로 표시하지 않는다.

## 개발·배포 연결

- 엔진: `backend/app/domains/semantic_mapping/engine.py`. 외부 I/O 없이 레시피·단위·측정 차원·위젯 계약을 검사한다.
- HTTP/저장: `backend/app/routers/semantic_mapping.py`, `backend/app/services/semantic_mapping.py`. 기존 인증·권한·SPDM 파일 경계와 canonical result ingestion을 재사용한다.
- 화면: `frontend/src/features/data/SemanticMappingWorkspace.tsx`, 실행별 `SemanticResultPanel.tsx`, 공용 `shared/components/semanticResults.tsx`.
- DB: `0023_voc_posts` 다음의 `0024_semantic_mapping`, 사전은 그다음 `0025_semantic_vocabulary` additive migration이다. PostgreSQL 앱 시작은 테이블/스키마 검사만 하고 DDL은 실행하지 않는다. DuckDB는 기존 개발 bootstrap 경로를 유지한다.
- 새 런타임·패키지·영구 디렉터리·환경 비밀값이 없다. 기존 `deploy.bat`/`update.bat`, 백업 후 migration, 앱 역할 CRUD/DDL 분리, 오프라인 정적 웹 패키징 계약을 따른다. 소스 변경 후 기존 절차로 새 릴리스 패키지를 만들어야 서버에 반영된다.

실제 사용자 DB나 서비스에는 자동 설치하지 않는다. 개발 PC에서 통과한 임시 DB·패키지 계약 검사는 폐쇄망 Windows Server 2022 신규 설치/업데이트/재부팅 실기 검증과 구분한다.

바로 시험할 수 있는 합성 CSV·JSON·정의 패키지는 [예제 안내](../examples/semantic-mapping/README.md)에 있다.
