# 결과 분석 4단계 — 기록 기준 여유와 비교 축

상태: 구현 및 기능 검증 완료 · 2026-09-11

## 목적과 범위

기존 Run 비교 위젯에서 결과가 판정 경계까지 얼마나 남았는지 확인한다. 위젯 배치와 저장 방식은 유지한다. 새로운 자동 원인 추론, 설계 승인, 서로 다른 물리량의 위험도 순위는 만들지 않는다.

## 기록 기준 여유

- `scalar_results.threshold_double`은 품질 기준 변경 시 과거 행도 재계산되므로 실행 시점의 불변 기준으로 취급하지 않는다. 현재 카탈로그와 PASS/FAIL에서 상한·하한을 추정하지 않는다.
- Run metadata의 명시적인 `result_criteria`를 사용한다. 기록이 없는 과거 Run은 계산 불가다.
- 상한은 상한−결과, 하한은 결과−하한, 닫힌 범위는 두 경계까지 거리 중 작은 값을 표시한다. 음수는 기록 범위 밖, 양수는 범위 안, 0은 경계다. 엄격한 부등호에서는 경계가 기준을 충족하지 않는다.
- 기준/대상 각각의 여유와 기록 기준·출처를 확인한다. 현재 저장 판정과 기록 기준의 충족 여부가 다르면 구분해 안내한다.
- 단위가 정확히 일치해야 한다. 숫자 0과 음수를 허용하되 누락·불명확한 연산자·비유한 값·잘못된 범위는 계산하지 않는다. 비율이나 안전율은 정의 없이 생성하지 않는다.
- 표에서는 대상의 여유를 간결하게 보여주고, 변수 선택 시 두 Run의 계산 기준과 사유를 상세 표시한다.

## 비교 그래프

- 기존 그래프도 두 Run이 하나의 Y축을 공유한다. 이를 유지하며 두 Run 전체를 포함하는 명시적인 공통 범위를 적용한다.
- 시간은 숫자 축으로 표현하여 불규칙한 시점 간격을 실제 비율대로 표시한다.
- 기본은 0을 포함하는 값 범위이며, 세부 변화를 확인할 때 데이터 범위로 전환할 수 있게 한다. 현재 축 방식은 화면에 명시한다.
- 값 누락은 끊어진 선으로 유지한다. 단위를 변환하거나 누락 지점의 결과를 생성하지 않는다. Run/변수가 바뀌면 축 선택 문맥을 초기화한다.

## 검증 흐름

결과 대시보드 → 결과 검토 → Run 비교 → 변수 선택 → 기록 기준 여유/계산 불가 사유 확인 → 시계열 축 전환 → Run 전환 및 모바일 확인.

- 백엔드: 상한·하한·범위·경계·누락·0·음수·단위 불일치와 실제 기록 저장/조회 연계.
- 프런트엔드: 기록 기준과 판정 구분, 구버전 응답, 불규칙 시간, 누락 선, 공통 축, Run 전환, 기존 근거/초안 회귀.
- Browser plugin not available: 기존 Playwright와 격리된 예제 서버를 사용한다. 검증 캡처는 저장소 밖에 보관한다.

## 결과 생산자가 기준을 기록하는 방법

마스터 폴더 가져오기의 `manifest.json`에 아래 metadata를 결과 파일과 함께 기록한다. 키는 결과의 정확한 `variable_key`다. 실행 입력 조건인 `run_conditions`와 판정 기준인 `result_criteria`는 별도로 보존한다.

```json
{
  "metadata": {
    "result_criteria": {
      "top_edge_max_stress": { "operator": "LT", "upper": 75, "unit": "MPa" },
      "minimum_clearance": { "operator": "GTE", "lower": 2, "unit": "mm" },
      "operating_temperature": { "operator": "BETWEEN", "lower": 10, "upper": 40, "unit": "degC" }
    }
  }
}
```

- `LT`/`LTE`는 `upper`, `GT`/`GTE`는 `lower`, `BETWEEN`은 두 경계가 필요하다. `BETWEEN`은 양 경계를 포함한다. 선택적인 `label`은 설명이며 계산 방향은 `operator`가 결정한다.
- 최대 128개 기준, 정규화된 JSON 16 KiB, 변수 키 120자, 단위 40자, 설명 240자로 제한한다. 알 수 없는 필드·충돌하는 키·유효하지 않은 기준은 `RESULT_CRITERIA_INVALID`로 거부한다.
- 기존 manifest에는 필수가 아니다. 기존 Run을 소급 수정하지 않고 새로 적재되는 Run부터 기록한다. 현재 수동 CSV 업로드에 별도 기준 입력창을 추가한 것은 아니다.
- 저장 판정 필터와 회귀/개선 집계의 의미는 유지한다. 기록 기준의 충족 여부와 저장 판정이 다르면 상세 화면에서 확인하도록 한다.
- Windows 마스터 폴더 새로고침의 기존 POSIX 권한·`fcntl` 잠금 제한은 [입력 조건 비교 문서](run-input-condition-comparison.md)의 범위와 같다. 이번 기준 비교에서 플랫폼 보안/잠금 경로를 우회하지 않는다.

## 구현 및 검증 결과

- Terra: 기준 metadata 검증·저장·비교 계산. Luna: 숫자 시간축·공통 값 범위와 그래프 모듈 분리. Sol: 기록 출처·판정 의미·누락·범위 검수. 루트: 여유 UI·문서·수치 예외 보정·통합/시각 검증.
- 백엔드 56개 테스트 통과(27.04초): 상한/하한/범위, 엄격·포함 경계, 0/음수, 미기록, 단위 불일치, 잘못된 출처와 입력, 초대형 숫자 및 계산 overflow를 검증했다.
- 실제 manifest 파서 → command → DB → 비교 경로에서 기준 75→40을 각각의 Run에 보존하고 +32.5/-2.5 여유를 확인했다. 과거 scalar 기준값을 999로 변경해도 기록 기준 여유는 유지된다. 전체 Windows master refresh 운영 검증과는 구분한다.
- 기존 비교/입력 조건 브라우저 시나리오 9개 통과. 새 4단계 시나리오 4개 최종 통과(53.2초): 여유/부족/엄격 경계, 저장 판정과의 차이, 구버전 응답, Run 전환, 불규칙한 시간 간격, 실제 SVG 좌표, 누락 구간, 고립 관측점·0 단일 시점, 축 초기화 및 모바일 넘침을 확인했다.
- 최초 통합 실행의 새 미기록 테스트는 구현 중 적재된 서버 모듈에서 사유 기대값이 달라 실패했다. 현재 DB 레코드와 최종 계산 함수를 확인하고 서버를 새로 시작하여 새 시나리오 전체를 통과했다. 그래프 고립 관측점 렌더러의 반환 타입도 TypeScript 검사에 맞게 보정했다.
- 타입 포함 빌드·프런트엔드 아키텍처(159 source files)·숫자축 helper 검사 통과. helper는 불규칙/음수 시점, 0/음수 상수 범위와 10만 점 배열도 검사했다. 기존 500 kB 번들 경고는 남아 있다.
- Chromium 데스크톱 1505×1045 / 모바일 390×844, 로컬 격리 서버 15173/API 18000 사용. 캡처로 여유 카드/범례/축/모바일 가로 넘침 확인. 가설과 인과관계, 실제 고객의 분석 시간 개선은 이 테스트로 검증하지 않았다.
- QA 캡처·로그: 저장소 밖 Codex visualization 작업 폴더 `phase4-qa`. 실제 값 변화가 애니메이션 중간 화면으로 보이지 않도록 비교 선 애니메이션을 끄고, 기록 기준 미충족 색상을 저장 판정의 개선 색상과 분리했다.
- 최종 색상/애니메이션 보정 후 여유 카드·수치축 시각 시나리오 2개 재검증 통과(20.9초). 데스크톱 카드의 미충족 강조, 완성된 비교 선과 모바일 범례/내부 탐색 캡처를 재확인했다.
