1. 먼저 이해할 사용자 의도
사용자는 Altair One 해석 결과 폴더를 탐색해 그 안의 수치·이미지·영상을 workbench 대시보드에서 보고 싶다. 폴더를 물리적으로 재배치하거나 모든 파일을 서로 다른 해석 Run으로 표시하는 것이 목표가 아니다.

사용환경은 한 Simulation Case 안의 다섯 평가 결과를 한 페이지에서 종합한다. 유통환경은 Simulation Case 안에서 하중경우·반복해석 Run·실행방식을 선택한 뒤 여러 Scene의 컨투어와 응력을 비교한다.

핵심 불변식:

SimType1=사용환경, SimType2=유통환경. 과거 엑셀의 상충 설명보다 이 정의를 우선한다.
Case=설계변경 조합, Run=같은 Case/하중경우의 반복해석. 결과 새로고침/파일 등록 횟수는 사용자 Run 횟수가 아니다.
같은 Case/Run/Scene의 수치와 미디어만 연결한다. 다른 버전의 결과로 결측을 채우지 않는다.
원본 폴더/파일/부호/단위/이력을 보존한다. 단위·임계값·재료·부품명은 추정하지 않는다.
이번 업무는 설계 문서만 작성한 상태다. 이하 구현 항목은 미구현 계획이다.
2. 확정 계층과 탐색 규칙
2.0 자료 탐색 루트는 프로그램 설정값
사용자가 정한 현재 루트는 D:/01.Projects/4_VD/26Y_VD_SPDM_SimulationPlatform/SimulationDB/Shared다. 프로그램에서 이 루트를 정의할 수 있으며 구현은 설정된 저장소 루트를 읽어야 한다. 예시 드라이브/회사 경로를 소스·프런트 코드에 고정하지 않는다.

저장 식별: storage_root_id + root_relative_path. 파일 처리 시 서버가 설정 루트와 상대 경로를 결합하고 경로 경계를 검증한다.
원본 파일을 Shared로 다시 복사하거나 부모 SimulationDB까지 자동 탐색하지 않는다.
다른 환경에서는 같은 기능으로 다른 Shared 위치를 설정한다. 루트 변경 시 기존 ID/연결을 자동 재해석하지 않고 기존 저장소 재연결 여부를 명시적으로 검토한다.
표준 Altair One 구조는 아래 2.1/2.2다. 실제 Shared의 SPDM (Admin) 같은 컨테이너 및 SPDM식 이름은 별도 읽기 프로파일/명시 매핑이 필요한 참고 구조다. 컨테이너를 프로젝트로 간주하지 않는다.
설명 엑셀은 Shared 바깥의 SimulationDB/폴더구조에 있는 참고자료이며 결과 탐색 루트에 포함시키지 않는다. 다른 환경에는 본 문서의 발췌 계약을 전달하면 된다.

3.3 미디어 연결과 한 페이지 배치

이 문서는 이미지 바이너리를 포함하지 않는다. 다른 환경에 실제 이미지가 없다면 구현 시 승인된 임시 테스트 영역에서 Scene 식별 글자가 있는 합성 이미지를 만들어 연결/확대/누락/정렬 동작만 검증할 수 있다. 이를 실제 CAE 컨투어 또는 실제 수치-영상 일치 검증으로 보고하지 않는다. 실제 이미지 육안 수락검사는 원본 확보 후 별도다.

5. 집계와 데이터 품질: 구현자가 임의 결정하지 않을 부분

A. 공통 Scene 축·Case 비교 계약
그래프 X축의 Scene number는 표준 Scene 폴더 맨 앞 숫자다. 3_Face_Drop_Scene03_Face6_1st는 3, 20_Face_Drop_Scene12_Face3는 20이다. 내부 Scene12를 X축 12로 대신 쓰지 않는다. scene_sequence_number와 scenario_number를 별도 저장한다.
순번 숫자로 정렬한다. Case별로 같은 순번에 다른 하중 자세가 있을 수 있으므로 비교 정렬은 운송 프로파일(Parcel/LTL 등), 하중경우, 자세/접촉코드, 회차의 대응까지 검증한다. Parcel/LTL의 Scene 목록·개수는 서로 다를 수 있고 20/30개를 고정하지 않는다. 프로파일은 확인된 메타데이터/명시 선택으로만 지정한다.
기존 샘플 DAMP-2 접두사의 숫자는 표준 선행 숫자 문법과 다르다. 별칭/매핑 확인 전 임의로 2라고 확정하지 않는다. 이 예외가 표준 20_...의 순번 규칙을 미확정으로 되돌리지는 않는다.
범례의 해석 Case는 Simulation Case다. 각 비교 Case에 하중경우·사용자 Run·Mode·capture·Component/물리 역할을 명시적으로 선택한다. 같은 이름의 Run이나 최신 파일을 조용히 고르지 않는다. 이전 Run 비교는 Case 비교와 별도 기능이다.
공통 비교축에는 대응 가능한 Scene만 같은 위치에 놓고 미대응/누락은 빈칸과 사유로 남긴다. 문자열 순번/배열 인덱스만으로 Case 간 서로 다른 Scene을 합치지 않는다.
Case마다 고정 색/패턴을 사용하고 네 엣지 패널과 두 비교표까지 유지한다. Scene 설명표는 순번 → Face/Edge/Corner·접촉코드·회차를 보여준다. Case 간 목록이 다르면 해당 프로파일/Case 문맥을 표시한다.
B. 결과 요약: Open Cell 엣지 맵과 Scene 최대응력
공통 선택: 의뢰 / 비교 Case / 하중경우 / Case별 Run·Mode·capture / Component
표시 엣지: 상단 [ ] 하단 [ ] 좌측 [ ] 우측 [ ]
[ Open Cell 직사각형 엣지 맵 + 선택 Scene 정보 ] [ Scene별 엣지 최대응력 비교 그래프 ]
우측 그래프: X축=선행 Scene 순번, Y축=Stress. Case별 계열의 막대/점/점과 선과 확대 기능. 기본 요약 대상은 **선택한 엣지의 최대값(envelope)**이며 코너를 포함한 기존 '추출 영역 최대'와 다른 지표다. 선택 엣지가 모두 해제되면 0 대신 선택 없음 표시.
그래프의 막대/점을 클릭하면 해당 Case + Run + Mode + capture + Scene + Component + 집계기준을 선택하고 좌측 맵을 즉시 갱신한다. Case가 두 개이면 같은 Scene의 서로 다른 막대가 서로 다른 Case를 선택한다.
좌측 맵에는 top/bottom/left/right별 최대값·단위를 실제 테두리 위치에 표시하고 선택/최대 엣지를 강조한다. 인치·하중 자세·날짜·제조사·제품모델명은 확인된 메타데이터가 있을 때만 표시한다.
이 직사각형 엣지 맵은 기존 'Scene×발생위치 범주 맵'과 별도 위젯이다. 정확한 좌표가 없으면 특정 노드 위치를 테두리 위의 임의 점으로 그리지 않는다. 좌표계/기하 대응이 확인된 경우에만 실제 피크 위치를 추가한다.
평가 기준이 없으면 기준선/합격 색을 표시하지 않고 미판정으로 둔다. 그래프 집계와 맵 값은 같은 엣지·라인 범위/원본요약 또는 상세 기준을 사용한다. 선택 범위 중 자료 누락이 있으면 최대값이 있어도 부분 결과 표시.

상단: Scene 번호 설명표, 비교 Case 선택/전체 선택·해제, 패널 크기, Case 순서·Scene 순서·그룹 표시 설정.
본문: Left / Right / Top / Bottom 네 패널을 기본 2×2 배치. 각각 X축=Scene 순번, Y축=해당 엣지 응력, 범례=Simulation Case. 예시 30 Scene도 대응하며 화면 폭에 따라 스크롤/확대를 제공한다.
정렬은 Scene별 Case 막대 교차 표시 또는 Case별 묶음 표시를 지원하는 안으로 구체화한다. 화면 정렬은 표현 순서만 바꾸며 CUMULATIVE 원본 실행 순서/식별자를 수정하지 않는다.
컨셉의 Upper/Lower 및 U/L은 추가 측정 구분이지만 현재 CSV와의 대응은 미확인이다. C23/C24나 L1/L4를 Upper/Lower라고 단정하지 않는다. 명시 매핑이 제공되면 Case와 별도 surface/측정 구분 차원으로 표현한다.
응력값 라벨, 방향/라인/표면 구분, 기준선은 근거가 있는 데이터만 표시한다. 패널 막대 클릭도 B와 같은 문맥으로 엣지 맵/Scene 상세를 갱신한다.
D. 상세 결과 2: Case×Scene 최종 프레임 컨투어 비교
행: Scene 순번 + 자세/충돌 설명 | Scale bar | Case A | Case B | Case C ...
각 교차 셀: 해당 Case의 선택 Run/Mode/Scene/Cell 컨투어 + 값/상태
상단 Case 헤더: 설계변경 설명·참조 모델 이미지(있는 경우)
행/열 바꾸기는 실제 전치 기능이다. 전치 후 행=Case, 열=Scene으로 바뀌되 선택·확대·수치/이미지 연결은 동일한 셀 ID를 유지한다. 단순 카드 정렬과 구분한다.
첫 열에는 낙하 자세(Face/Edge/Corner, 접촉 코드, 1차/2차 충돌 설명)와 관련 그림을 제공한다. 자료 없는 자세도는 임의 생성하지 않고 텍스트/없음 상태로 둔다.
사용자 제목의 Cell Tmax 마지막 Frame Contour는 선택 Scene의 최종 프레임 컨투어 요구로 기록한다. Tmax가 물리량/시각/최대 발생 시점 중 무엇인지 별도 확인이 필요하며 '응력 최대 발생 프레임'으로 자동 대체하지 않는다.
자산에는 frame_role, frame_index, time_value, time_unit, 확인 근거를 보존한다. 파일명 Max_Stress만으로 FINAL_FRAME을 부여하지 않는다. 최종 프레임 검증 전에는 프레임 미확인, 자료가 없으면 없음 표시.
Scale bar는 물리량·단위·범위·평균화·표면·시점을 비교할 수 있을 때만 공통으로 표시한다. 서로 다른 원본 이미지의 컬러 범위를 재색칠하지 않는다. 미확인이면 셀별 원본 범례와 차이 안내를 보존한다.
셀 밑의 Left Max 같은 수치는 대응하는 엣지/집계 범위를 명시한다. 시간 집계 범위가 다른 CSV 최대를 최종 프레임 이미지의 측정값으로 오인시키지 않는다. 이미지와 수치의 시간 정합성 미확인도 표시한다.
컨투어 이미지 클릭 확대, 긴 Case/Scene 이름 툴팁, 누락 셀 유지. 데이터 없음을 0 또는 인접 Case 이미지로 채우지 않는다.
E. 상세 결과 3: 선택 Scene의 Cell/Cushion/Box 거동
좌측 Scene 선택과 자세/충돌 정보. 우측은 열=비교 Simulation Case, 행=Cell / Cushion / Box로 배치한다.
각 셀은 해당 물리 대상 역할의 이미지 또는 영상이다. C23/C24를 Cell/Cushion/Box에 임의 대응하지 않고 subject_role과 Component 원문 ID를 별도 관리한다.
정적 이미지가 있으면 정적으로 표시한다. 영상이 있으면 재생·일시정지·확대를 제공하는 안이다. Case 간 동기 재생은 시간 기준/시작점이 정합한 경우에만 허용하는 후속 정책이며, 같은 프레임 번호라는 이유로 동기라고 주장하지 않는다.
Cushion/Box 자료는 조사한 CSV/JPG 샘플에서 확인되지 않았다. 슬롯은 요구사항으로 설계하되 실제 매핑/영상 기능을 검증했다고 기록하지 않는다. 미제공 상태를 유지한다.

8. 원본 파일 없이 가능한 합성 검증 명세

8.1 작은 완전 합성 입력

Node_id,coord_x,coord_y,coord_z,ref_coord,C23_SIDE_TOP_L1,C23_SIDE_TOP_L2,C23_SIDE_TOP_L3,C23_SIDE_TOP_L4

8.2 20 Scene 그리드 검증
1~20 순번이 명시된 Scene을 만들고 각 Scene n에 값 n과 n+0.5를 가진 최소 코너 상세를 배치하는 테스트를 정의한다. 순번/Scene/Component 글자가 있는 합성 이미지 한 장씩을 연결한다. 단위는 테스트 원문 단위 미확인 상태를 유지한다.

기대: 카드 20개, 숫자 정렬 1..20, 최대값 1.5..20.5, 서로 다른 Scene의 자산 혼합 없음. Scene10 이미지 제거 시 카드/수치는 남고 이미지만 없음. Scene12 수치 제거 시 이미지 카드 유지, 그래프는 값 없음이며 0 아님. 기대 Scene 목록이 명시된 별도 시험에서만 폴더 미도착 상태를 표시한다.

역할과 순서
Astra: 확정 요구와 미결정 목록 확인 → 현재 저장 모델 조사 → 공통 ID/관계/조회 응답·마이그레이션 필요성 설계. Luna/Terra에게 동일 인터페이스를 전달한다.
Luna: 승인된 인터페이스에 따라 환경별 역할 인식, 파일 선택/파싱, 정규화, 원본/요약 구분, capture와 조회를 담당한다. 독립적인 순수 파서와 도메인 단위로 유지한다.
Terra: 같은 응답 예시로 Case/Run 선택, 종합표, Scene 그리드, 최대응력/위치/라인 그래프 및 문맥 전환을 담당한다. 프런트에서 별도 파일명 파싱·집계 기준을 만들지 않는다.
Sol: 요구사항–입력–기대값–실제 구현 대응을 검수한다. 누락/오류/동률/권한/과거 버전/기존 기능 회귀를 확인한다.
Astra: 통합 검증과 문서 갱신. 미확정 물리량·원본 부족으로 검증하지 못한 항목을 명시한다.
새 라이브러리보다 검증된 기존 그래프/미디어/파서/자산 계층 재사용을 우선한다. 대형 파일 무차별 조사·원본 실행·실제 사용자 DB 테스트를 하지 않는다.

10. 배포 및 승인 경계
향후 구현도 deploy.bat 최초 설치, update.bat 업데이트, 사용자 상태/계정/첨부 보존, 검증된 백업 후 migration, 앱 시작 시 스키마 검사만 수행하는 계약을 유지한다. Windows Server 2022 폐쇄망에서 Git/Node/인터넷을 요구하지 않는다. 새 의존성이 필요하면 lock/Windows x64/offline 패키징 검증도 같은 변경에 포함한다.

실제 현장 배포를 하지 않았으면 검증 완료라고 기록하지 않는다. 문서에 든 경로/값은 근거와 예시이며 파일 설치/다운로드/운영 데이터 적재 지시가 아니다.

사용자 확인이 필요한 물리/집계 결정은 가정으로 확정하지 않는다. 그 외 기존 정책 안의 구현 방식은 향후 구현 권한을 받은 Astra가 검토 가능한 설계로 구체화한다. 현재 작업의 최종 산출물은 Markdown 문서뿐이다.
