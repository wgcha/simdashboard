# 환경별 폴더 규칙과 결과 조회 UX 개선계획

작성일: 2026-09-19. 상태: **로컬 구현·검증 완료, 사내 배포 전**. 사용자가 이 계획의 구현과 최대한의 에이전트 분업을 지시했다. 이번 지시는 과거 화면·역할·Mode 설계보다 우선한다. 실제 버튼 순서는 [사용 안내](folder-environment-guide.md), 검증 결과는 `log/work-log.md`를 따른다. 아래 현황 표는 설계 당시 문제를 기록한 것이다.

구현은 환경 프로파일·버전, 부모 역할/이름 패턴/선택적 깊이, 역할 트리와 수동 확정, 미리보기, 업무 등록과 Case 수집, 이력·재시도, 옵션 원문과 안정 ID, 결과 딥링크를 포함한다. 규칙 제안은 `확인한 구조에서 가져오기`로 만들고 사용자가 패턴을 편집·재조사하여 확인한다. 이름·코드 추출과 읽기 레시피의 기존 고급 편집은 `기존 폴더 스키마`와 `의미 매핑`에 유지한다. 기존 규칙 복사는 의미가 동일한 역할만 옮긴다.

화면에서는 환경별 마지막 선택 규칙을 기억하고, 단일 결과 후보는 배지로 줄이며, 390px에서는 폴더 트리와 선택 폴더 설정을 전환한다. 초기 데이터 구성 화면에서도 기존 하중경우 없이 폴더 연결로 진입할 수 있다. 새 의존성은 없으며 DB migration `0030_folder_environment_profiles`를 배포 단계에서 적용한다. 실제 사내 자료와 Windows Server 2022 폐쇄망 설치·업데이트·재부팅 실기는 별도 운영 검증 대상이다.

## 1. 목표와 설계 결정

사용자는 실제 폴더를 조사하고 의미를 확인한 다음 같은 흐름에서 업무와 결과를 등록한다. 폴더 스키마 화면에서 등록했는데 Case 결과 화면에서 다시 같은 경로를 조사해야 하는 중복을 없앤다.

- 화면은 하나, 규칙은 **사용환경 / 유통환경** 두 종류로 분리한다. 기존 범용 규칙은 `기존 규칙`에서 계속 사용할 수 있다.
- 기본 사용자는 환경·폴더·해석된 구조만 확인한다. 깊이·코드 토큰·별칭·파일 읽기 설정은 필요한 행의 상세에서 편집한다.
- 프로젝트·의뢰·해석 Case·하중경우·Run Case·Run Option의 의미를 구분한다. 역할 이름만 추가하지 않고 조사·미리보기·저장·수집·조회까지 연결한다.
- 결과 화면은 선택한 의뢰와 환경에 맞는 컨트롤만 보여준다. 사용환경에 하중경우나 Run을 요구하지 않는다.
- 자동 추천과 확정된 연결을 구분한다. 이름·깊이만으로 애매한 폴더를 조용히 등록하지 않는다.

## 2. 현재 구현과 차이

| 현재 확인한 구현 | 개선 방향 |
|---|---|
| 폴더 역할 처리 동작은 PROJECT, REQUEST, LOAD_CASE, RESULTS, INPUT 5종 | 환경별 의미 계층을 실제 연결 대상으로 확장 |
| 폴더 조사는 절대 깊이와 포함 단어·구분자·토큰으로 분류 | 실제 트리에서 역할 지정, 부모 역할 기준 규칙과 선택 계층 지원 |
| 업무 생성과 dashboard Case capture가 별도 진입점 | 한 번의 조사·미리보기에서 등록과 수집으로 연결 |
| 유통환경 수집기는 명명 옵션으로 Individual/Cumulative만 인식하고 대문자 mode로 변환, 없으면 UNKNOWN | Run Option 원문·존재 여부를 보존, 미확인과 없음 구분 |
| Case·Capture·Run·Mode 등 다수 선택기를 노출 | 한 개뿐인 값은 표시로 축약하고 다중 후보만 선택 |

근거: `frontend/src/features/data/FolderDiscoveryWorkspace.tsx`, `backend/app/services/folder_discovery_plan.py`, `backend/app/services/dashboard_capture.py`, `frontend/src/features/results/SimulationDashboard.tsx`. 기존 상세 문서의 Mode/UNKNOWN 정의보다 이번 사용자 요청을 신규 계약 설계에 우선한다. 과거 데이터는 소급해서 추정하지 않는다.

## 3. 환경별 계층 계약

| 환경 | 의미 계층 |
|---|---|
| 사용환경 | 프로젝트 → 의뢰 → 해석 Case → 평가 항목 → 결과 파일 |
| 유통환경 | 프로젝트 → 의뢰 → 해석 Case → 하중경우 → Run Case → Run Option(선택) → Scene/결과 |

사용환경의 `Assy_RES_...`는 해석 Case다. `Settle`, `Wobble`, `Horizontal_Force_Angle`, `Slope_Angle`, `Slope_Angle_360`은 Case 내부 평가 항목이다. 누락된 평가가 있어도 다른 Case나 하중경우를 만들지 않고 해당 평가를 `자료 없음`으로 표시한다.

유통환경의 해석 Case와 Run Case는 서로 다른 개체다. 기존 AnalysisRun(파일 처리 실행), 수집 버전(Capture)과도 구분한다. 하중경우는 해석 Case에 속하고 Run Case는 그 하중경우에 속한다. 기존 의뢰 직속 LOAD_CASE 레코드로 자동 대체하거나 복제하지 않는다.

환경은 Case와 규칙 프로파일에 저장한다. 한 등록 작업은 환경 한 개를 대상으로 하며, 한 의뢰는 명시적으로 연결한 두 환경의 Case 집합을 보유할 수 있다. 표준 `WR_..._SimType1/2` 폴더는 별도 의뢰로 생성하며 같은 번호라는 이유로 합치지 않는다. 기존 의뢰에 두 환경을 연결하는 것은 사용자가 그 대상을 명시적으로 선택한 경우에만 가능하다.

### Run Option 규칙

- `Individual`, `Cumulative`는 기본 인식 후보이며 고정 enum으로 제한하지 않는다. 다른 이름은 트리에서 Run Option으로 지정하고 저장 규칙으로 재사용한다.
- 이름의 대소문자·원문을 표시와 출처에 보존한다. Run Option 이름으로 계산법이나 누적 의미를 추정하지 않는다.
- 옵션 폴더가 없으면 `옵션 없음`. 실제 경로가 `Run/Scene/...`인 결과와 `Run/Individual/Scene/...`인 결과를 모두 읽는다.
- 한 Run 안에 직접 Scene과 옵션 폴더가 함께 있어도 `옵션 없음`과 명명된 옵션을 별도 선택으로 유지한다. 같은 Scene 이름을 합치지 않는다.
- 확실한 없음은 ABSENT, 실제 옵션은 PRESENT, 분류가 불확실하면 UNRESOLVED로 구분한다. UNRESOLVED를 옵션 없음으로 숨기지 않는다.
- 일반 컨테이너 폴더는 역할 없이 통과할 수 있으나, 의미 있는 미분류 폴더를 무조건 통과시키지 않는다. 후보가 둘 이상이면 확인 대상으로 남긴다.
- 결과 하위 구조가 지원 읽기 규칙에 맞지 않으면 미지원 경로와 이유를 보여준다. 모든 임의 계층을 지원한다고 표시하지 않는다.

## 4. 폴더 스키마 화면: 세 단계로 통합

기존 메뉴 위치를 유지하고 화면 제목을 `폴더 연결·규칙`으로 정리한다. 기본 탭은 `폴더 연결`, 보조 탭은 `저장된 규칙`, `등록 이력`이다. 역할 사전·읽기 레시피·JSON 편집은 `고급 설정`으로 모은다.

```text
폴더 연결·규칙             [사용환경 ▾] [저장된 규칙 ▾]
① 폴더 선택 ── ② 구조 확인 ── ③ 등록·결과 확인

저장소 / 선택 경로                                  [폴더 선택]
┌ 실제 폴더 트리 ──────────────┬ 선택한 폴더 ────────────┐
│ Project_...    [프로젝트]    │ 역할: 해석 Case         │
│ └ WR_...      [의뢰]        │ 이름: Assy_RES_...       │
│   └ Assy...   [해석 Case]   │ 연결: 새로 등록 / 기존   │
│     └ Settle  [평가 항목]   │ [상세 규칙 ▾]           │
└─────────────────────────────┴────────────────────────┘
신규 3 · 기존 유지 2 · 확인 필요 1      [확인 필요만 보기]
                                      [이전] [등록 내용 확인]
```

### ① 폴더 선택

환경, 저장소 폴더, 적용할 저장 규칙을 한 줄씩 선택한다. `SimType1/2`는 추천 근거로 표시하며 사용자가 확인한 환경으로 저장한다. 여러 환경이 섞인 루트는 의뢰별로 분리해 각각의 규칙을 적용한다. 한 규칙으로 전체를 덮어쓰지 않는다.

첫 설정은 `기본 규칙으로 시작`, 반복 작업은 마지막으로 적용한 환경별 규칙을 추천한다. 의뢰 작업공간에서 열면 프로젝트·의뢰를 미리 채워 주며 기존 대상에 연결할 수 있다. 프로젝트 위 공유 폴더·CAE 같은 컨테이너 때문에 시작 위치가 달라도 부모 역할 관계를 기준으로 해석한다.

### ② 구조 확인

왼쪽 트리에 역할 배지를 붙이고 오른쪽에는 선택한 폴더 한 개의 설정만 표시한다. 환경별로 가능한 역할만 보여주고, Run Option에는 `선택 계층` 표시를 붙인다. 입력 폴더·결과 폴더는 공통 보조 역할로 유지한다.

역할을 지정하면 같은 부모 아래 유사한 폴더에 적용할 규칙을 제안하되 실제 일치 목록을 보여준다. 세부 규칙에는 부모 역할, 일치할 이름/패턴, 선택 계층 여부, 이름·코드 추출, 읽기 설정이 들어간다. 기존 깊이 규칙은 고급 방식으로 유지한다.

기본 화면은 폴더 원문 이름을 사용하고 코드 추출을 강제하지 않는다. 저장소·경로·부모 ID로 식별하며, 같은 WR 번호라도 환경이 다르면 병합하지 않는다. 기존 항목과 충돌하면 기존 대상 연결 또는 신규 등록을 명시적으로 선택한다.

전체 트리는 접어서 탐색하고 `확인 필요` 필터로 애매한 경로·읽기 실패·기존 연결 충돌을 모은다. 큰 트리와 긴 경로는 페이지/점진 로딩과 전체 경로 보기로 처리한다.

### ③ 등록·결과 확인

적용 직전에 신규·기존 유지·제외·충돌 건수, 연결될 대상과 읽을 파일 범위를 보여준다. 조사/규칙 저장/등록은 서로 구분한다. 규칙을 저장하는 것만으로 업무나 결과를 생성하지 않는다.

주 동작은 `등록하고 결과 읽기` 하나다. 필요한 등록 권한과 결과 수집 권한을 각각 검사한다. 조회 전용 사용자는 설정 버튼 없이 기존 결과를 연다. 충돌·불완전 조사가 남으면 해당 적용을 막고 이유와 수정 위치를 제공한다.

등록 완료 뒤 수집 상태를 같은 화면에서 표시하고, 성공하면 `결과 보기`로 정확한 의뢰·Case·수집 버전을 연다. 별도 Case 조사·게시 패널을 다시 열게 하지 않는다. 여러 Case면 성공/실패를 각각 보여주고 실패 건만 재시도한다.

업무/연결 등록과 파일 수집은 별도 상태로 기록한다. 수집 실패 시 `연결 완료 · 결과 읽기 실패`를 표시하고 기존 성공 버전을 보존한다. 재시도는 등록을 중복 생성하지 않는다. 장시간 수집은 진행 상태 조회와 화면 재진입을 지원하며 필요한 작업 저장 방식은 기존 인프라를 우선 활용한다.

등록은 미리보기 개정과 멱등 키를 검증해 DB 트랜잭션으로 한 번 확정하고, Case별 수집 작업은 그 확정 연결을 참조한다. 파일 읽기 전체를 등록 트랜잭션 안에 넣지 않는다. 연결 완료 건의 실패 재시도는 수집만 수행한다. 응답 유실·중복 클릭·새로고침 후에도 동일 작업 상태를 조회하고 중복 업무/Case/Run 생성을 막는다.

## 5. 결과 화면을 컴팩트하게

프로젝트·의뢰는 기존 공통 헤더 한 곳에서만 선택한다. 결과 영역에서 반복하지 않는다. 의뢰의 확정 환경은 배지로 표시하고 두 환경의 결과가 실제 존재할 때만 환경 전환을 노출한다.

| 사용환경 | 유통환경 |
|---|---|
| `해석 Case [선택]` | `해석 Case [선택] · 하중경우 [선택] · Run Case [선택]` |
| 바로 다섯 평가 표·그래프·미디어 표시 | Run Option이 여러 값일 때만 선택기를 표시 |
| 전방/후방/공통을 평가 결과 안에서 표현 | 옵션 한 개면 원문 배지, 없으면 `옵션 없음` 배지 |

공통 축약 정책:

- 후보가 한 개면 자동 선택하고 이름을 배지로 보인다. 여러 후보면 사용자가 고른다. 0개는 이유와 다음 행동을 표시한다.
- 새로 열 때 최신 **성공 수집 버전**을 기본으로 제안·선택하고 수집 시각/버전을 계속 표시한다. 열어 둔 화면이나 공유 URL의 버전을 자동으로 바꾸지 않는다. 과거 버전은 `수집 이력`에서 고른다. 이는 현재 모든 Capture를 수동 선택하는 방식의 변경 제안이다.
- 비교는 `비교 추가`를 누른 뒤 펼친다. 평소에는 Reference 선택기를 숨긴다.
- Component가 여러 개면 선택을 요구하고 한 개면 표시로 축약한다. 출처 집계와 상세 계산 기준이 여러 개면 의미를 설명하고 선택을 요구한다. 편의를 위해 서로 다른 값을 자동 혼합하지 않는다.
- 상위 선택 변경 시 하위 값과 이전 그래프를 함께 초기화한다. 늦게 온 응답은 현재 선택을 덮어쓰지 않는다.
- 같은 Case의 카탈로그 새로고침은 여전히 유효한 Case/Run/Option 선택과 고정 수집 버전을 유지한다. 더 이상 접근할 수 없는 선택만 이유를 표시하고 가장 가까운 유효 부모로 돌아간다. 새 수집 완료 알림에서 사용자가 새 버전을 열 수 있다.
- 미등록/미수집/읽기 실패/권한 없음/실제 값 없음의 빈 화면을 구분한다. 운영자는 `폴더 연결` 또는 `다시 읽기`로 이어갈 수 있다.
- Scene은 별도 장황한 설정 화면 대신 목록/그래프에서 선택하고 세부 결과를 같은 화면에 표시한다.
- 1366×768에서 설정 화면의 단계·경로·주 버튼을 동시에 확인하고, 결과 화면 첫 화면에 선택 문맥과 첫 평가 결과가 보이도록 한다. 390px에서는 트리→상세를 전환하고 주 버튼을 유지한다. 전역 가로 스크롤 없이 표 영역만 필요할 때 스크롤한다. 긴 이름 전체 보기·키보드 이동·접힌 설정의 접근성을 보장한다.

## 6. 구현 구조와 호환성

기존 조사기·권한·읽기 레시피·capture 서비스·표/트리 컴포넌트를 재사용한다. 계획 단계에서 새 라이브러리는 선정하거나 추가하지 않는다. 단순한 역할 enum 확장만으로 끝내지 않는다.

1. **규칙 계약**: 환경·버전·부모 역할·선택 계층·원문 유지 정책을 갖는 규칙 프로파일. 미리보기에는 실제 경로, 추천/확정 상태, 생성/기존 연결 대상, 오류를 반환한다.
   처리 종류에 SIMULATION_CASE와 EXECUTION_RUN(화면명 Run Case)을 추가한다. RUN_OPTION은 선택적 분류와 상태 계약을 갖고, EVALUATION/SCENE은 수집 결과 내부 분류이며 독립 업무나 폴더 registry 항목을 양산하지 않는다. 공통 LOAD_CASE 역할은 기존 규칙에서는 의뢰 직속 업무, 유통환경 규칙에서는 Case 소속 하중경우로 목적 모델을 명시한다. 역할 키만 같다는 이유로 두 모델의 ID를 호환 취급하지 않는다. 확정 연결 계획은 어떤 저장 대상에 쓰는지 포함한다.
2. **폴더 해석**: 사용/유통환경별 resolver를 분리하고 공통 경로·권한 검사를 공유한다. 조사 결과를 Case/Run/Option 연결 계획으로 만들며 수집기가 다른 규칙으로 재해석하지 않게 한다.
3. **등록·수집 연결**: 기존 dashboard Case/capture 모델을 재사용하고 discovery registry의 연결 대상을 확장한다. 저장소+경로+부모 문맥으로 안정적 식별자를 만들고 규칙 버전과 해석 근거를 수집 이력에 남긴다.
4. **Run Option 계약**: 내부 option ID, 원문 label, PRESENT/ABSENT/UNRESOLVED 상태를 분리한다. 조회·비교·미디어·캐시·Scene 식별·URL까지 option ID를 전달한다. 같은 Scene명과 파일명이 다른 옵션에 있어도 섞이지 않는다.
   ABSENT도 안정적인 식별값을 사용해 빈 선택값/UNRESOLVED와 구별한다. 공유 URL은 project/request/environment/Case/capture와 유통환경의 load-case/run/option 문맥을 포함하고, 접근 권한과 부모 관계를 서버에서 검증한다.
5. **호환 계층**: 기존 mode API와 저장 capture를 즉시 제거하지 않는다. 과거 UNKNOWN은 기본적으로 `미확인(기존 자료)`이며 근거 없이 ABSENT로 변환하지 않는다. 과거 대문자 값은 원문을 복원했다고 주장하지 않는다. 원본 재조사는 새 수집 버전으로 남긴다.

기존 저장 규칙은 원본 버전을 보존하고 `새 환경 규칙으로 복사`하여 차이와 연결 영향을 미리 본다. 과거 LOAD_CASE를 Case/Run으로 자동 변경하지 않는다. 기존 결과·업무 ID·연결·레시피·불변 capture를 유지한다. 기존 화면과 북마크는 계속 열 수 있도록 연결한다.

기존 5종 역할 카탈로그도 업데이트 후 조회·수정·저장이 가능해야 한다. 새 필수 종류 검증이 구 카탈로그를 거부하지 않도록 버전별 검증과 기본 항목 보완을 함께 설계한다. 원본 폴더가 사라진 경우 기존 연결/capture를 삭제하지 않고 `원본 경로 확인 필요`로 남긴다. 저장소 경계·symlink/reparse 제한·조사 깊이/개수/시간·파일/수집 크기 한도를 유지한다. UI 점진 로딩이 서버의 무제한 조사를 뜻하지 않게 한다.

DB 변경은 필요한 부분만 확정 후 migration으로 추가한다. 빈 설치와 기존 데이터 업데이트, 백업·권한·오프라인 배포 계약을 검증한다. `deploy.bat`, `update.bat`, 앱 시작 시 스키마 검사 원칙을 유지한다. 실제 사내 DB나 공유 폴더를 테스트 대상으로 사용하지 않는다.

## 7. 구현 순서와 완료 기준

| 단계 | 산출물 | 완료 기준 |
|---|---|---|
| 1. 의미 계약·샘플 | 사용/유통 규칙, 옵션 상태/API, 합성 트리, UI 와이어프레임 | 옵션 있음/없음/혼재와 기존 규칙의 예상 해석을 문서로 고정 |
| 2. 조사·등록 통합 | 환경별 resolver, 미리보기, Case/Run/Option 연결, 호환 migration | 사용환경5평가·유통Run/옵션이 올바른 부모에 연결되고 반복 적용 중복 없음 |
| 3. 폴더 설정 UI | 3단계 화면, 역할 트리, 행 상세, 충돌 필터, 등록·수집 상태 | 기본 흐름에서 깊이/토큰/JSON 편집 없이 등록 가능 |
| 4. 결과 UI | 환경별 선택 줄, 옵션 축약, 수집 이력, 등록 완료 직접 이동 | 등록 후 추가 폴더 조사 없이 결과 조회, 옵션 없는 Run도 정상 조회 |
| 5. 보존·배포 검수 | 회귀/접근성/실패 경로 검사, 사용자 안내 | 기존 규칙·결과 보존, 설치/업데이트 계약 통과, 수행하지 않은 실기는 명시 |

Astra가 계약·설계를 조정하고 통합 및 최종 검수한다. Terra는 resolver/등록·수집/API, Luna는 폴더 설정 UI, Sol은 Run Option의 수집·조회 계약과 결과 UI를 독립 담당한다. Sol도 구현에 활용하라는 최신 지시를 반영하며 인터페이스를 먼저 합의한다. 자기 구현 외 영역의 교차 검수와 Astra 최종 검수로 검증을 분리한다.

필수 인수 시나리오:

- 사용환경: Case 2개, 평가 누락, 전/후방 자료, 하중경우 0개인 의뢰.
- 유통환경: 옵션 없음, Individual만, Individual/Cumulative 함께, 사용자 정의 옵션, 직접 Scene과 옵션 혼재, Run/옵션별 동명 Scene.
- 컨테이너·조사 시작 깊이 차이·동일 WR 번호의 다른 환경·기존 연결 충돌·부분 조사 실패.
- 반복 등록·새 파일 재수집·수집 실패 후 재시도·규칙 수정 중 미리보기 만료·권한별 동작.
- 재수집 때 Capture만 갱신되고 Case/Run이 증식하지 않으며, 기존 선택과 고정 버전이 유지됨.
- 기존 규칙과 capture 조회·명시 버전 URL·느린 응답 중 환경/Case 전환·키보드·긴 이름·작은 화면.
- 기존 5종 카탈로그의 migration 후 저장, 평가5개/대량Scene의 업무·registry 비증식, 등록 응답 유실 후 재시도, 원본 경로 소실 시 보존, 경로 경계·조사 한도 검사.
- 한 후보 자동 선택/여러 후보 명시 선택/후보 없음이 구분되고 옵션 없음과 미확인이 뒤섞이지 않음.

## 8. 이번 범위에서 제외

원본 폴더 이동·재명명, 기존 업무의 자동 재분류, 사내 실자료 무단 재수집, 모든 파일 형식을 읽는 범용 파서, 폴더명만으로 계산 방식 추정, 주기적 자동 감시는 포함하지 않는다. 사내 실제 저장 규칙과 샘플 경로는 이후 연결 검증에 쓰되, 지금 확정한 계층 계약과 합성 자료로 개발할 수 있다.
