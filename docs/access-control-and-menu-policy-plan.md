# 사내 SSO·프로젝트 권한·좌측 메뉴 정책 구축 계획서

## 1. 문서 목적

이 문서는 Analysis Canvas에 다음 기능을 추가하기 위한 제품·보안 기준 문서다.

1. 사내 OIDC SSO를 통한 임직원 인증
2. 최초 접속자 승인과 계정 중지
3. 프로젝트별 `일반 사용자`, `파워 사용자`, `관리자` 역할
4. 전역 관리자와 프로젝트 관리자의 범위 분리
5. 역할과 프로젝트에 따른 기능·API 권한 제어
6. 권한과 전역 메뉴 정책을 결합한 좌측 메뉴 노출
7. 전역 관리자가 편집·버전 복원할 수 있는 메뉴 노출 정책
8. 사내 임직원 검색, 프로젝트 초대, 담당자 배정
9. 모든 보안 관련 변경의 감사 기록

상세 구현 순서와 파일·API·테스트 지시는 [권한 및 메뉴 정책 구현 수행서](./access-control-and-menu-policy-implementation-guide.md)를 따른다.

## 2. 현재 상태와 변경 이유

현재 시스템에는 다음 기반이 있다.

- `viewer`, `editor`, `admin` 전역 역할
- password 로그인과 HttpOnly 세션 쿠키
- HTTP 메서드와 URL 패턴 중심의 `minimum_role()` 검사
- `users`, `audit_events` 테이블
- 일부 프런트 버튼과 `작업 유형 관리` 메뉴의 역할별 노출
- 작업 담당자 문자열과 로그인 사용자의 표시 이름을 비교하는 실행 제한

그러나 다음 요구를 안전하게 처리하지 못한다.

- 같은 사용자가 프로젝트마다 다른 역할을 갖는 경우
- 일반 사용자의 본인 업무 실행과 파워 사용자의 의뢰 편집을 분리하는 경우
- 메뉴는 숨겼지만 직접 URL이나 API로 접근하는 경우
- 전역 관리자가 역할별 좌측 메뉴 노출을 운영 중 변경하는 경우
- 이름이 같거나 변경된 임직원을 담당자로 식별하는 경우
- SSO 최초 접속자를 승인 전 상태로 격리하는 경우

따라서 역할의 숫자 서열만 검사하지 않고, 역할을 세부 permission의 묶음으로 정의하며 프로젝트와 리소스 범위를 함께 검사한다.

## 3. 확정된 제품 결정

### 3.1 인증과 계정

- 운영 인증은 OIDC Authorization Code + PKCE 방식의 사내 SSO를 우선 사용한다.
- 최초 SSO 접속자는 `PENDING` 계정으로 생성한다.
- 전역 관리자가 승인한 `ACTIVE` 계정만 애플리케이션 데이터에 접근할 수 있다.
- 퇴직·휴직·보안 차단 대상은 `SUSPENDED`로 전환하며 다음 API 요청부터 기존 세션도 거부한다.
- 로컬 개발과 자동 테스트를 위해 기존 `password`, `disabled` 모드는 유지한다.
- 운영 환경에서는 `AUTH_MODE=oidc`만 허용한다.

### 3.2 데이터 조회 범위

- 승인된 사용자는 모든 프로젝트의 운영 대시보드, 의뢰 현황, 분석 결과와 보고서를 조회할 수 있다.
- 프로젝트 멤버십은 조회 범위가 아니라 해당 프로젝트의 편집·실행 범위를 결정한다.
- 멤버십이 없는 프로젝트에서는 조회 전용으로 동작한다.

### 3.3 역할 범위

- 프로젝트 멤버십 역할은 `general`, `power`, `admin` 세 가지다.
- 사용자마다 프로젝트별로 하나의 역할만 갖는다.
- 전역 관리자는 별도의 역할 종류를 만들지 않고 `admin` 권한이 시스템 전체와 모든 프로젝트에 적용되는 사용자로 취급한다.
- 프로젝트 관리자는 해당 프로젝트 안에서만 관리자 권한을 갖는다.
- 전역 관리자만 최초 사용자 승인, 계정 중지, 전역 설정, 메뉴 정책, 전체 감사로그를 관리한다.

### 3.4 임직원 검색과 담당자 배정

- 파워 사용자 이상은 현재 프로젝트의 승인된 멤버를 검색해 담당자로 지정할 수 있다.
- 프로젝트 관리자 이상은 사내 디렉터리에서 임직원을 검색해 프로젝트 초대를 만들 수 있다.
- 아직 승인되지 않은 임직원은 바로 담당자로 배정하지 않는다.
- 전역 관리자 승인과 프로젝트 멤버십 생성이 끝난 사용자만 담당자로 지정할 수 있다.
- 사용자 식별과 권한 판정은 표시 이름이 아니라 내부 `user_id`와 불변 OIDC subject를 사용한다.

### 3.5 좌측 메뉴 정책

- 좌측 메뉴는 로그인 사용자의 권한, 현재 선택 프로젝트, 전역 메뉴 정책을 결합해 계산한다.
- 전역 관리자는 `권한 및 메뉴 정책` 화면에서 역할별 메뉴 표시 여부를 변경할 수 있다.
- 메뉴 정책은 기능 권한을 부여하지 않는다. 역할상 허용된 메뉴를 추가로 숨길 수만 있다.
- 직접 URL과 API는 메뉴 표시 여부와 무관하게 서버 permission 검사로 보호한다.
- 전역 관리자의 사용자 승인·메뉴 정책 진입 경로는 전역 관리자에게 항상 표시하며 숨길 수 없다.

### 3.6 운영 플랫폼

- Windows 가상머신을 최종 운영·배포 기준 플랫폼으로 사용한다.
- 현재 가정용 Windows PC는 개발·테스트 환경으로 사용하며 운영 VM 검증과 구분한다.
- Windows VM의 PostgreSQL 마이그레이션, PowerShell 기반 시작·중지·상태 확인, 백업·복구, 로그·경로, HTTPS reverse proxy와 OIDC 쿠키 동작을 배포 release gate로 삼는다.
- Linux 호환 코드와 Ubuntu CI는 유지하되 운영 완료의 필수 증거가 아니라 교차 플랫폼 회귀 방지 증거로 사용한다.
- Windows와 Linux의 스크립트 구현은 달라도 데이터·권한·보안·복구 의미는 동일해야 한다.

### 3.7 다른 기능과의 독립성 및 사내 이전

- 권한 기능은 `인증 공급자`, `임직원 디렉터리`, `권한 정책`, `메뉴 정책`, `감사` 모듈로 분리하고 분석·의뢰·실행 도메인은 공개된 권한 facade만 호출한다.
- 로컬/Windows 개발은 외부 사내 시스템 없이 `disabled` 또는 `password` 인증과 local directory adapter로 실행할 수 있어야 한다.
- Windows VM 사내 운영은 동일한 facade 뒤에서 OIDC와 HTTP directory adapter를 선택한다. 사내 IdP·인사시스템의 vendor 응답 형식을 도메인 모델이나 UI에 직접 노출하지 않는다.
- 권한 DB 변경은 기존 분석 결과·의뢰·실행 테이블을 삭제하거나 재작성하지 않는 additive migration을 기본으로 한다. 담당자 ID 전환처럼 기존 테이블을 확장하는 경우 원문 snapshot을 보존하고 dry-run 결과를 먼저 제공한다.
- 사내 이전 전용 preflight는 계정 충돌, 중복 임직원 ID, 매칭되지 않은 담당자, 프로젝트별 관리자 부재, 메뉴 정책 버전, DB revision을 보고하며 데이터 변경 없이 실행할 수 있어야 한다.
- 운영 adapter 설정이 없거나 연결에 실패하면 권한을 추정하거나 로컬 계정으로 자동 우회하지 않는다.

## 4. 요구사항 목록

### 4.1 인증 요구사항

| ID | 요구사항 |
|---|---|
| AUTH-01 | OIDC 로그인은 Authorization Code, PKCE, state, nonce를 검증한다. |
| AUTH-02 | 최초 SSO 사용자를 `PENDING`으로 생성하고 승인 대기 화면만 허용한다. |
| AUTH-03 | `ACTIVE`만 일반 API를 사용하고 `SUSPENDED`는 다음 요청부터 즉시 차단한다. |
| AUTH-04 | 운영 세션은 HttpOnly, Secure, SameSite 쿠키를 사용하고 토큰을 브라우저 저장소에 저장하지 않는다. |
| AUTH-05 | OIDC issuer와 subject 조합을 사용자 외부 식별자의 유일 키로 사용한다. |
| AUTH-06 | password/disabled 모드는 개발·테스트 호환성을 위해 유지한다. |

### 4.2 역할·권한 요구사항

| ID | 요구사항 |
|---|---|
| RBAC-01 | 프로젝트 멤버십은 프로젝트마다 `general`, `power`, `admin` 중 하나다. |
| RBAC-02 | 전역 관리자는 모든 프로젝트의 admin permission과 시스템 permission을 갖는다. |
| RBAC-03 | 일반 사용자는 본인에게 배정된 업무만 시작·진행·완료할 수 있다. |
| RBAC-04 | 파워 사용자는 해당 프로젝트의 의뢰·워크플로·결과를 편집할 수 있다. |
| RBAC-05 | 프로젝트 관리자는 해당 프로젝트의 대시보드·기준·변수·멤버를 관리할 수 있다. |
| RBAC-06 | 프로젝트 관리자는 다른 프로젝트의 변경 권한을 갖지 않는다. |
| RBAC-07 | 전역 사용자 승인·전역 설정·메뉴 정책·전체 감사로그는 전역 관리자만 접근한다. |
| RBAC-08 | 권한 검사는 HTTP 메서드 서열이 아니라 명시적 permission과 리소스 범위로 수행한다. |
| RBAC-09 | 승인된 사용자는 모든 프로젝트의 읽기 기능을 사용할 수 있다. |
| RBAC-10 | 전역 관리자의 타인 업무 실행은 별도 `work.execute_any` permission과 구체 감사 이벤트가 있을 때만 허용한다. |

### 4.3 메뉴 정책 요구사항

| ID | 요구사항 |
|---|---|
| MENU-01 | 좌측 메뉴는 `계정 활성 + permission 충족 + 메뉴 정책 표시 + 화면 컨텍스트 충족`일 때만 표시한다. |
| MENU-02 | 전역 관리자는 역할별 좌측 메뉴 표시 여부를 저장할 수 있다. |
| MENU-03 | 메뉴 정책은 permission을 확대하지 못한다. |
| MENU-04 | 메뉴 정책 변경은 버전과 감사로그를 남긴다. |
| MENU-05 | 전역 관리자는 이전 메뉴 정책 버전을 미리 보고 복원할 수 있다. |
| MENU-06 | 마지막 전역 관리자와 전역 관리자 필수 메뉴는 비활성화할 수 없다. |
| MENU-07 | 정책 변경 또는 역할 회수 후 현재 페이지가 허용되지 않으면 안전한 기본 화면으로 이동한다. |
| MENU-08 | 메뉴 정책으로 숨긴 화면은 직접 UI 진입도 막지만, API 허용 여부는 메뉴 정책이 아니라 permission으로 판정한다. |

### 4.4 디렉터리·멤버십 요구사항

| ID | 요구사항 |
|---|---|
| DIR-01 | 사내 임직원 검색은 백엔드가 디렉터리 API를 대행한다. |
| DIR-02 | 검색은 최소 2자, 결과 수 제한, 타임아웃, 최소 개인정보 필드를 적용한다. |
| DIR-03 | 프로젝트 관리자는 검색 결과로 초대를 만들 수 있다. |
| DIR-04 | 전역 관리자 승인 전에는 프로젝트 멤버십과 담당자 배정을 완료할 수 없다. |
| DIR-05 | 담당자 후보는 `ACTIVE`이며 해당 프로젝트 멤버인 사용자로 제한한다. |
| DIR-06 | 임직원 검색·초대·승인·역할 변경을 감사 기록한다. |

### 4.5 감사·운영 요구사항

| ID | 요구사항 |
|---|---|
| AUDIT-01 | 로그인 성공·실패·승인 대기·계정 차단을 감사 기록한다. |
| AUDIT-02 | 사용자 상태, 전역 관리자, 프로젝트 역할, 메뉴 정책 변경 전후 값을 기록한다. |
| AUDIT-03 | 감사 이벤트는 수행자, 대상, 프로젝트, 요청 ID, 결과 상태를 포함한다. |
| AUDIT-04 | 비밀번호, OIDC 토큰, 디렉터리 토큰, secret과 불필요한 개인정보를 기록하지 않는다. |
| OPS-01 | 사내 SSO나 디렉터리 장애 시 권한을 우회하지 않고 명시적인 오류를 반환한다. |
| OPS-02 | 신규 스키마와 인덱스는 PostgreSQL과 테스트용 DuckDB에서 동일한 의미를 갖는다. |
| OPS-03 | 기존 viewer/editor/admin 데이터는 새 모델로 손실 없이 이전한다. |
| OPS-04 | Windows VM 운영 배포를 release gate로 삼고 가정용 Windows 테스트와 Linux CI에서도 동일한 기능 의미를 검증한다. |

### 4.6 모듈 독립성과 사내 이전 요구사항

| ID | 요구사항 |
|---|---|
| MOD-01 | 분석·의뢰·실행 도메인은 사내 OIDC·디렉터리 구현을 직접 import하지 않고 권한 facade만 호출한다. |
| MOD-02 | 인증과 임직원 검색은 provider adapter로 교체 가능하며 local과 intranet profile이 같은 DTO 계약을 사용한다. |
| MOD-03 | local profile은 외부 네트워크 없이 Windows 개발·테스트가 가능하고 intranet profile은 Windows VM에서 fail-closed로 동작한다. Linux CI는 같은 계약의 이식성을 검증한다. |
| MOD-04 | migration은 기존 원문과 업무 데이터를 보존하고 dry-run/preflight 결과 없이 파괴적 변환을 수행하지 않는다. |
| MOD-05 | 사내 이전 preflight는 사용자·담당자·프로젝트 관리자·메뉴 정책·DB revision의 충돌과 누락을 기계 판독 가능한 보고서로 제공한다. |
| MOD-06 | 사내 vendor claim/응답 차이는 adapter 내부에서 정규화하며 DB·API·React는 provider 중립 필드만 사용한다. |

## 5. Permission 모델

### 5.1 Permission 목록

| Permission | 의미 | 범위 |
|---|---|---|
| `company.dashboard.view` | 전사 운영 대시보드 조회 | 전사 |
| `project.data.view` | 프로젝트·의뢰·분석 결과 조회 | 전사 읽기 정책 |
| `report.export` | 접근 가능한 결과의 보고서 생성 | 전사 읽기 정책 |
| `work.execute_assigned` | 본인 배정 업무 시작·진행·완료 | 프로젝트+소유자 |
| `work.execute_any` | 담당자가 지정된 타인 업무의 관리자 비상 실행 | 시스템+감사 |
| `request.create` | 의뢰 생성 | 프로젝트 |
| `request.edit` | 의뢰 정보·유형·담당자 수정 | 프로젝트 |

## 6. 좌측 메뉴 기본 정책

### 6.1 메뉴 표시 계산식

```text
visible(menu, user, selected_project) =
  user.account_status == ACTIVE
  AND has_permission(user, menu.required_permission, selected_project)
  AND role_menu_policy(menu.id, policy_role).is_visible
  AND menu.context_requirement_is_satisfied
```

- 전사 읽기 메뉴는 프로젝트가 선택되지 않아도 표시할 수 있다.
- 프로젝트 변경 메뉴는 선택 프로젝트에서 permission을 가질 때만 표시한다.
- 사용자가 프로젝트 A에서는 power, 프로젝트 B에서는 general이면 선택 프로젝트에 따라 메뉴가 즉시 바뀐다.
- `policy_role`은 선택 프로젝트의 membership role이며, 멤버십이 없는 조회 전용 프로젝트에서는 `general`을 사용한다. 전역 관리자는 메뉴 정책을 우회해 필수 관리자 메뉴를 포함한 전체 허용 메뉴를 본다.
- 메뉴 정책 행이 없으면 코드에 정의한 기본값을 사용하지 않고 서버가 seed한 활성 정책을 사용한다.
- 정책 조회 실패 시 변경 메뉴를 추정해 표시하지 않고 최소 읽기 메뉴만 표시한다.

### 6.3 전역 관리자 메뉴 정책 화면

- 행은 등록된 메뉴, 열은 `일반`, `파워`, `프로젝트 관리자` 역할이다.
- 각 셀은 `표시` 또는 `숨김`이며 permission이 없는 조합은 잠금 상태로 보여준다.
- 저장 전 변경 요약을 보여주고 한 번의 트랜잭션으로 저장한다.
- 활성 정책 버전과 마지막 변경자·변경 시각을 표시한다.
- 버전 목록에서 과거 정책을 읽기 전용으로 비교하고 복원할 수 있다.
- 복원은 과거 버전을 다시 활성화하지 않고 동일 내용의 새 버전을 생성한다.
- `menu_policy_admin`, `audit_admin` 등 전역 관리자 복구 경로는 정책 편집 대상에서 제외한다.

## 7. 사용자 흐름

### 7.1 최초 로그인과 승인

1. 사용자가 `사내 SSO 로그인`을 선택한다.
2. 백엔드가 OIDC state, nonce, PKCE verifier를 서버 세션에 저장하고 IdP로 이동시킨다.
3. 콜백에서 issuer, subject, employee ID와 최소 프로필을 검증한다.
4. 신규 사용자는 `PENDING`으로 생성하고 승인 대기 화면으로 이동시킨다.
5. 전역 관리자가 사용자 정보를 확인하고 승인 또는 거부한다.
6. 승인 후 사용자가 새로고침하거나 다시 로그인하면 읽기 메뉴를 사용할 수 있다.

### 7.2 프로젝트 초대와 역할 부여

1. 프로젝트 관리자가 현재 프로젝트의 `사용자·프로젝트 권한`을 연다.
2. 임직원 ID, 이름 또는 이메일 일부로 디렉터리를 검색한다.
3. 이미 `ACTIVE`인 사용자는 즉시 프로젝트 역할을 부여할 수 있다.
4. 미등록·미승인 사용자는 초대 요청을 만들고 `승인 대기`로 표시한다.
5. 전역 관리자가 계정을 승인한 뒤 프로젝트 관리자가 멤버십을 확정한다.
6. 역할 변경은 즉시 다음 API 요청과 메뉴 계산에 반영한다.

### 7.3 업무 담당자 지정과 실행

1. 파워 사용자 이상이 현재 프로젝트의 `ACTIVE` 멤버를 검색한다.
2. 선택한 `user_id`를 의뢰·단계·작업의 `owner_user_id`로 저장하고 이름은 스냅샷으로 함께 저장한다.
3. 일반 사용자는 본인 `owner_user_id`와 일치하는 작업의 실행 버튼만 활성화된다.
4. 서버는 버튼 상태와 무관하게 실행 API마다 담당자를 다시 검사한다. 전역 관리자의 타인 업무 실행은 별도 `work.execute_any` 권한으로만 허용하고 구체적인 관리자 override 감사 이벤트를 남긴다.

## 8. 데이터와 보안 원칙

- OIDC access/refresh/id token과 디렉터리 API 토큰은 DB, 감사로그, 프런트 저장소에 저장하지 않는다.
- 디렉터리 결과는 임직원 ID, 표시 이름, 부서, 직책, 업무 이메일, 재직 상태로 제한한다.
- 검색어 원문은 감사로그에 남기지 않고 검색 수행 사실과 결과 수만 기록한다.
- 세션 주체는 매 요청 DB에서 계정 상태를 재확인한다.
- 변경 API는 클라이언트가 보낸 `created_by`, `updated_by`, `completed_by`를 신뢰하지 않고 principal에서 생성한다.
- 역할·메뉴 정책 변경은 낙관적 버전 검사를 적용해 덮어쓰기를 방지한다.
- 전역 관리자 수가 1명일 때 해당 사용자의 전역 관리자 해제나 중지는 `409`로 거부한다.
- API는 존재하는 프로젝트를 숨길 필요가 없으므로 권한 부족에 `403`, 존재하지 않는 리소스에 `404`를 사용한다.

## 9. 마이그레이션 원칙

- 기존 `admin` 계정은 `ACTIVE`, `is_global_admin=true`로 이전한다.
- 기존 `editor` 계정은 `ACTIVE`로 이전하고 모든 기존 프로젝트에 `power` 멤버십을 생성한다.
- 기존 `viewer` 계정은 `ACTIVE`로 이전하고 모든 기존 프로젝트에 `general` 멤버십을 생성한다.
- 기존 사용자 이름과 owner 문자열이 정확히 하나의 사용자와 일치하면 `owner_user_id`를 채운다.
- 일치하지 않거나 중복된 owner는 문자열을 보존하고 `owner_user_id=NULL`로 둔다.
- `owner_user_id=NULL`인 기존 작업은 조회 가능하지만 재배정 전 실행할 수 없다.
- 초기 메뉴 정책은 6.2의 기본 노출표로 seed한다.
- 기존 password hash는 개발·호환 모드에서만 사용하고 OIDC 계정은 password hash를 요구하지 않는다.

## 10. 완료 기준

다음 조건을 모두 만족해야 기능이 완료된 것으로 본다.

1. 일반·파워·프로젝트 관리자·전역 관리자 네 사용자 시나리오의 좌측 메뉴가 기본 정책과 일치한다.
2. 전역 관리자가 역할별 메뉴를 숨기고 다시 표시하면 활성 세션에 반영된다.
3. 메뉴를 표시하도록 설정해도 역할 permission이 없으면 메뉴와 API가 허용되지 않는다.
4. 메뉴 정책으로 숨겨진 화면의 URL을 직접 열면 안전한 화면으로 이동한다. API는 별도로 permission을 검사하며, permission이 있으면 메뉴가 숨겨져도 허용되고 permission이 없으면 `403`을 반환한다.
5. 일반 사용자는 본인 업무만 시작·진행·완료하며 다른 사용자의 업무는 UI와 API 모두 거부된다.
6. 파워 사용자는 의뢰·업무 흐름·결과를 편집하지만 대시보드·기준·변수·멤버는 변경하지 못한다.
7. 프로젝트 관리자는 자신의 프로젝트만 관리하고 다른 프로젝트 변경 요청은 거부된다.
8. 전역 관리자는 승인·중지·메뉴 정책·전역 설정·감사로그를 관리할 수 있다.
9. 신규 SSO 사용자는 승인 전 데이터를 볼 수 없고 `SUSPENDED` 사용자의 기존 세션은 즉시 차단된다.
10. 미승인 임직원은 담당자로 배정할 수 없다.
11. 메뉴 정책, 사용자 상태, 프로젝트 역할 변경은 변경 전후 값과 수행자가 감사로그에 남는다.
12. PostgreSQL 마이그레이션, DuckDB 테스트 스키마, 백엔드 테스트, 프런트 빌드, Playwright E2E가 모두 통과한다.
13. Windows 개발 테스트와 Ubuntu Linux CI가 통과하고, 운영 Windows VM에서 PostgreSQL 마이그레이션·백엔드·프런트·OIDC smoke test가 통과한다.
14. local profile에서 사내 연결 없이 기존 기능을 개발·테스트할 수 있고, migration preflight가 실제 데이터 변경 없이 사내 이전 위험을 보고한다.

## 11. 범위 제외

- 전역 관리자가 permission 묶음 자체를 자유롭게 생성·삭제하는 기능
- 사용자별 임의 permission 예외
- 프로젝트별로 서로 다른 메뉴 정책을 운영하는 기능
- 부서·직급에 따른 역할 자동 부여
- SAML 동시 지원
- 사내 디렉터리 원본 데이터의 로컬 동기화 저장소 구축
- 승인 워크플로의 다단계 결재
