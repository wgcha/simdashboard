# Windows 배포 정책 — 모든 소스 변경의 유지 계약

- 기준일: 2026-09-14
- 상태: 현재 개발 기준
- 적용: 기능 개발, 버그 수정, 패키지 업데이트, DB migration, 소스/설치 파일 배포
- 사용자 요구: 소스가 수정·개발되어도 배포 방식과 데이터 보존 정책이 한결같아야 한다.

## 바뀌지 않는 사용 흐름

| 대상 | 최초 배포 | 이후 업데이트 | 실행 환경 |
|---|---|---|---|
| 소스 PC | 소스 전체 압축 해제 → `deploy.bat` → 최초 연결/계정 입력 → 실행 | `update.bat` → 백업·업데이트·상태 확인 | PostgreSQL 준비됨, 외부 의존성 다운로드 가능 |
| 폐쇄망 서버 | 완결 설치 패키지 반입 → 설치 진입점 → DB 방식/계정 입력 → 서비스 실행 | 새 패키지의 같은 설치 진입점 → 기존 경로/설정 보존 → 백업·업데이트·상태 확인 | Windows Server 2022 x64만 사전 설치 |

새 기능을 쓰기 위해 대상 서버에 Python·Node.js·Git·VS Code·인터넷 연결을 수동으로 추가하도록 배포 전제조건을 바꾸지 않는다. 운영자가 입력할 자격 증명과 서비스 등록 UAC 승격은 최초 설치 안내 안에 둔다.

## DB와 실패 처리

- PostgreSQL 서버의 다른 DB를 변경하지 않는다. 앱 DB가 없으면 전용 DB와 최소 권한 역할을 준비한다.
- 실제 빈 대상은 최초 스키마를 적용한다. 테이블에 행이 없더라도 기존 revision이 있으면 업데이트로 취급한다.
- 기존 DB는 설정·데이터·계정·관리형 첨부파일 백업을 검증한 뒤 migration한다. 백업 실패, 인증/권한 오류, 미식별 스키마, 복구 대기 상태에서는 중단한다.
- 원클릭 배포에 기존 DB 교체·초기화·다른 PC 데이터 덮어쓰기를 섞지 않는다. 명시적 백업/복원/이관 작업은 별도다.
- 앱 시작이나 재부팅은 migration을 수행하지 않는다. DB가 새 소스와 맞지 않으면 배포 경로로 안내한다.
- migration 시작 이후 실패하면 이전 앱 자동 재실행으로 성공 처리하지 않는다. DB 복구와 앱 복구의 절차를 구분한다.
- 앱 업데이트로 PostgreSQL 메이저 버전을 변경하지 않는다.

## 패키지와 상태의 경계

설치 패키지는 검증할 수 있는 릴리스 코드, 정적 웹, Python과 잠긴 의존성, PostgreSQL과 백업 도구, Caddy, 서비스 래퍼, 필요한 시스템 런타임을 포함한다. wheel 검증은 대상과 같은 Windows x64/Python 버전으로 수행한다. `.venv` 폴더를 다른 PC에서 복사해 실행 가능하다고 가정하지 않는다.

설치 후 설정·인증 키·DB 데이터·첨부파일·백업은 영구 상태이며 소스 교체에서 제외한다. 빌드는 허용된 소스 경로만 패키징하여 개발 PC의 사용자 데이터·비밀·로그를 반입하지 않는다. 파일 목록과 SHA-256 manifest로 누락/변조를 거부한다. 해시는 배포자 서명을 대체하지 않는다.

## 변경 종류별 완료 조건

| 변경 | 같은 변경에 포함할 사항 |
|---|---|
| 프런트엔드 | 정적 빌드 통과, API 프록시/기본 경로 호환, 개발 서버 없는 패키지 실행 유지 |
| Python/라이브러리 | lock 갱신, Windows wheel 준비, 네트워크 없는 의존성 설치·import 확인 |
| OS 바이너리/런타임 | 공식 출처·버전·무결성 기록, 라이선스 동봉, bare Server 2022 전제 유지 |
| DB 스키마 | 신규/기존 revision 경로, 기존 데이터·계정 유지, 백업 실패 시 변경 차단 |
| 파일/저장 경로 | 릴리스와 영구 상태 분리, 기존 데이터 접근·백업 범위 유지 |
| 배포/시작/종료 | 기존 진입점/인수 호환, 자체 서비스만 제어, 실패 코드와 상태 확인 |

`AGENTS.md`는 이 정책을 모든 개발 작업에 적용한다. `.github/workflows/windows-deployment-contract.yml`은 구현의 계약 검사를 수행한다. 테스트를 제거하거나 완화하여 정책 위반을 통과시키지 않는다. 구조적으로 다른 구현으로 바꿀 때도 같은 실패·보존 시나리오를 실행하는 검사를 유지한다.

## 릴리스 기록

개발 문서에는 구현한 기능, 실행한 검사, 실제 패키지 파일, 대상 OS 실기 검증 여부를 구분한다. 실제 폐쇄망 Server 2022 VM에서 신규 설치·업데이트·재부팅을 검증한 릴리스만 현장 검증 완료로 기록한다. 검증 기록은 소스 revision/작업 트리 상태, 패키지 해시, 런타임 버전, 결과를 포함한다.

정책 변경은 최신 사용자 지시를 근거로 ADR와 이 문서, 설치 안내, 계약 검사를 함께 갱신한다. 일반 기능 개발이 이 계약을 조용히 바꾸어서는 안 된다.
