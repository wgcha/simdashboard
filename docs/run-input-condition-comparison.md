# Run 입력 조건 비교

상태: 조건 비교·조건 메타데이터 저장 구현 및 기능 검증 완료 · 2026-09-11

## 목적과 사용 경로

결과 검토 → Run 비교에서 기준/대상 Run의 기록된 입력 조건을 비교한다. 재료·두께·하중·접촉 및 해석기 차이를 결과 변화와 함께 확인한다. 조건 차이는 원인 후보를 좁히는 근거이며, 결과 변화의 원인으로 자동 확정하지 않는다.

기존 Run 비교 위젯에 조건 패널을 추가한다. 위젯 위치·편집·레이아웃 저장과 영상 열/행 설정은 유지한다. 새로운 승인 절차나 과거 Run 입력을 수정하는 기능은 추가하지 않는다.

## 데이터 원칙

- Run에 직접 연결된 실행 입력 기록과 해당 Run의 명시적 조건 메타데이터만 사용한다.
- 현재 하중 경우의 parameters나 현재 제품 사양을 과거 Run의 조건으로 대입하지 않는다.
- 실행 기록은 Run과 동일한 하중 경우에 속하는지 확인한다.
- 기록의 출처를 값과 함께 확인할 수 있게 한다. 서로 다른 출처가 충돌하면 임의의 우선순위를 적용하지 않는다.
- 숫자 0과 false는 기록된 값이다. null·빈 기록·잘못된 형식과 구별한다.
- 단위가 다르거나 필요한 단위가 없으면 자동 환산하거나 수치 차이를 계산하지 않는다.
- 양쪽 모두 미기록이어도 ‘동일’이 아니다. 한쪽만 기록된 경우도 실제 조건의 추가/삭제를 추정하지 않는다.
- 구조화 값은 키 순서만 다른 객체를 같은 값으로 볼 수 있으나 배열의 순서는 보존한다.

## 화면과 판정

| 상태 | 의미 |
|---|---|
| 변경 | 양쪽의 비교 가능한 기록이 다름 |
| 동일 | 양쪽의 비교 가능한 기록이 같음 |
| 확인 필요 | 미기록·불완전·단위 불일치·출처 충돌 등으로 결론을 낼 수 없음 |

상단에는 변경 및 확인 필요 건수를 표시하고, 기본 목록에서 변경/확인 필요를 먼저 보여준다. 전체 보기로 동일한 기록도 확인한다. 각 행에서 항목명, 기준/대상 값과 단위, 판정 및 사유, 출처를 읽을 수 있다. 모든 표시 항목이 같아도 전체 모델·메시·경계 조건의 동일성을 인증한다는 뜻은 아니다.

## 구현 및 검증 범위

- 기존 run-comparison 응답에 condition_comparison을 추가하며, 예전 응답을 받는 UI는 조건 기록 확인 필요로 처리한다.
- 비교 정책은 별도 모듈로 분리한다. DB 스키마 변경 없이 기존 기록을 사용한다.
- 기록된 차이/동일/양쪽 미기록/한쪽 미기록/0·false/단위 불일치/객체·배열/출처 충돌/다른 하중 경우 실행 기록을 검증한다.
- 기존 비교·초안·시계열 전환 회귀와 조건 필터·Run 전환·작은 화면을 검증한다.
- Browser plugin not available: 기존 프로젝트 Playwright와 격리된 예제 서버를 사용한다.

## 결과와 함께 조건 기록하기

마스터 폴더 가져오기를 사용하는 생산자는 기존 `manifest.json`의 `metadata.run_conditions`에 해당 실행의 조건을 넣는다. 아래는 전체 manifest가 아닌 추가할 metadata 부분이다. 결과 파일·대상 의뢰·하중 경우 등 기존 필수 항목은 [마스터 폴더 계약](work-type-request-results-and-master-refresh.md)을 따른다.

```json
{
  "metadata": {
    "run_conditions": {
      "material": "SPCC",
      "thickness": { "value": 1.2, "unit": "mm" },
      "pressure_mpa": 0.5,
      "contact": { "type": "surface_to_surface", "friction": 0.2 },
      "mesh_size_mm": 2
    }
  }
}
```

- 마스터 폴더 새로고침으로 새 Run을 적재할 때 조건을 함께 저장한다. 과거 Run을 현재 manifest 내용으로 덮어 채우지 않는다.
- 선택적인 조건 기록만 추가하므로 기존 manifest는 그대로 가져올 수 있다. 수동 요약 파일/CSV 업로드에 조건 입력 UI를 새로 추가한 것은 아니다.
- 최상위 조건 최대 64개, UTF-8 JSON 16 KiB, 중첩 깊이 6 이내를 허용한다. 잘못된 형식은 `RUN_CONDITIONS_INVALID`로 가져오기 전에 거부한다.
- 기본 항목의 정확한 키: `material`, `material_id`, `material_grade`, `thickness`, `thickness_mm`, `load`, `load_case`, `pressure_mpa`, `drop_height_mm`, `hold_time_sec`, `contact`, `contact_type`, `mesh_size_mm`. `solver`는 Run 자체의 해석기 기록을 사용한다.
- `thickness_mm`와 단위 mm를 명시한 `thickness`는 같은 두께 항목으로 모은다. 재질명/ID/등급과 압력/낙하높이는 서로 다른 정보를 나타내므로 각각 표시한다.
- 압력·낙하높이·유지시간·메시 크기의 단위는 명시적인 키에서 MPa/mm/s/mm로 읽는다. 단위가 생략된 일반 숫자 두께·하중은 확인 필요다. 단위 환산은 하지 않는다.
- 추가 조건은 `run_conditions` 내부에 명시한 경로로 비교한다. 바깥쪽 metadata의 작성자·체크섬 등을 입력 조건으로 추정하지 않는다.

## 검증 결과와 플랫폼 제한

- 백엔드 35개 테스트 통과(14.18초): 신규 조건 정책·metadata 검증·파서/DB 저장 연계 및 기존 분석 계약을 함께 검증했다. 두 번 가져온 조건 차이가 비교 응답에 반영되고 첫 Run의 조건은 보존되며 같은 내용 재처리는 SKIPPED임을 확인했다.
- 브라우저 테스트 9개 통과(새 조건 시나리오 3개와 기존 비교 시나리오 6개). 실제 예제 Run의 미기록 처리, 제어된 조건 차이/출처/전체 보기/Run 전환, 구버전 응답, 모바일 가로 넘침과 pageerror 없음 확인.
- 데스크톱 1505×1045 및 모바일 390×844 캡처 확인. 기존 위젯 내부 스크롤로 조건과 결과 근거를 이어서 탐색한다.
- 프론트엔드 빌드와 아키텍처 검사(154 source files) 통과. 기존 500 kB 초과 번들 경고 유지.
- **Windows 가져오기 제한:** 기존 snapshot workspace의 POSIX `0700` 검사와 DuckDB 가져오기 실행 잠금의 `fcntl` 의존 때문에 이 Windows 환경에서 전체 마스터 폴더 새로고침 서비스는 실행되지 않았다. 이 기능에서 운영 보안 검사나 잠금을 우회하지 않았다. 저장 연계 테스트는 실제 manifest 파서 → 마스터 command 어댑터 → DB 트랜잭션 → 비교 쿼리를 호출해 검증했고, 폴더 권한·프로세스 잠금·전체 서비스 운영 검증과 구분한다. Windows에서 마스터 폴더 가져오기를 사용하려면 기존 플랫폼 제약을 별도로 해결해야 한다.
- QA 캡처·브라우저 로그: 저장소 밖 Codex visualization 작업 폴더 `run-conditions-qa`. 기존 고객의 미기록 조건을 자동 복구하지 않는다.
