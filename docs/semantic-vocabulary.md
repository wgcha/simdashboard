# 기준 정의·별칭 사전

기준일: 2026-09-15. 사용자 요청 1번(기준 정의·별칭 관리)의 구현 계약이다. [전체 계획](semantic-storage-mapping-plan.md)과 [배포 정책](windows-deployment-policy.md)을 따른다. 상태: 구현·검증 완료, 실제 서버 배포 전.

## 기준 정의와 실제 대상

사전 항목은 고정 키, 표시명, 설명, 연결할 기준 종류와 대상, 여러 별칭을 가진다. 예를 들어 `project_eagle` 정의에 `Eagle_2026`, `이글`, `Eagel`을 등록하여 기존 프로젝트 ID 하나에 연결한다. `peak_stress` 정의에는 `Smax`, `Max Stress`, `최대응력`을 등록하여 기존 결과 항목 ID에 연결한다. 오타도 관리자가 별칭으로 등록하면 재사용할 수 있다.

| 기준 종류 | 연결 대상 | 사용 위치 |
|---|---|---|
| 폴더 역할 | 프로젝트·의뢰·하중 경우·입력·결과 역할 | 폴더의 역할 선택 |
| 프로젝트 | 기존 프로젝트 ID | 임의 이름 폴더의 업무 대상 선택 |
| 의뢰 | 기존 의뢰 ID와 해당 프로젝트 | 폴더의 의뢰/프로젝트 선택 |
| 하중 경우 | 기존 하중 경우 ID와 해당 의뢰/프로젝트 | 결과 폴더의 업무 대상 선택 |
| 결과 항목 | 기존 결과 항목 ID | 레시피 원본 필드→기준 항목 선택 |

이는 지원된 업무 종류와 결과 항목을 기준으로 하는 사전이다. 사용자 정의 문자열만으로 새로운 실행 엔진, 값의 의미, 단위 변환이나 위젯 종류가 생기는 것은 아니다. 관계 추론 엔진과 AI 이름 추정은 이번 범위 밖이다.

## 매칭과 변경 계약

- 고정 키·표시명·별칭을 모두 정확 매칭 후보로 사용한다. Unicode NFKC, 대소문자와 연속 공백을 정규화한다. 구두점·밑줄 제거, 부분 문자열, 유사도 추정으로 서로 다른 대상을 합치지 않는다.
- 범위는 전역 또는 특정 프로젝트다. 프로젝트 문맥이 주어지면 같은 기준 종류의 프로젝트 정의를 먼저 찾고 없을 때 전역 정의를 사용한다. 문맥이 없으면 전역 정의만 검색한다. 실제 프로젝트·의뢰·하중 경우를 가리키는 정의는 해당 프로젝트 소속을 검증하며, 프로젝트 문맥이 주어진 검색에서 다른 프로젝트의 실제 대상은 전역 정의라도 반환하지 않는다.
- 같은 기준 종류·범위의 활성 정의가 같은 정규화 단어를 소유할 수 없다. 여러 종류에 같은 단어가 있으면 후보를 함께 표시한다. 첫 후보를 자동 확정하지 않는다.
- 기준 정의의 고정 키·종류·대상·범위는 생성 후 불변이다. 연결 의미를 바꾸려면 새 정의를 만들고 기존 정의를 비활성화한다. 표시명·설명·별칭·활성 여부는 revision 충돌 검사 후 수정한다.
- 비활성 정의는 매칭에서 제외한다. 프로젝트 정의를 비활성화하여 지역 후보가 없어지면 전역 후보가 다시 나올 수 있다. 별칭 수정/비활성화는 이미 저장한 레시피·폴더 연결·과거 실행을 변경하지 않는다. 기존 읽기 버전과 결과 스냅샷 계약을 유지한다.
- 별칭 추천은 관리자 편집을 돕는다. 필드 원본 경로·단위·위젯 설정·폴더 바인딩을 자동 저장하지 않는다. 후보 선택 후 기존 미리보기/저장/활성화 절차를 거친다.
- 같은 단어의 동시 등록과 같은 정의의 동시 수정은 서버에서 충돌 처리한다. 사전 변경과 감사 기록을 한 트랜잭션에 저장한다.
- 사전은 비활성을 포함해 최대 2,000개 정의, 정의당 별칭 64개, 용어당 정규화 후 200자까지 지원한다. 설명은 4,000자다. 삭제된 실제 대상을 가리키는 정의는 목록에서 표시하며 추천에서 제외한다. 해당 정의를 비활성화할 수 있다.

## 관리자 흐름

1. 의미 매핑 화면의 기준 정의·별칭 탭에서 기준 종류와 실제 대상을 선택한다.
2. 고정 키·표시명·설명·전역/프로젝트 범위를 정하고 별칭을 줄별로 등록한다.
3. 저장 후 검색과 편집으로 정의를 관리한다. 삭제 대신 비활성화하여 매칭에서 제외한다.
4. 읽기 레시피의 원본 필드에 대해 별칭 찾기를 실행한다. 후보의 정의·실제 결과 항목을 확인한 뒤 적용하고 기존 통합 미리보기로 검증한다.
5. 폴더에서 별칭 찾기를 실행하면 폴더 이름에 대응하는 역할/업무 대상 후보가 나온다. 후보를 적용한 뒤 기존 폴더 연결 저장을 수행한다.

사전은 DB에 보존되어 앱 재시작이나 다음 파일 등록에도 사용할 수 있다. 기존 레시피 정의 반입/내보내기 패키지는 사전과 프로젝트 대상 ID를 포함하지 않는다. 사전 전체 복원은 기존 DB 백업/복원을 사용한다.

## 모듈·검증·배포

백엔드 사전 모듈과 전용 API `/api/semantic-vocabulary`, 프런트 사전 편집기/추천 UI를 기존 파싱 엔진과 분리한다. 기존 인증·관리 권한·generated API·DB 연결을 재사용한다. 새 런타임 의존성이나 외부 서비스는 없다.

새 additive migration은 0024 다음 단일 head로 연결한다. PostgreSQL 스키마 변경은 기존 배포 단계에서 수행하고 앱 역할에는 CRUD만 부여한다. DuckDB는 개발용 bootstrap을 유지한다. 설치기·소스 배포 진입점·영구 경로를 바꾸지 않는다. 실제 사용자 DB·설정·서비스를 테스트에 사용하지 않는다.

수락 검사는 정의/별칭 저장·재조회·개정·비활성, Unicode/공백/대소문자 매칭, 범위 우선순위, 종류 간 모호성, 잘못된 소속, 동시성, 권한 차단, 필드/폴더 후보의 명시적 적용, 기존 레시피/실행 불변, 신규·기존 DB migration과 백업/복원을 포함한다.

## 검증 기록

- 기능·기존 매핑 회귀 63개 통과 후 PostgreSQL NUL/제어문자 입력 차단 테스트 1개를 추가해 통과했다. 기존 레시피·위젯·활성화·경로 소유권·OpenAPI 계약·중복 방지 검사를 포함한다.
- 배포 회귀 206개 통과/5개 건너뜀. 업데이트 실패 처리, 오프라인 설치기 계약, manifest 변조/누락/중복/경로 이탈, 서비스 소유권 PowerShell 자체 검사를 통과했다.
- 독립 임시 PostgreSQL에서 신규 설치와 실제 0024→0025 업데이트의 제약/컬럼 일치, 기존 업무 데이터·결과 항목 보존, 반복 migration, 기본/사용자 지정 앱 역할 CRUD와 DDL 차단, 실제 API 함수의 동시 용어 충돌·revision CAS·감사 rollback, 별칭·revision·검색 용어의 dump/restore를 확인했다.
- 실제 비밀번호 로그인과 API를 사용한 신규 Playwright 5개 통과: 별칭 원문 입력·저장·재조회·비활성·필드 적용, 현재 폴더 경로 보존·명시적 선택, 전역 의뢰/하중 경우 선택, 교체된 필드 행에 지연 후보 응답 적용 차단, viewer 접근 차단. 기존 의미 매핑 브라우저 4개도 통과했다.
- TypeScript·프런트엔드 아키텍처·정적 빌드 통과. 실제 화면에서 사전 목록과 표 열 정렬을 확인했다. 격리 사본의 의존성 junction 때문에 Vite 검증에는 runner와 QA 전용 cache/허용 경로 설정을 사용했으며 배포 실행기에는 반영하지 않았다.
- Sol이 1차 검수하고 별도 Astra가 최종 검수했다. 신규 설치 제약 누락, 부모 폴더 오연결 가능성, 늦은 후보 적용, 의뢰 전환 시 남는 하중 경우 목록을 수정하고 재확인했다.

전체 저장소 테스트나 실제 폐쇄망 Windows Server 2022 신규 설치·업데이트·재부팅 검증을 완료한 것으로 표현하지 않는다. 실제 사용자 DB/서비스에는 적용하지 않았다. 새 소스는 기존 배포 절차에서 백업 후 migration하여 적용하고, 오프라인 서버에는 새 릴리스 패키지가 필요하다.
