# Windows 소스 배포·폐쇄망 설치 시나리오

- 기준일: 2026-09-14
- 요청: 소스 배포는 PostgreSQL과 VS Code만 있는 PC에서 시작하며, 폐쇄망 설치 대상은 Windows Server 2022 x64만 설치되어 있다고 가정한다.
- 구현·검증 상태와 명령은 [소스 설치 안내](windows-one-click-deployment.md), [폐쇄망 서버 설치 안내](windows-server-offline-installation.md)를 따른다.

## 사용자 진입점

| 환경 | 최초 설치 | 버전 업데이트 | 필요한 입력 |
|---|---|---|---|
| 인터넷/허용된 사내 프록시에 연결되는 소스 PC | 전체 소스 압축 해제 후 `deploy.bat` | `update.bat` | 최초 PostgreSQL 연결과 관리자 계정 |
| 폐쇄망 Windows Server 2022 | 외부 빌드 PC에서 만든 설치 패키지를 반입해 설치 실행 | 새 설치 패키지를 기존 설치 경로에 실행 | 최초 설치 경로·DB 방식·관리자 계정 |

원클릭은 하나의 진입점이 런타임 준비부터 서비스 실행까지 안내한다는 의미다. 최초 DB 자격 증명과 웹 관리자 계정 입력, Windows 서비스 설치를 위한 UAC 승격은 필요하다. VS Code는 소스 확인용이며 서버 실행에 필요하지 않다.

## DB 판정과 처리

| 대상 상태 | 처리 | 보존·중단 기준 |
|---|---|---|
| PostgreSQL 서버가 있고 앱 DB가 없음 | 앱 전용 DB·owner/app 역할 준비 후 스키마·첫 관리자 생성 | 서버의 다른 DB는 건드리지 않음 |
| 전용 앱 DB가 실제로 비어 있음 | 권한 검증 후 최초 스키마 적용 | 연결 실패를 빈 DB로 판정하지 않음 |
| 앱 DB와 계정·업무 데이터가 있음 | 설정·DB·관리형 첨부파일 백업 검증 → 대기 중인 스키마 변경 → 계정 상태 확인 | 데이터·비밀번호·인증 키 유지; 백업 실패 시 마이그레이션 중단 |
| 데이터는 있으나 앱 스키마 이력을 식별할 수 없음 | 작업 중단 및 명시적 이관 안내 | 임의 초기화, 무조건 stamp 또는 schema drop 금지 |
| DB 설정이 없으나 기존 DuckDB가 있음 | 기존 사용/별도 PostgreSQL 이관 안내 | 새 PostgreSQL로 조용히 바꾸지 않음 |
| 접속 실패·권한 부족·복구 대기 표시 존재 | 원인 안내 후 중단 | 새 DB로 우회하거나 운영 서비스 성공으로 표시하지 않음 |

“초기화 가능”은 일반 배포에서 기존 DB를 지울 수 있다는 뜻으로 해석하지 않는다. 테이블이 있으나 행이 없는 DB도 스키마 이력이 있으면 업데이트 경로를 사용한다. DB 교체·PC 간 데이터 이관은 [이전 안내](postgresql-pc-transfer-guide.md)의 별도 작업이다.

## 소스 배포의 책임

1. 프록시·CA 정책을 적용하고 고정된 Python·Node.js·패키지 관리자를 프로젝트 폴더에 준비한다.
2. Python 의존성과 프런트엔드 빌드를 준비한다.
3. 기존 설정을 읽고, PostgreSQL 최초 준비와 기존 DB 유지 경로를 구분한다.
4. 기존 관리 대상 앱을 중지하고 백업·마이그레이션·계정 준비를 순서대로 실행한다.
5. 준비 완료 후 앱을 시작하고 상태 확인을 통과한 주소를 안내한다.

소스 업데이트의 Git 다운로드는 이 경로에만 속한다. 소스 ZIP은 폐쇄망 완결 설치 패키지가 아니다.

## 폐쇄망 패키지의 책임

외부 Windows 빌드 PC에서 프런트엔드 정적 파일, 고정 Python, 모든 Windows Python wheel, PostgreSQL 바이너리, Caddy, Windows 서비스 래퍼, 필요한 VC++ 런타임을 함께 묶는다. 대상 서버에서 Git·Node.js·VS Code·pip 온라인 저장소·인터넷 인증서 발급을 요구하지 않는다.

서버는 Caddy가 정적 웹을 제공하고 loopback의 FastAPI로 API를 전달한다. 웹/API는 Windows 서비스로 등록하며 재부팅 후 자동 시작한다. 새 로컬 PostgreSQL은 기존 설치와 구분되는 전용 서비스·데이터 경로를 사용한다. 기존 PostgreSQL을 연결하는 설치는 해당 DB 서버의 바이너리나 데이터를 교체하지 않는다.

앱 릴리스와 영구 상태를 구분한다. 설정·인증 키·DB 데이터·첨부파일·백업은 업데이트의 소스 교체 대상에서 제외한다. 설치 이력은 현재 릴리스, DB 방식과 포트, 단계별 성공·실패를 남긴다. 비밀번호는 명령행 인수·배포 manifest·로그에 기록하지 않는다.

앱 스키마 업데이트와 PostgreSQL 메이저 업그레이드는 별개다. 설치기가 운영 중인 PostgreSQL 메이저를 자동 변경해서는 안 된다. 마이그레이션을 시작한 뒤 실패하면 서비스를 중단 상태로 두고 백업 복구 절차를 안내한다. 이전 앱만 재시작하면 DB까지 복구된다고 가정하지 않는다.

## 검증 기준

| 검증 환경 | 확인할 항목 |
|---|---|
| 임시 소스 폴더·가짜 외부 명령 | 옵션 전달, DB 분기, 실패 시 후속 단계 차단, 시작 순서 |
| 임시 PostgreSQL | DB 없음/빈 DB/기존 revision/미식별 스키마, 계정·업무 데이터·첨부파일 보존 |
| 오프라인 패키지 검사 | 필수 파일, 전체 파일 해시, 경로 이탈·누락·변조 거부, 비밀·운영 데이터 제외 |
| 네트워크 차단 Server 2022 VM | 다른 도구 없이 설치, 첫 로그인, 웹/API 상태, 재부팅 후 자동 시작 |
| 동일 VM 업데이트 | 기존 데이터 생성 후 새 패키지 설치, 백업 증거, 서비스 재등록·상태 확인 |
| 실패 주입 | 백업 실패·DB 접속 실패·설치 중단·상태 확인 실패·패키지 변조 |

스크립트 검사나 모의 실행 통과를 깨끗한 Server 2022 VM의 실제 설치 통과로 표현하지 않는다. 배포 승인은 실제 대상과 같은 VM에서 신규 설치·기존 DB 업데이트·재부팅을 통과한 릴리스에 부여한다.

Windows의 기존 Master Refresh는 POSIX snapshot traversal 제약으로 제한된다. 서버 설치기가 이 애플리케이션 기능 제한을 해소하지는 않는다. 파일 수동 업로드와 지원되는 기능의 범위는 [프로젝트 README](../README.md)를 따른다.
