# 폴더 규칙·공통 조회·최종확정 구현 계획

- 기준일: 2026-10-02
- 상태: 단계별 구현·격리 검증 완료. 실제 운영 배포 검증은 별도다.
- 승인 범위: 저장 규칙 편집·삭제, 계층별 역할 재사용, 공통 Folder Schema 조회 복구, Working/Final 구분, Case 결과 최종확정 및 파일 복사.
- 기준: [공용 위치 계약](../features/folder-schema-refresh.md), [결과 등록](../features/result-registration.md), [Windows 배포 정책](../windows-deployment-policy.md).

## 사용자 계약과 예제

`E:\shared\SPDM (Admin)`은 읽기 전용 참고자료다. 실제 폴더·DB·설정·실행 서비스는 테스트 대상으로 사용하지 않는다. 합성 파일과 임시 DB로 같은 구조를 재현한다.

```text
75R9J_PV/
└─ [WR-0001]_[유통_환경]/
   ├─ Working/                                  깊이 0
   │  └─ Package_Model_SetCase1_…/               깊이 1: SIMULATION_CASE
   │     └─ Drop/                               깊이 2: LOAD_CASE
   │        └─ 85qn80h_ref_organized/            깊이 3: EXECUTION_RUN
   │           └─ INDIVIDUAL/                   깊이 4: RUN_OPTION
   │              ├─ 2_Face/                   깊이 5: SCENE
   │              └─ 3_Face/                   깊이 5: SCENE
   └─ Final/
      ├─ CAD/
      ├─ CAE/
      └─ Reports/
```

예제는 Case 2개, Case별 Scene 2개다. 각 Scene에 CSV 4개와 INC 2개가 함께 있다. RAD·보고서는 예제에 없으며 합성 검증으로 보완한다. 두 번째 의뢰 폴더는 비어 있다.

Working은 결과 등록·Case 결과·소재 물성의 작업 영역이다. Final은 사용자가 best Case를 선택해 보존하는 영역이다. 의뢰 직속 Working/Final은 같은 깊이라도 서로 다른 역할이며, Working 내부 깊이 매핑이 Final로 전파되어서는 안 된다. **Scene 안에 입력과 결과파일이 함께 존재한다. INPUT/RESULTS 하위폴더를 요구하지 않는다.**

## 단계 1: 저장 규칙과 계층 역할

- Working 기준 깊이별 역할을 이름과 무관하게 같은 깊이에 적용한다. 기존 이름 규칙은 호환한다.
- 같은 깊이에 역할 지정과 개별 예외를 구분한다. 충돌을 조용히 덮어쓰지 않는다.
- 구조 가져오기는 이름 목록 대신 깊이별 역할을 저장하며, 부모 화면 갱신이 편집 초안을 초기화하지 않는다.
- 규칙 선택·편집·복사·취소·개정 저장·현재 폴더 적용을 연결한다.
- 규칙 삭제는 참조 중 이력을 보존한다. 삭제/보관된 규칙은 신규 선택에서 제외하고 기존 schema/capture/Final·사용자 파일은 보존한다.
- 기존 수동 지정·제외와 stable ID의 보존을 검증한다.
- 완료 조건: 저장→재진입→불러오기→재적용, 여러 가지/다른 이름의 같은 깊이, 개정 충돌, 삭제 후 과거 조회, Final 경계 회귀.

## 단계 2: 공통 위치 조회 계약 복구

- 구조 목록은 확정 Folder Schema가 정본이다. 결과 등록·Case 결과·소재 물성이 같은 계층·경로·ID를 공유한다.
- 현재 Case 결과 catalog가 capture.payload.runs만으로 하위 목록을 만드는 문제를 수정한다. 수집본이 없거나 runs가 비어 있어도 확정된 구조는 표시한다.
- 값·그래프·미디어는 선택 capture에서 조회한다. 현재 구조와 과거 수집본의 차이를 표시하며 임의 병합하지 않는다.
- 확정 Scene 자체가 공통 입력/결과 위치다. 명시적 하위 INPUT/RESULTS는 기존 자료 호환 용도로 유지할 수 있다.
- 미수집·수집 실패·계층 미확정·결과 파일 없음·스키마 오류를 구분한다.
- 완료 조건: Case 2개 각각 Drop→Run→INDIVIDUAL→2_Face/3_Face 조회, 미수집 구조 표시, Scene 직속 CSV/INC 연결, 제외 경로 차단, 과거 capture 보존.

## 단계 3: Case 결과 최종확정

- 상단 Case 선택기 옆 `최종확정`과 현재 확정 Case·버전·시각을 표시한다. best 판단은 사용자에게 맡긴다.
- 선택 Case·capture·스키마와 파일 목록·개수·목적지·누락을 미리보기한 뒤 명시적으로 확정한다.
- RAD/INC는 `Final/CAE`, 결과와 보고서는 `Final/Reports`로 복사한다. Case 안 상대 계층과 include 참조를 보존한다. CAD 복사는 이번 범위에 없다.
- 기존 Final을 덮어쓰지 않도록 개정별 폴더와 기록을 보존한다. Working 원본은 변경하지 않는다.
- 원본 해시·스키마·권한을 재검증하며 과거 capture와 현재 파일을 조용히 혼합하지 않는다.
- 모든 복사가 검증된 뒤 현재 확정 상태를 전환한다. 부분 실패·응답 유실·중복 요청은 같은 확정 기록으로 복구하고 기존 최종본은 유지한다.
- 완료 조건: 선택 Case 파일만 복사, 서로 다른 Scene 동일 이름 보존, 누락 RAD/보고서 표시, source 변경 차단, 실패 재시도, 중복 확정 멱등, 권한·경로 경계 검사.

## 단계 4: 통합 검수와 기록

- 기능별 Luna 구현 후 주 Sol이 요구사항·diff·오류 처리·관련 테스트를 검수한다. Astra 설계/최종 통합 검수와 데이터 보존·경로 경계의 독립 Astra 검수를 수행한다.
- 경로 쓰기·권한 변경은 security-diff-scan으로 확정 변경분을 검수한다. 미가용·실패는 완료로 기록하지 않는다.
- 데스크톱 UI, 프런트 빌드, API 생성/계약, 관련 backend 회귀 및 배포 계약 검사를 수행한다. 신규 의존성은 기본적으로 추가하지 않는다.
- 실제 Server 2022 폐쇄망 설치·업데이트·재부팅과 사내 DB 검증은 수행하지 않은 한 완료로 기록하지 않는다.
- 단계별 실제 결과와 잔여 문제는 작업 로그에 기록하고 현재 기능 문서를 갱신한다.

## 검수 기록과 범위

### 등록 후 결과 읽기·표시 후속 보완

- 실제 실행 로그에서 `FOLDER_SCHEMA_REQUEST_BINDING_REQUIRED`를 확인했다. 저장소 전체 조사에 포함된 다른 의뢰의 PROJECT/REQUEST 역할이 현재 등록의 경로 후보에 섞이는 문제를 현재 환경·정확한 target ID 필터로 수정했다. 실제 다중 연결은 계속 차단한다.
- 수집 준비 실패를 Case별 FAILED와 코드로 남겨 같은 등록에서 재시도할 수 있게 했다. 현재 의뢰 밖의 Case는 저장 전에 차단하며, 여러 의뢰의 결과도 의뢰별로 등록한다. 기존 데이터와 이력은 삭제하지 않는다.
- 확정 역할에 남은 조사 경고를 제거하고 실제 상위 역할 오류는 새 진단으로 유지한다. 미리보기는 경로·역할·이름·상태 네 열로 줄바꿈하며 Refresh는 세 열을 유지한다. 긴 이름과 상태의 겹침을 데스크톱 화면에서 검증한다.
- 최신 합성 백엔드 10개 통과: 경고 해소, 진짜 경로 모호성 차단, 올바른 Case 소유권·실제 값, 빈 두 번째 의뢰와 Working의 두 유통환경 Case, Scene 직속 CSV와 실패 후 재시도. 독립 Astra 기능 검수와 후속 수동 보안 검수 통과. 실제 DB·서비스·공유 폴더는 테스트하지 않았다.
- TypeScript/Vite build 통과. Playwright Chromium 1440×1000·14pt의 라이트/다크에서 역할 수정→미리보기→겹침 없음, URL·제목·유효 화면·오류 overlay 없음·로그인 후 console/page 오류 없음을 확인했다. 최종 실행 1개 통과(5.8초), runner exit 0. 로그인 전 의도된 /auth/me 401을 화면 오류로 세던 테스트를 수정했다. 초기 테스트 자체 통과 뒤 Windows 정리 권한 오류는 권한 확장 실행으로 해소했으며, 실제 서비스·DB를 사용하지 않았다. Browser 플러그인이 없어 기존 Playwright 실행기를 사용했다.
- 후속 기준 스캔 `a059e8a2-b4b2-450d-b146-1519829ace04`는 `f2e7b39` 기준 고정 digest `b7938c88eafee093d137bca120027ef567f53283230b7725d57fc9f6a9de5f4d`의 6개 파일 검수 완료, 보안 발견 0건이다. 스캔 이후 추가한 Case 범위 차단·안내 문구·테스트와 문서 변경은 독립 수동 검수·회귀로 확인했으며 플러그인 재스캔으로 기록하지 않는다.
- 후속 보안 도구 연결 스레드 집계: total 4,413,016 / input 4,401,842 / cached input 4,290,304 tokens. 이번 요청의 신규 사용량을 뜻하지 않는다.

- Codex Security 기준 스캔: `a5982897-a812-455d-9bbe-2996db3a512d`, HEAD `73c35b1a4ce2884c56b366b676ec0dd0786ed53f`, working-tree digest `86c11905082a6f416b62b2d30623913ae0021b99de43f407e6545083bf96f548`. 변경 소스 28개를 검수했다.
- 기준 스캔에서 최종확정 JSON을 서명 검증 전에 크기 제한 없이 읽는 문제 1건(CWE-400, medium)을 기록했다. 합성 8 MiB 파일이 약 16 MiB를 할당하는 것을 확인했다. 후속 수정으로 metadata 4 MiB 제한, 일반 파일·재파싱 경로 검사, 안정된 파일 핸들 읽기, 깊은 JSON 오류 격리, 상태 조회 1,000개/metadata 64 MiB/출력 검증 1 GiB 한도를 적용했다. 초과 시 불완전한 최신 상태 대신 명시적 오류를 반환한다. 관리자 비문맥 Final 조사 우회는 권한 상승이 없어 보안 발견으로는 제외했으며 기능 계약으로 수정·검증했다.
- 기준 보고서는 수정 전의 고정 변경분에 대한 기록이다. 스캔 완료 뒤 보완한 Scene 목록·등록·확정 표시 및 파일 범위·JSON 읽기 제한은 후속 diff와 관련 회귀 검수로 따로 기록한다. 수정 후 코드 전체를 같은 스캔 digest로 검수했다고 표시하지 않는다.
- 후속 수정은 주 에이전트의 수동 경로·권한 검수와 위 회귀 검사로 확인했다. 최종 독립 Astra 검수는 기능 계약에 대해 통과했으며, 최신 수정의 별도 독립 보안 재검수나 플러그인 재스캔을 완료했다고 기록하지 않는다. 앞서 Windows 네이티브 junction 교체 시 외부 쓰기가 차단되는 독립 검증은 통과했다.
- 스캔 도구가 반환한 사용량: total 10,236,118 / input 10,202,877 / cached input 9,895,168 tokens (`codex_rollout`, coverage complete). 도구의 연결 스레드 집계이며 현재 요청의 신규 토큰 사용량으로 해석하지 않는다.
- `check:architecture`는 이번 변경 밖의 기존 4건으로 실패한다: App 길이 기준, 소재 API 직접 호출 2곳, 결과 페이지의 소재 모듈 import, 기존 1280px breakpoint. 해당 파일의 이번 diff가 없음을 확인했다.
- Windows 데스크톱의 합성 경로 검증을 수행했다. 실제 Server 2022 폐쇄망 설치·업데이트·재부팅, SMB 및 POSIX 동시 경로 교체는 검증하지 않았다.
