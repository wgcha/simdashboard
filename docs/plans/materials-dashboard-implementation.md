- 상태: 1~3단계 구현·격리 검증 완료, 4단계 사용자 확인 대기 · 2026-09-29
- 요구 출처: GitHub [#34](https://github.com/wgcha/simdashboard/issues/34) (사양), [#35](https://github.com/wgcha/simdashboard/issues/35) (parts 발췌), [#36](https://github.com/wgcha/simdashboard/issues/36) (eps 발췌), [#37](https://github.com/wgcha/simdashboard/issues/37) (plast 발췌), [#38](https://github.com/wgcha/simdashboard/issues/38) (축약 테스트 덱)
- 범위: 읽기 전용 Radioss Starter Deck 목록·상세 조회. Part Shape Image, 편집, 외부 카탈로그 연동, 모바일 전용 UI는 제외한다.

## 확정할 동작

1. `/PART`, `/PROP/*`, `/MAT/*`, `/FUNCT`, `/MOVE_FUNCT`, `/SUBSET`, `/PARAMETER/*`, `/FAIL/*` 카드를 파일에서 규칙대로 읽는다. 카드 개수·ID·순서·물성값을 고정하지 않는다. 지원하지 않는 카드는 경고를 남기되 가능한 목록은 표시한다.
2. 목록은 **Part 한 개당 한 행**이다. Part가 참조하는 Property와 Material을 연결하고, 같은 Material을 여러 Part가 참조하면 각각의 행을 유지한다. 미해결 참조도 누락하지 않고 상태를 표시한다.
3. 왼쪽 목록은 데이터 건수와 긴 이름에 맞춰 데스크톱 영역 안에서 스크롤·폭 조절·말줄임이 동작한다. 행을 선택하면 오른쪽에 그 Material의 물성·함수와 선택 Part의 Property·실패 모델 출처를 표시한다. 다른 행을 선택하면 상세가 즉시 바뀌고, 같은 재질을 공유하는 다른 Part를 선택해도 Part 문맥은 유지한다.
4. 원본 `RHO_I`와 환산 밀도, 원본 숫자 문자열과 단위·출처를 구분한다. 함수 역할에 따라 축 단위를 정한다. LAW70 인장 비율 함수와 실패 조건 함수에 일률적으로 응력 축을 붙이지 않는다.
5. #38은 원본 카드와 참조 해소용 STUB을 함께 담은 **축약 픽스처**다. #35~37은 별도 실제 발췌다. 각 자료의 카드 수·값을 해당 자료만의 기대 결과로 검증한다. 원본 전체 덱의 성능·인코딩·탐색 검증을 축약 자료의 통과로 대체하지 않는다.

## 사양서에서 구현 전에 바로잡을 계약

- `GET /api/dashboard/catalog`는 `simulation_cases`·`scenes` 배열을 반환하지 않는다. 새 소재 카탈로그는 기존 응답과 다른 독립 계약으로 정의하고 프런트 타입을 생성한다.
- `request_id` 권한 검사만으로 덱 위치 ID·상대 경로의 소속이 증명되지 않는다. 서버는 선택 위치의 유통 의뢰·storage root 관계와 최종 덱 경로를 검증한다.
- `REAL_EXPR` 예제에는 `2*LC_G`처럼 `&` 없는 심볼 참조도 있다. `eval()` 없이 제한된 식 문법으로 처리한다.
- `/FAIL`의 ID는 재질 식별자다. 일치하는 Material이 없으면 직전 Material에 추정 연결하지 않고 미연결로 남긴다.
- `refresh=true`에 같은 fingerprint의 캐시 행을 무조건 새로 만든다는 설명은 제안된 UNIQUE 제약과 맞지 않는다. 캐시가 필요해질 때 재파싱·동일 내용 재사용·이력 정책을 먼저 정한다.
- #38 본문의 원본 `/FUNCT` 개수는 3개/4개로 서로 다르게 적혀 있다. 원본 값 단정은 일치가 확인된 61053·1014·1015에 한정한다.

## 보존·검증 조건

- 기존 미커밋 변경, 결과 등록 동작, 사용자 DB·설정·첨부파일을 건드리지 않는다. 모든 파일·DB 검증은 합성 자료와 격리 환경에서 수행한다.
- 새 런타임 의존성 없이 기존 Python·React·recharts·CSS 토큰을 우선 사용한다.
- migration은 PostgreSQL 기준 한 줄기 revision으로 유지하고 DuckDB 미러·빈 설치·기존 데이터 업데이트를 함께 확인한다. 배포는 `docs/windows-deployment-policy.md`의 Windows/폐쇄망 계약을 따른다.
- 단계마다 변경 파일, 검증 결과, 남은 위험을 제시하고 사용자 확인을 받은 뒤 다음 단계로 진행한다.

## 1단계 확인 결과 (2026-09-29)

- `backend/app/parsers/radioss_deck_parser.py`에 입력 라인 스트림 기반 파서와 카드·참조 정규화를 작성했다. 파일 경로를 직접 여는 진입점은 두지 않았고, 대량의 메시·미등록 카드 본문은 보관하지 않는다.
- #38 댓글의 축약 덱 2개와 #35~37 발췌를 별도 테스트 자료로 보존했다. `backend/tests/test_radioss_deck_parser.py`의 관련 테스트 **10개 통과**: 고정폭·빈 행·가변 카드 수·파라미터·Part 연결·함수 역할·Property 빈 슬롯·서로 다른 두께·대량 스킵 행.
- 아직 실제 원본 덱 전체, cp949 파일, 파일 크기·시간 상한, 씬 소속·권한, API·화면은 검증하지 않았다. 이 항목은 다음 단계의 완료 조건이다.

## 2단계 확인 결과 (2026-09-29)

- 읽기 전용 `GET /api/materials/catalog`, `GET /api/materials/deck`를 추가했다. 의뢰별 조회 권한과 씬 소속·환경을 확인하고, 씬 → 씬/INPUT → Run Option → Execution Run → Execution Run의 INPUT/deck/solver 순서로 Parts·Materials 역할이 모두 있는 첫 폴더를 선택한다. 목록의 `has_deck`와 상세 조회가 같은 탐색 규칙을 사용한다.
- `/INCLUDE` 참조 파일을 의뢰 경계 안에서 재귀 탐색한다. 누락·경로 이탈·reparse·순환 참조를 거부하며, 중복 파일은 한 번만 파싱한다. 파일당 64 MiB, 고유 파일 합계 256 MiB, 깊이 5, 파일 5,000개, 함수 점 500,000개, 파싱 20초 제한을 적용한다. 함수 점·시간 제한은 파싱 중에 검사한다. 응답에는 정규화된 곡선 좌표와 파일 출처를 포함하고 캐시는 두지 않았다.
- 합성 의뢰·임시 SPDM을 사용한 API·파서 테스트 28개가 통과했다. 최종 조정에 해당하는 포함 파일 종료·함수 점 조기 중단·시간 제한 테스트 3개도 통과했다. OpenAPI와 프런트 타입을 생성하고 TypeScript 검사를 통과했다.
- 변경분 보안 검사(스냅샷 ID `93a3faa3-d17e-4478-8485-d5aabf20c2d5`)는 함수 점·시간 제한의 사후 검사로 인한 자원 고갈 위험 1건을 발견했다. 검사 후 파싱 중 조기 중단으로 수정하고 관련 테스트를 통과했다. 보안 검사 스냅샷 자체는 수정 전 코드이며, 수정 후 새 플러그인 검사는 수행하지 않았다.
- `/INCLUDE`는 파일별 깊이 우선 순서로 파싱하며 원본 파일 내 삽입 위치의 카드 순서를 재현하지 않는다. 별도 곡선 endpoint는 없고 `/deck`에서 좌표를 반환한다. 실제 원본 전체 덱·Windows Server 2022·운영 데이터 검증과 화면·메뉴는 아직 수행하지 않았다. 사용자 확인 후 3단계로 진행한다.

## 3단계 확인 결과 (2026-09-29)

- 의뢰·환경·씬 선택기를 갖춘 `/workspace/materials` 화면과 메뉴를 추가했다. Part별 가변 목록은 검색·정렬·50행 페이지·CSV 내보내기를 지원하고, 선택한 Part의 Material·Property·실패 모델·곡선·누락 참조를 우측 스크롤 창에 표시한다. 선택과 필터는 URL/뒤로 가기에 반영한다. 같은 Material을 공유해도 Part별 문맥을 유지한다.
- 메뉴 권한은 `project.data.view`에 연결했다. PostgreSQL `0032_materials_dashboard_menu`은 기존 메뉴/역할 정책을 덮어쓰지 않고 신규 행만 추가하며, DuckDB 기본 정책도 맞췄다. downgrade는 사용자 설정 삭제를 막기 위해 중단한다. 별도 고위험 독립 검수에서 차단할 문제는 없었고, 메뉴·API 경계의 수동 보안 검수에서도 조치할 문제를 찾지 못했다.
- 합성 데이터로 4 Part(긴 이름·공유 소재·누락 참조·실패/곡선·필터)와 128 Part(딥링크 페이지·선택·뒤로 가기) 데스크톱 Playwright 시나리오 2개가 통과했다. TypeScript·Vite 빌드와 관련 마이그레이션/정책 테스트 6개도 통과했다. Windows 테스트 실행기의 자식 프로세스 종료 권한 오류로 전체 명령 종료 코드는 1이었지만, 두 테스트의 assertion은 통과했고 테스트 포트의 잔류 리스너는 없었다.
- 실제 PostgreSQL 빈 설치/기존 DB migration, 실제 전체 원본 덱과 cp949, Windows Server 2022 폐쇄망 배포는 미검증이다. Codex Security 플러그인 변경분 검사는 이번 단계에서 실행하지 않았으며 4단계 통합 검증에 남긴다. 실제 사용자 DB·설정·서비스는 사용하지 않았다. 사용자 확인 후 4단계로 진행한다.

## 사용자 확인 반영: 유통환경 결과 폴더 덱 탐색 (2026-09-29)

- 소재·물성 화면은 유통환경 전용으로 고정하고 환경 선택기를 제거한다. 기존 Scene 선택과 조회 권한은 유지하며, Scene 역할 폴더가 없는 실행도 결과 폴더가 확인되면 덱 위치로 표시한다. SPDM 폴더 스키마·DB·사용자 데이터는 변경하지 않는다.
- Scene 안의 `results`와 요청 소유의 등록 RESULTS 폴더를 확인하고, Scene 역할이 없는 경우에는 의뢰 아래 유통 실행 계층으로 추적되는 정규 `results` 폴더를 찾는다. 덱 후보 내용 sniff 전에 경로 전체와 소유권을 검사하고, 후보 폴더·파일 sniff 한도로 무관한 폴더의 덱 오탐을 줄인다.
- 합성 API 픽스처에서 Scene 역할이 없는 `INDIVIDUAL/DAMP-2_Face/results` 경로를 파싱하고, 무관한 폴더·다른 환경에 등록된 결과 경로를 제외한다. 실행 계층과 다른 결과 위치를 중복 없이 표시하고 기존 Scene/results 경로도 계속 지원한다.
- 실제 사내 결과 폴더의 정확한 상대 경로는 아직 확인하지 않았다. 운영 SPDM·사용자 DB·실행 서비스 검증으로 간주하지 않는다.

## 현장 피드백 반영: 적용된 유통 스키마·101/103 덱·내 작업 탭 (2026-09-29)

- GitHub [#40](https://github.com/wgcha/simdashboard/issues/40)의 `WR/Working/Package.../Drop/Run/INDIVIDUAL/Scene...` 계층을 기준으로, 적용된 유통 폴더 등록의 미리보기 역할 스냅샷에서 Scene 경로를 읽는다. 적용된 Scene이 있으면 이름만 Scene처럼 보이는 미등록 폴더는 소재 위치 후보에서 제외한다. Scene 바로 아래 `results`는 같은 위치로 중복 표시하지 않는다. 적용 등록이 없는 기존 의뢰의 이름 기반 탐색은 호환을 위해 유지한다.
- 덱 후보 판별에서 101 Parts 파일의 `/BEGIN`, `/PARAMETER`, `/SUBSET`을 소재 카드의 증거로 사용하지 않는다. `101_parts.inc`와 `103_material_propertdb.inc`를 각각 읽어 Part의 `mat_ID`를 `/MAT` 카드에 연결한다. 101만 있는 폴더는 완성된 덱으로 표시하지 않는다.
- 소재 화면은 별도 메뉴 대신 내 작업의 `Case 결과` 오른쪽 탭에서 연다. 내 작업의 프로젝트·의뢰 선택을 공유하며, 기존 `/workspace/materials` 주소는 이 탭으로 연결한다.
- 적용된 등록의 역할 스냅샷은 등록 이후 프로필 수정과 무관하게 유지한다. 미적용 규칙 프로필만 저장된 경우에는 요청별 활성 프로필 연결이 없어 확정 Scene으로 간주하지 않는다. 실제 사내 파일·DB 검증은 남아 있다.

### 현재 차이

### 화면 구성

페이지 상단에는 제목과 계층 선택 영역을 배치한다. 폴더 구조 갱신은 최상단 공용 도구 모음의 **저장 폴더 새로고침**으로 통일하고, Case 결과·모델 소재물성 페이지 안의 중복 Refresh 버튼은 제거한다. 선택 순서는 두 화면에 같은 용어를 사용한다.

해석 Case → 하중경우 → Run Case → Run Option → Scene

- 기존 덱 위치 선택기를 선택한 Option 아래 Scene 선택기로 바꾼다. Scene 아래에는 확정된 상대 경로와 입력 덱 유무를 표시한다.
- 부모 아래 후보가 하나면 자동 선택하고 Case 결과처럼 고정값으로 표시한다. 여러 후보는 선택기로 표시한다. 상위 선택이 없거나 후보가 없으면 비활성 상태와 이유를 보여준다.
- Run Option이 생략된 계층은 옵션 없음으로 표시하고 해당 Run의 직속 Scene만 조회한다. 다른 Option의 Scene과 합치거나 새 폴더·영구 ID를 만들지 않는다.

- 승인·등록이 완료되면 DB의 Case/capture/asset 저장과 선택 Scene 자체로의 승인 파일 복사를 확인한다. 입력·결과파일을 별도 results 폴더에 잘못 저장하지 않고, 원본 이름·크기·해시 및 저장된 파일 수를 확인한다. DB 등록과 파일 복사는 각각 상태를 반환하며 둘 중 하나가 실패한 경우 전체 완료로 표시하지 않는다.
- 성공한 생성·게시·파일 복사 후 공용 갱신 처리로 의뢰·환경·Case 범위의 구조 목록과 capture 조회를 갱신한다. Case 결과로 이동하면 새 Scene과 등록 결과가 추가 Refresh나 재로그인 없이 보이게 한다. 진행 중 다른 의뢰나 Case로 이동한 경우 이전 응답을 현재 선택에 적용하지 않는다. 폴더 생성만 성공한 경우와 결과 등록까지 성공한 경우를 구분한다.
- 등록 화면에 초안 업로드 완료, 검수·등록 대기, DB 등록 완료, 파일 복사 실패, 구조 갱신 실패 상태와 다음 조치를 표시한다. DB 게시 성공 후 복사·갱신만 실패하면 기존 capture와 파일을 보존하며 해당 실패 단계만 재시도한다. 중복 클릭·응답 유실 후 재시도로 capture·파일을 중복 생성하거나 기존 파일을 덮어쓰지 않는다.

완료 조건은 확정 규칙의 Scene 깊이에 생성한 임의 이름의 해석 Scene 폴더가 해당 가지의 목록에 즉시 반영되는 것, 초안 업로드 후 검수 대기 표시, 승인·등록 후 파일 존재와 DB 결과 조회 일치, Case 결과 이동 즉시 신규 Scene/결과 표시다. 합성 4_Edge를 포함한 여러 이름·여러 Case/Run/Option 가지의 동일 깊이 신규 폴더, 다른 깊이·제외 영역, 업로드·게시·복사·Refresh 각각의 실패, 빈 Scene, 같은 이름의 타 의뢰 Scene, 연속 클릭·재시도·이동 중 응답을 검증한다. 실제 사용자 DB·설정·실행 서비스를 테스트 대상으로 사용하지 않는다. 구현 대상은 결과 등록의 생성·업로드·게시·복구 처리와 공용 Refresh/조회 상태 전달이며, 저장·권한·경로 경계 변경은 프로젝트 지침에 따른 독립 검수와 변경분 보안 검수를 수행한다.

### Case 결과 보고서 내보내기 호환

2026-10-02 추가 요청: 보고서 내보내기는 기존 Run 대시보드와 Case 결과 양쪽에서 지원한다. 공통 보고서 창·템플릿·생성 기능을 유지하고 진입 화면의 선택 문맥에 맞는 원본을 연결한다. 현재 ReportExportDialog와 useReportExportController는 기존 분석 페이지의 Overview, dashboard, analysis run 및 비교 보고서 문맥을 받는다. SimulationDashboard에는 이 연결이 없으므로 버튼 표시와 함께 데이터 원본 연결이 필요하다.

- Case 결과 상단의 계층 선택 영역 옆에 보고서 내보내기 버튼을 배치한다. 유효한 저장 capture가 선택되면 활성화하고, Folder Schema 구조만 보거나 결과가 없으면 비활성 이유를 표시한다. 최종확정 버튼과 보고서 내보내기는 각 목적이 드러나도록 구분한다.
- 창을 열 때 프로젝트·의뢰·환경·Case·capture·하중경우·Run·Run Option 및 적용 중인 Scene 필터를 요약한다. 기본 범위는 현재 선택한 결과이며, 다른 Case나 다른 capture의 자료가 섞이지 않게 한다. 내보낼 범위를 확장하는 경우 창에서 사용자가 명시적으로 선택하고 범위를 다시 표시한다.
- 기존 보고서 창의 레이아웃·개정 선택, 문구 편집, 포함 콘텐츠 설정, 회사 PPTX 템플릿과 변수 연결, 편집 가능한 PPTX 다운로드를 재사용한다. 사용환경과 유통환경의 결과값·그래프·이미지·표를 기존 보고서 콘텐츠 형식에 대응시키고, 지원하지 않는 항목과 누락된 템플릿 변수는 안내한다.
- ReportSource에 Case capture 문맥을 명시하는 원본 분기와 어댑터를 설계한다. 실제 선택된 stable ID 및 immutable capture의 값·미디어를 사용하며, 공용 Folder Schema는 위치와 계층 확인에 사용한다. 현재 파일에서 다시 읽은 값으로 과거 capture 보고서의 결과를 바꾸지 않는다.
- 보고서 창을 연 뒤 Case·Run Option·capture 등 범위가 바뀌면 이전 초안을 무효화하고 다시 열도록 안내한다. 생성 중에는 시작 시점의 범위를 고정하고, 늦게 도착한 이전 요청이 다른 선택의 파일로 다운로드되지 않도록 기존 generation guard를 확장한다.
- 생성 파일은 기존 다운로드 흐름을 유지한다. 최종확정과 Final/Reports 파일 보존은 [최종확정 계약](../features/case-finalization.md)에 따라 별도 동작으로 연결한다.

추가 대상은 frontend/src/features/reports/ReportExportDialog.tsx, useReportExportController.ts, 보고서 원본·콘텐츠 타입과 frontend/src/reportExport.ts다. 기존 분석 페이지 및 비교 보고서의 내보내기를 함께 회귀 검증한다. 원본 문맥, 템플릿·미디어 접근 권한 또는 경로 경계가 바뀌면 변경분 보안 검수를 수행한다.

### 구현 순서와 완료 조건

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 0 | 공용 Refresh 통합·목록·현재 이름·직접 이동 복구 | 최상단 버튼 한 번으로 의뢰 목록과 두 탭의 계층·현재 이름이 갱신되고 페이지 내부 중복 Refresh가 없으며 폴더 연결 버튼이 올바른 화면으로 이동한다. |

검증은 두 프로젝트·여러 의뢰, 같은 이름의 Case/Scene, 복수 Run/Option, Option 생략, 단일 후보, 덱 없음, Scene 없음, INC 전용 덱, Part ID가 같은 서로 다른 덱을 포함한다. 상위 선택 변경·빠른 연속 선택·Refresh로 선택 폴더가 사라진 경우에는 이전 덱을 남기거나 다른 가지로 자동 이동하지 않는지 확인한다. Case 결과의 기존 수집 이력·최종확정 동작을 회귀 확인한다. 실제 사용자 DB·실행 서비스는 테스트 대상으로 사용하지 않는다. 권한·경로 접근 경계가 바뀌면 프로젝트 지침에 따라 변경분 보안 검수를 수행한다.

보고서는 사용/유통환경, 기본 레이아웃·저장 개정·회사 템플릿, 결과 없음·부분 자료·누락 변수, 창을 연 뒤 선택 변경, 생성 중 선택 변경을 검증한다. 생성된 PPTX의 제목·원본 식별 정보·표·그래프·이미지가 선택 범위와 일치하고 다른 Case/Option/capture의 값이 포함되지 않는지 확인한다. 기존 분석 상세·비교 보고서 내보내기도 유지되는지 확인한다. 구현 전 계획 단계이며 실제 PPTX 생성 검증은 아직 수행하지 않았다.
