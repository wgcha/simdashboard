# 사용자 정의 상세분석 페이지 및 페이지별 보고서 구현 계획

## 1. 목적과 원칙

상세분석 화면에 관리자가 원하는 분석 페이지를 만들고, 현재 제공되는 위젯과 일부 확장 위젯을 자유롭게 배치할 수 있는 기능을 추가한다. 참고 레이아웃은 외형을 그대로 복제하지 않고 `조건 선택 + 평가 결과 + 차트/표 + 참고 미디어`라는 기능 구성과 배치 방식만 반영한다.

기존 프로그램의 상단 컨텍스트 선택기, 상세분석 진입 구조, 12열 위젯 캔버스, 대시보드 정의/버전 저장, Workflow, Run 비교, 운영 대시보드는 유지한다. 새 기능은 기존 `DashboardDefinition`과 위젯 렌더링 구조 위에 분석 페이지 메타데이터와 관리 흐름을 추가하는 방식으로 구현한다.

## 2. 확정 의사결정

### 2.1 페이지와 위젯 개수

- 사용자 정의 분석 페이지 개수에는 제품 차원의 상한을 두지 않는다.
- 한 페이지에 추가할 수 있는 위젯 개수에도 제품 차원의 상한을 두지 않는다.
- 탭이 화면 너비를 넘으면 가로 스크롤과 검색 가능한 전체 페이지 목록을 제공한다.
- 위젯이 많아지면 기존 12열 캔버스가 세로로 계속 확장된다.
- 저장 시에는 개수를 제한하지 않고, 위젯 ID 중복, 지원하지 않는 타입, 잘못된 좌표/크기, `x + w > 12` 같은 정의 무결성만 검증한다.

### 2.2 페이지 소유 범위와 데이터 연결

- 사용자 정의 분석 페이지는 `프로젝트 > 의뢰 > 하중 경우(신뢰성)` 중 **하중 경우**에 귀속한다.
- 페이지 생성 API는 `load_case_id`를 받고 서버에서 연결된 의뢰와 프로젝트를 역검증한다.
- 프로젝트, 의뢰 또는 하중 경우가 변경되면 분석 페이지 목록, 변수 카탈로그, 최신 실행 결과를 새 컨텍스트 기준으로 다시 조회한다.
- 위젯은 기존과 동일하게 현재 하중 경우의 최신 실행과 결과 데이터에 동적으로 연결한다.
- 숫자 결과 위젯은 `settings.variableId` 또는 기존 변수 키를 통해 `scalar_results`와 판정 정보를 조회한다.
- 이미지/영상/컨투어 계열 위젯은 동일 실행의 미디어 메타데이터를 사용한다.
- 다른 하중 경우의 초안이나 게시 페이지가 섞여 보이지 않도록 모든 목록/상세/저장 요청에서 귀속 관계를 검증한다.

### 2.3 권한과 페이지 생명주기

- 페이지 상태는 `draft`, `published`, `archived` 세 단계로 관리한다.
- `admin`은 빈 페이지 생성, 이름/설명 변경, 게시, 게시 해제, 순서 변경, 보관, 보관 복원, 사용자 페이지 영구 삭제를 수행한다.
- `admin`은 초안·게시·보관 페이지 모두 조회하고 위젯을 편집할 수 있다.
- `editor`는 게시된 페이지의 위젯 추가·삭제·이동·크기 변경·속성 편집만 수행할 수 있다. 페이지 이름, 설명, 상태, 순서는 바꿀 수 없다.
- `viewer`는 게시된 페이지만 읽을 수 있다.
- 새 페이지는 빈 `draft`로 생성하고 위젯이 하나 이상 저장된 뒤에만 게시할 수 있다.
- 시스템 페이지인 Open Cell, Chassis rear, Run 비교·검토는 보관하거나 삭제할 수 없다.
- 보관은 복원 가능한 생명주기 상태이고, 삭제는 보관과 구분되는 **영구 삭제(hard delete)** 다. 삭제 시 해당 사용자 페이지의 `dashboard_versions`를 먼저 삭제한 뒤 `dashboards` 행을 같은 트랜잭션에서 삭제한다. 별도 DB 테이블이나 `deleted_at`은 추가하지 않는다.
- 삭제는 `admin`에게만 허용하며 `SYSTEM_ANALYSIS_PAGE_IDS` 또는 `page.is_system=true`인 페이지, `analysis_key`가 `custom`이 아닌 페이지는 서버가 `409`로 거부한다. 프런트 표시 여부만으로 시스템 페이지를 보호하지 않는다.
- 관리 화면의 삭제 확인 대화상자는 페이지 이름, 영구 삭제 안내, 복구 불가 안내를 표시하고 사용자가 정확한 페이지 이름을 입력해야 삭제 버튼을 활성화한다. 진행 중에는 중복 요청을 막는다.
- 현재 활성 페이지를 삭제했다면 삭제 전 목록에서 바로 다음 사용자 페이지, 바로 이전 사용자 페이지, Open Cell, Chassis rear 순으로 살아 있는 페이지를 선택한다. 삭제 후 서버 목록을 다시 읽고 대상 대시보드를 불러오며, 보고서 대화상자가 삭제 페이지를 가리키면 닫고 초안 상태를 폐기한다.
- 같은 하중 경우의 활성 페이지(`draft`/`published`) 사이에서는 이름 중복을 허용하지 않는다.

### 2.4 위젯 편집

- 현재 편집 경험을 유지하여 위젯 추가, 삭제, 드래그 이동, 리사이즈, 속성 편집을 모두 지원한다.
- 편집 가능한 공통 속성은 제목, 위젯 종류, 연결 변수, 집계 방식, 색상, 글자 크기, 기준선 표시, `보고서 포함` 여부다.
- 재사용 가능한 위젯은 KPI, 판정, 게이지, 막대, 시계열, 산점도, 결과표, 컨투어, 영상, 영상 그리드, 의견, 조건 요약이다.
- 기존 특화 위젯인 Open Cell 맵과 Chassis 요약·위치도·막대·상세표도 카탈로그에서 사용할 수 있게 한다.
- `run_comparison`은 Run 비교·신뢰도·검토 묶음을 렌더링하는 시스템 특화 위젯으로 추가한다. 기본 Run 비교 시스템 페이지에 포함하되 일반 사용자 페이지의 추가 카탈로그 노출 여부는 기존 데이터 문맥 지원 범위에 맞춘다.
- 실제 렌더러가 없는 `model3d`와 분석 페이지 용도가 아닌 `workflow`는 사용자 페이지의 추가 목록에서 제외한다.
- 저장할 때 기존 대시보드 버전 생성 방식을 그대로 사용하고, 저장 취소와 이전 버전 복구를 지원한다.
- 이전 버전을 복구할 때는 위젯 구성만 복구하고 현재 페이지의 이름, 상태, 표시 순서는 유지한다.
- 기존 복제 API는 유지하되 복제본에서 분석 페이지 메타데이터를 제거하여 복제만으로 새 분석 탭이 생기지 않게 한다.

### 2.5 보고서 내보내기

- 상세분석 상단의 보고서 버튼은 하나를 유지하되 Open Cell, Chassis rear, Run 비교·검토, 모든 게시 사용자 페이지에서 항상 노출한다. Workflow에서는 노출하지 않는다.
- 버튼을 누르면 현재 화면을 보고서 대상으로 기본 선택한다. 분석 페이지에서는 접근 가능한 시스템/게시 페이지 중 하나를 선택할 수 있고, admin이 현재 편집 중인 초안 페이지는 그 초안만 내보낼 수 있다. 보관 페이지는 내보내지 않는다.
- 한 번의 내보내기에서는 분석 페이지 하나 또는 현재 Run 비교·검토 문맥 하나만 선택한다. 여러 분석 페이지를 한 PPTX에 합치는 기능은 이번 범위에서 제외한다.
- Run 비교·검토 보고서는 사용자가 화면에서 선택한 `load_case_id`, `baseline_run_id`, `target_run_id`를 내보내기 대화상자를 여는 시점에 고정한다. 비교 API 결과, 대상 Run의 trust 결과, 대상 Run의 review-items 결과를 같은 식별자로 다시 조회하여 화면과 보고서가 다른 Run을 섞지 않게 한다.
- Run 비교·검토의 보고서 콘텐츠는 비교 요약, 변수별 수치 비교, 선택 가능한 공통 시계열, 신뢰도 요약, 검토 의견 각각을 가상 위젯 결과로 정규화한다. 각 항목에는 안정적인 `contentId`, 제목, 종류, 원천 키/Run ID와 렌더링 데이터를 둔다.
- 분석 페이지는 `보고서 포함=false`가 아닌 위젯을 캔버스의 `y`, `x`, 위젯 ID 순으로 읽어 보고서 콘텐츠 항목으로 만든다. 같은 변수에 연결되어도 서로 다른 위젯이면 별개 결과로 유지하며 변수 ID 기준으로 중복 제거하지 않는다.
- **기본 본문 구성은 보고서 1슬라이드당 대시보드 위젯 결과 1개**다. 표지/요약 슬라이드는 이 규칙과 별도이며, Run 비교·검토의 가상 위젯 결과에도 같은 기본 규칙을 적용한다.
- 사용자는 내보내기 전에 콘텐츠 포함/제외, 슬라이드 순서, 슬라이드 추가·복제·삭제, 콘텐츠의 다른 슬라이드 이동, 한 슬라이드에 여러 콘텐츠 배치, 위치·크기·표현 형식을 편집할 수 있다.
- 기존 32×18 `ReportLayoutEditor`, `ReportSlideDefinition`, 드래그/리사이즈, 마스터/색상/템플릿, 저장·버전 API를 재사용한다. 새 편집기를 병렬로 만들지 않고, 선택한 보고서 원천을 `ReportContentItem[]`으로 정규화한 뒤 기존 슬라이드/요소 바인딩으로 변환한다.
- 기존 보고서 레이아웃 정의에는 `content` 바인딩과 원천 범위를 선택형 필드로 추가한다. 새 필드가 없는 기존 저장 레이아웃은 현재 series/scalar/media 방식으로 그대로 렌더링한다. 새 기본 구성을 선택하거나 새로 만들 때만 1슬라이드 1콘텐츠 구성을 생성한다.
- 페이지 화면을 픽셀 이미지로 캡처하지 않고 위젯의 연결 결과를 기존 PPTX 생성기에 전달한다. 영상 재생과 상호작용 전용 결과는 정적 대표 프레임/메타데이터로 변환하며 변환할 자료가 없으면 제외 사유를 내보내기 전에 표시한다.

### 2.6 운영 대시보드와 결과 공유

- 운영 대시보드의 기존 화면, KPI, 추이, 상태 분포, 품질/유형 차트, CSV 동작은 변경하지 않는다.
- 운영 대시보드와 상세분석 페이지는 `프로젝트/의뢰/하중 경우/최신 실행/scalar_results`라는 동일한 원천 결과와 변수 키를 계속 공유한다.
- 사용자 정의 페이지를 위해 결과 데이터를 복제하거나 별도 집계 테이블을 만들지 않는다.
- 사용자 페이지에서 사용하는 새 숫자 변수가 실제 실행 결과와 판정에 저장되면 기존 운영 PASS/FAIL 및 요약 집계에서도 같은 원천 결과를 통해 반영될 수 있어야 한다.
- 상세분석 페이지의 임의 레이아웃을 운영 대시보드에 그대로 복제하거나, 임의 변수를 운영 KPI 위젯으로 승격하는 기능은 이번 범위에서 제외한다.

## 3. 저장 모델

새 DB 테이블을 추가하지 않고 기존 `dashboards.definition_json`과 `dashboard_versions`를 재사용한다. `DashboardDefinition`에 선택형 페이지 메타데이터를 추가한다.

```ts
type AnalysisPageMeta = {
  kind: 'analysis_page'
  analysis_key: 'open_cell' | 'chassis_rear' | 'run_comparison' | 'custom'
  status: 'draft' | 'published' | 'archived'
  display_order: number
  is_system: boolean
}

type DashboardDefinition = {
  id: string
  name: string
  description: string
  widgets: DashboardWidget[]
  page?: AnalysisPageMeta
}

type ReportSource = {
  kind: 'analysis_page'
  dashboardId: string
  loadCaseId: string
  runContext?: { baselineRunId: string; targetRunId: string }
}

type ReportContentItem = {
  contentId: string
  kind: 'dashboard_widget' | 'comparison_summary' | 'comparison_variable' | 'comparison_series' | 'trust_summary' | 'review_item'
  sourceKey: string
  title: string
  defaultPresentation: 'card' | 'chart' | 'table' | 'image' | 'text'
}
```

- 기존 Open Cell과 Chassis rear 대시보드 ID와 새 `dashboard-run-comparison-default`를 읽기 시 시스템 분석 페이지 메타데이터로 정규화한다. Run 비교 페이지에는 전체 영역을 사용하는 `run_comparison` 위젯을 기본 정의로 저장한다.
- 시스템 분석 페이지의 `page` 메타데이터와 ID는 보호하지만 위젯 정의 저장은 허용한다. 따라서 editor/admin은 Run 비교 위젯을 포함한 시스템 페이지의 위젯 추가·삭제·이동·크기·속성을 저장할 수 있고, 이름·상태·순서·삭제는 변경할 수 없다.
- 기존 정의 중 `page` 메타데이터가 없는 복제본과 저장 변형본은 분석 탭 목록에 노출하지 않는다.
- 페이지 개수와 위젯 개수에 대한 `max` 검증은 모델과 API에 추가하지 않는다.
- 기존 저장 포맷과의 하위 호환을 유지하여 `page`가 없는 대시보드도 계속 읽을 수 있게 한다.
- `ReportElementBinding.source`에 `content`를 선택형으로 추가하고 `contentId`를 저장한다. `ReportLayoutDefinition`에는 선택형 `sourceScope`와 `contentMode: 'one-per-slide' | 'manual'`을 추가한다.
- 원천별 자동 구성은 표지 다음에 콘텐츠 수만큼 슬라이드를 생성한다. 자동 구성에서 콘텐츠를 32개로 자르지 않도록 기존 저장 검증의 고정 `slides <= 32` 제한을 제거하고, ID 중복·좌표·경계·지원 타입 무결성 검증은 유지한다.
- 저장 레이아웃의 `sourceScope`가 현재 보고서 원천과 맞지 않으면 기존 바인딩을 억지로 적용하지 않고 1슬라이드 1콘텐츠 기본 구성을 새로 만든 뒤 사용자에게 알린다.

## 4. API 계약

### 4.1 페이지 목록과 관리자 API

- `GET /api/dashboard-pages?load_case_id={id}`
  - 시스템 페이지와 해당 하중 경우의 `published` 사용자 페이지를 표시 순서대로 반환한다.
- `GET /api/admin/dashboard-pages?load_case_id={id}`
  - admin에게 해당 하중 경우의 `draft`, `published`, `archived` 페이지를 반환한다.
- `POST /api/admin/dashboard-pages`
  - `load_case_id`, 이름, 설명을 받아 빈 사용자 페이지를 `draft`로 생성한다.
- `PATCH /api/admin/dashboard-pages/{id}`
  - 이름, 설명, 상태를 변경한다. 게시/게시 해제/보관/복원을 같은 생명주기 검증으로 처리한다.
- `PUT /api/admin/dashboard-pages/order`
  - 하나의 하중 경우에 속한 사용자 페이지 순서를 원자적으로 저장한다.
- `DELETE /api/admin/dashboard-pages/{id}?load_case_id={id}`
  - admin 전용이다. 경로 페이지가 쿼리의 하중 경우에 속하는 custom 사용자 페이지인지 재확인하고, 버전과 본체를 트랜잭션으로 hard delete한다.
  - 성공 시 `{ status: 'deleted', id, load_case_id }`, 없는 페이지는 `404`, 시스템/비-custom 페이지는 `409`, 컨텍스트 불일치는 `409`, 권한 위반은 `403`을 반환한다.

### 4.2 기존 대시보드 API와의 결합

- 기존 `GET/PUT /api/dashboards/{id}` 및 복제, 버전 조회, 버전 복구 API를 유지한다.
- 일반 대시보드 `PUT`은 페이지의 이름, 설명, 상태, 순서 메타데이터를 변경하지 못하고 위젯 정의만 저장한다.
- editor의 저장 요청은 게시 페이지에만 허용한다.
- 초안과 보관 페이지 직접 조회 및 위젯 저장은 admin에게만 허용한다.
- 모든 상세/저장 요청은 요청 사용자가 접근 가능한 프로젝트-의뢰-하중 경우와 페이지 귀속 관계를 확인한다.
- 빈 페이지 게시 요청은 `422`, 시스템 페이지 보관/삭제 시도는 `409`, 권한 위반은 `403`으로 처리한다.
- 지원하지 않는 위젯 타입, 중복 위젯 ID, 음수 좌표/크기, 12열 범위 초과는 `422`로 처리한다.
- `run_comparison`을 대시보드 위젯 allowlist와 렌더러 매핑에 추가한다. `dashboard-run-comparison-default`는 다른 시스템 페이지와 같은 일반 `GET/PUT /api/dashboards/{id}` 경로를 사용하며 별도 저장 API를 만들지 않는다.
- 보고서 데이터 전용 복제 테이블은 만들지 않는다. 분석 페이지 보고서는 기존 dashboard/overview API를, Run 비교·검토 보고서는 기존 run-comparison, run-trust, review-items API를 사용하고 프런트에서 공통 `ReportContentItem[]`으로 조립한다.

### 4.3 대시보드 저장 이력 계약

- 기존 버전 목록/상세 API를 유지하고 `DELETE /api/dashboards/{dashboard_id}/versions/{version}`을 추가한다. 삭제는 행을 물리 제거하지 않고 `dashboard_versions.is_valid=false`로 바꾸는 논리 삭제이며 일반 저장 이력 목록에서는 제외한다.
- 과거 버전 삭제는 `admin`만 가능하다. `dashboards.version`과 같은 현재 live 버전, 존재하지 않거나 이미 무효인 버전은 각각 `409`/`404`로 거부한다.
- 시스템 대시보드의 최초 기준 버전(v1)은 삭제할 수 없다. 시스템/사용자 대시보드 모두 삭제 후에도 현재 live 버전 외에 최소 1개의 유효한 과거 버전이 남아야 하며, 이 조건을 깨는 요청은 `409`로 거부한다.
- 버전 삭제는 대시보드 자체, 현재 정의, 버전 번호를 변경하지 않는다. 이후 저장 버전은 기존 최대 버전보다 큰 단조 증가 번호를 사용하여 삭제된 번호를 재사용하지 않는다.

## 5. 프런트엔드 구현

- 기존 Workflow, Run 비교 내용, 상단 프로젝트/의뢰/하중 경우 선택기와 상세분석 전체 뼈대를 유지한다. 단, Run 비교·검토는 별도 화면 예외가 아니라 `dashboard-run-comparison-default` 시스템 분석 페이지의 `run_comparison` 위젯 렌더러로 편입한다.
- Open Cell/Chassis 하드코딩 탭 영역을 시스템 페이지와 게시 사용자 페이지를 함께 표시하는 동적 목록으로 교체한다.
- 현재 화면 종류와 실제 분석 페이지 ID를 분리하여 `activeDashboardId`에서 활성 페이지를 파생한다.
- 하중 경우 전환 시 overview, 변수 카탈로그, 분석 페이지 목록을 병렬로 다시 조회한다.
- 전환된 컨텍스트에 기존 활성 페이지가 없으면 Open Cell, Chassis rear, Run 비교·검토, 첫 게시 사용자 페이지 순으로 안전하게 이동한다.
- 관리자에게 `+ 분석 페이지` 버튼과 페이지 관리 드로어를 제공한다.
- 관리 드로어의 사용자 페이지 행에는 보관과 별도의 삭제 동작을 제공한다. 시스템 페이지에는 삭제 동작을 렌더링하지 않으며 서버 보호도 함께 둔다.
- 생성 직후 빈 캔버스를 선택하고 편집 모드로 진입하며, 위젯 추가 안내 CTA를 표시한다.
- 다수 탭은 가로 스크롤, 키보드 이동, 검색 가능한 전체 페이지 메뉴로 탐색한다.
- 기존 판정·차트·미디어 위젯은 `variableId`가 있으면 선택 변수의 단위, 기준, 판정, 미디어 메타데이터를 사용하도록 일반화한다. 변수가 없으면 기존 시스템 페이지 기본 동작을 유지한다.
- 이전 버전 복구 뒤 기본 대시보드를 다시 읽는 경로가 있다면 활성 `dashboard.id`를 다시 읽도록 수정한다.
- 기존 `activeView === 'compare'` 전용 렌더링, 보고서 숨김, 편집 숨김, 자연어 개선 숨김 분기를 제거한다. 기존 URL/추천 진입의 `preferred_view=compare`는 새 시스템 페이지 ID로 변환하여 북마크와 예제 진입 호환성을 유지한다.
- 보고서 내보내기, 자연어 개선, 대시보드 편집/저장/복구는 화면 종류를 분기하지 않고 모두 현재 `activeDashboardId`의 정의를 대상으로 한다. 자연어 개선안도 활성 정의의 위젯만 변경하고 `page` 메타데이터는 변경하지 못한다.
- `run_comparison` 위젯은 현재 baseline/target 선택을 위젯 설정 또는 페이지 런타임 문맥으로 유지하고 보고서 생성 시 해당 ID를 함께 넘긴다. 비교·trust·review API와 내부 비교·검토 UI는 기존 구현을 재사용한다.
- 보고서 대화상자는 원천 선택과 `ReportContentItem[]` 구성 단계만 추가하고 기존 `ReportLayoutEditor`를 그대로 사용한다. 콘텐츠 팔레트에서 포함 여부와 슬라이드 이동을 편집하고 기존 캔버스에서 순서·위치·크기를 편집한다.
- Open Cell `EdgeFilter`의 버튼은 글자 크기를 키워도 두 줄로 감기지 않게 `white-space: nowrap`과 내용 기반 최소 폭을 적용한다. 필터 행 자체를 강제로 압축하지 않고 좁은 화면에서는 가로 스크롤하며, 기존 선택 상태·클릭 동작·접근 가능한 레이블은 유지한다.
- 대시보드 편집 드로어의 `다른 이름으로 복제 / 최근 정상 버전 복구 / 저장 이력` 영역에 버전별 목록을 표시한다. 버전을 선택하면 상세 API에서 해당 정의를 읽어 **편집 초안**으로만 불러오며 이 동작만으로 live 정의나 이력은 바뀌지 않는다.
- 분석 페이지의 과거 버전을 초안으로 불러올 때 `id`, 현재 이름/설명, 현재 `page` 메타데이터는 live 정의에서 유지하고 위젯 등 편집 가능한 정의만 선택 버전에서 가져온다. 사용자가 `변경 저장`을 눌렀을 때만 현재 최대 버전 다음 번호로 새 버전을 생성하며 과거 버전 행을 덮어쓰지 않는다.
- 각 삭제 가능한 과거 버전 행에는 삭제 버튼과 확인 UX를 제공한다. 현재 live 버전, 시스템 v1, 최소 이력 보호 대상은 삭제 버튼을 비활성화하고 이유를 표시하며, 서버의 권한/보호 검증을 최종 기준으로 삼는다.
- 저장·복제·초안 불러오기·복구·버전 삭제에 사용하는 공통 notice/toast는 표시 후 4초에 자동으로 닫고 `X`로 즉시 닫을 수 있게 한다. 새 알림이 오면 기존 타이머를 취소하고 4초를 다시 계산하며 컴포넌트 해제 시 타이머를 정리한다. 오류 알림도 수동 닫기와 자동 종료를 지원하되 화면 읽기 도구가 인지할 수 있는 상태 역할을 유지한다.
- 보고서 `ReportLayoutEditor`의 기존 레이아웃 버전 선택/불러오기/저장은 위 대시보드 버전 UI와 독립적으로 그대로 유지한다.

   - 기존 변경과 충돌 가능성, 시스템 페이지 호환성, 운영 대시보드 공유 불변식을 검토한다.

## 7. 검증 계획과 완료 기준

### 7.1 백엔드/API

- 한 하중 경우에 여러 사용자 페이지를 생성할 수 있고 인위적인 개수 제한이 없는지 확인한다.
- 한 페이지에 여러 위젯을 저장할 수 있고 인위적인 개수 제한이 없는지 확인한다.
- 초안 생성, 이름 변경, 위젯 저장, 게시, 게시 해제, 순서 변경, 보관, 복원을 검증한다.
- 공개 목록에서 초안과 보관 페이지가 제외되고 시스템 페이지가 계속 노출되는지 검증한다.
- 하중 경우별 페이지 격리와 프로젝트/의뢰 귀속 검증을 확인한다.
- viewer/editor의 관리자 API 접근 거부, editor의 게시 페이지 위젯 편집, admin의 초안 편집을 확인한다.
- 빈 페이지 게시, 시스템 페이지 보관, 잘못된 위젯 정의가 정해진 상태 코드로 거부되는지 확인한다.
- 복제본이 분석 탭에 노출되지 않고, 버전 복구 후에도 페이지 메타데이터가 보존되는지 확인한다.
- admin hard delete 시 `dashboard_versions`와 `dashboards`가 모두 없어지고 이름을 재사용할 수 있는지, editor/viewer는 `403`인지, 시스템/비-custom/다른 하중 경우 대상은 삭제되지 않는지 확인한다.
- 삭제 도중 한 쿼리가 실패하면 트랜잭션이 롤백되어 본체와 버전이 모두 남는지 확인한다.
- Run 비교 보고서의 baseline/target 식별자, 수치 비교, trust, review가 동일한 대상 Run 문맥인지 확인한다.
- 위젯 N개의 새 기본 보고서가 표지를 제외하고 N개의 본문 슬라이드를 만들며 지원 위젯을 조용히 누락하거나 32개에서 자르지 않는지 확인한다.

### 7.2 프런트엔드/E2E

- admin이 페이지 생성, 위젯 추가/변수 연결/배치/설정, 저장, 게시 후 새로고침해도 상태가 유지되는지 검증한다.
- editor는 게시 페이지의 위젯만 편집하고 viewer는 읽기 전용으로 보는지 검증한다.
- 다수 페이지의 탭 overflow, 전체 목록 검색, 키보드 탐색을 검증한다.
- 프로젝트/의뢰/하중 경우를 변경하면 페이지, 변수, 결과가 새 컨텍스트에 맞게 갱신되는지 검증한다.
- 데이터가 없는 위젯은 페이지를 숨기지 않고 위젯별 빈 상태를 표시하는지 확인한다.
- 단일 보고서 버튼에서 현재 페이지가 기본 선택되고, 다른 게시 페이지 하나를 선택하여 해당 데이터만 PPTX에 반영할 수 있는지 검증한다.
- 활성 사용자 페이지 삭제 확인에서 정확한 이름 입력 전에는 실행할 수 없고, 삭제 뒤 정해진 우선순위의 페이지로 이동하며 삭제 페이지를 추가 조회하지 않는지 검증한다.
- 모든 분석 페이지에서 보고서·자연어 개선·대시보드 편집이 보이고 현재 `activeDashboardId`만 대상으로 동작하는지 검증한다. Run 비교에서 선택을 바꾸면 새 보고서가 새 baseline/target 문맥을 사용하고, 편집/자연어 개선 결과가 `dashboard-run-comparison-default` 정의에 저장되는지 확인한다.
- 위젯별 기본 1슬라이드 생성, 포함/제외, 슬라이드 재정렬, 콘텐츠 페이지 이동, 한 페이지에 여러 결과 배치, 드래그·리사이즈 후 PPTX 결과 순서와 배치를 검증한다.
- 새 `content` 바인딩 레이아웃 저장/버전 복구와 기존 레이아웃의 무변경 렌더링을 함께 회귀 검증한다.
- Run 비교 시스템 페이지의 위젯 이동·리사이즈·속성 저장과 버전 복구는 성공하고, 생명주기 변경·보관·삭제는 `409`로 거부되는지 검증한다.
- 기존 `preferred_view=compare` 진입이 새 시스템 페이지를 활성화하고, 별도 compare 예외 분기가 제거된 뒤에도 비교·신뢰도·검토 생성/상태 변경 기능이 회귀하지 않는지 검증한다.
- EdgeFilter를 기본 글자 크기, 확대 글자 크기, 좁은 viewport에서 확인하여 버튼 문구가 한 줄로 유지되고 가로 스크롤로 모든 항목에 접근 가능하며 선택 토글이 회귀하지 않는지 검증한다.
- 저장 이력에서 과거 버전을 선택하면 캔버스 초안만 바뀌고 새로고침 전 live 정의는 유지되며, 변경 저장 후에는 과거 이력 수정 없이 새 단조 증가 버전이 생성되는지 검증한다.
- admin의 개별 과거 버전 논리 삭제와 목록 제외를 확인하고 editor/viewer `403`, live 버전·시스템 v1·최소 1개 과거 이력 보호 `409`, 삭제 번호 미재사용을 API 테스트로 검증한다.
- 저장 관련 notice/toast가 4초 뒤 사라지고 `X`로 즉시 닫히며 연속 알림 시 마지막 알림 기준으로 타이머가 재시작되는지 검증한다.
- 대시보드 저장 이력 기능 추가 후에도 보고서 레이아웃 버전 선택과 복구가 기존대로 동작하는지 회귀 검증한다.
- Open Cell, Chassis rear, Edge Filter, 기존 보고서, 영상 그리드, Workflow, Run 비교, 운영 대시보드 집계를 회귀 검증한다.
