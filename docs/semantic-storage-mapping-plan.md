# 기준 정의 기반 폴더·읽기 레시피·결과·위젯 연결 개발 계획

- 작성일: 2026-09-14
- 개정: 2026-09-15, 사용자 요청 1번에 따라 기준 정의·별칭 관리와 명시적 추천 적용 확장
- 상태: CSV/JSON 기본 관리자 흐름 구현·검증 완료 / 고급 규칙·선택 확장 및 실제 서버 배포 검증은 후속 단계
- 결정: 완료된 배포 소스를 기준으로 분리한 사본에서 구현·검증 후 기능 변경만 통합한다. 배포 정책과 사용자 상태는 유지한다.
- 적용 우선순위: 최신 사용자 요청 → [개발 지침](../AGENTS.md)과 [Windows 배포 정책](windows-deployment-policy.md) → 본 계획.
- 아래 12.3절이 실제 구현 범위를 구분한다. 전체 계획 또는 실제 Windows Server 2022 검증 완료를 의미하지 않는다.

## 1. 사용자 요구와 이번 결정

프로젝트 폴더를 `Project_...`라는 이름으로 제한하지 않는다. 먼저 프로젝트·의뢰·하중 경우·실행·결과 같은 기준 개념을 정의하고, 임의 이름의 폴더·단어·파일 필드를 그 정의 및 실제 업무 대상에 연결한다. 사용자가 새 파일 샘플의 읽기 규칙을 저장하면 다음 파일부터 재사용한다. 일상적인 연결·별칭·포맷 변경은 코드 수정이나 서버 재배포 없이 처리한다.

후속 요구는 `결과 파일 샘플 → 라벨·포맷을 정의한 읽기 레시피 → 폴더의 확장자/내용 판별 → 공통 결과 항목 → 위젯 입력 연결` 전 과정을 관리자가 정의하는 것이다. 읽기 레시피, 결과 항목 사전, 표시 템플릿을 별도로 버전 관리하면서 한 설정 흐름에서 연결한다. 기존 문서의 포맷 프로필은 이 문서에서 읽기 레시피와 같은 개념이며 별도 중복 기능을 만들지 않는다. 최신 요청에서 배포 개발 완료와 기능 구현을 승인했으므로 이전의 문서 전용 보류를 해제한다.

최초 계획 작성 때 사용자는 진행 중인 배포 정책 개발과 충돌이 예상되면 상세 계획만 작성하도록 지정했다. 아래 표는 당시 보류 근거이며, 정책 자체는 설계와 양립한다. 구현에서는 같은 통합 경계를 회귀검사 대상으로 유지한다.

| 경계 | 관찰한 현재 상태 | 지금 구현할 때 예상되는 영향 |
|---|---|---|
| 시작과 DB 변경 | `backend/scripts/check_postgres_schema.py`는 pending revision이면 시작을 막고 배포로 안내한다. 관련 시작 스크립트가 변경 중이다. | 새 migration을 추가하는 순간 기존 개발 DB에서도 배포 경로가 필요하다. 기능 숨김만으로 해결되지 않는다. |
| 신규/기존 DB 배포 | ADR 0005와 배포 정책은 검증한 백업 후 migration, 기존 계정·데이터 보존을 요구한다. | 새 연결/사전/프로필/원본 저장 상태를 신규 설치·기존 데이터 업데이트·복원 검사에 포함해야 한다. |
| 폐쇄망 패키지 | 외부 PC에서 정적 웹·잠긴 의존성·서비스와 DB 도구를 묶는 설치기가 개발 중이다. | 파서 의존성이나 영구 파일 경로 추가는 패키지·백업 계약 검증 범위를 바꾼다. |
| 기존 SPDM | 경로 기반 ID와 `relative_path` 연결, 정해진 Project/WR/CAE 인식 규칙을 사용한다. | 무조건 교체하면 기존 대상 중복 생성·연결 소실·수집 중복 위험이 있다. |
| 동시 작업 | 같은 작업 폴더에서 배포 및 화면 개선 작업이 실행 중인 것을 읽기 전용으로 확인했다. | 공통 문서·환경 설정·시작/설치 코드·화면 진입점 수정은 작업 간 충돌 가능성이 있다. |

최초 작업은 문서만 작성했다. 이번 구현은 최신 작업 트리의 배포 변경을 보존하고 additive migration 0024, 순수 CSV/JSON 엔진, 관리자 화면 및 실행별 결과 조회를 추가한다. 기존 배포 진입점, 의존성 lock, 영구 자산 경로를 변경하지 않는다. 현재 지원 범위와 사용 절차는 [구현·사용 안내](semantic-mapping-guide.md), 선택 확장과 수락 목표는 본 계획을 기준으로 한다.

## 2. 현행 코드에서 재사용할 기반

| 기반 | 확인 경로 | 유지/확장 방향 |
|---|---|---|
| SPDM 인식·연결 | `backend/app/services/spdm_storage.py` | 기존 이름 규칙을 legacy adapter로 유지하고 명시적 의미 연결 adapter를 추가한다. |
| 저장소 테이블 | `backend/migrations/versions/0020_spdm_storage.py` | 기존 프로젝트·의뢰·하중 경우·Run ID와 연결을 보존한다. |
| 포맷 저장·버전 이력 | `backend/app/application/import_schemas/commands.py`, `backend/app/adapters/persistence/import_schemas.py` | 기존 포맷 버전 저장을 재사용하되 새로운 프로필 종류를 명시적으로 구분한다. |
| 현재 정의 검증 | `backend/app/domains/import_schemas/policies.py` | 현재 `mappings` 배열 여부 검증을 구조·의미·지원 연산 검증으로 확장한다. |
| 결과 정규화·저장 | `backend/app/application/results/ingestion.py`, `backend/app/adapters/persistence/result_ingestion.py` | 새 포맷도 기존 canonical 결과와 공통 UoW에 전달한다. 별도 결과 DB를 만들지 않는다. |
| canonical manifest | `backend/app/parsers/manifest_format.py`, `backend/app/folder_import.py` | `mappings`/legacy 형식 구분과 검증을 유지한다. 새 규칙으로 기존 오류를 묵시적으로 우회하지 않는다. |
| 위젯 선택·변수 설정 | `frontend/src/features/workbench/requestResultWidgetCatalog.ts`, `RequestResultWidgetConfiguration.tsx` | 기존 타입/배치를 재사용하고 변수 키 직접 입력을 결과 항목 선택과 입력 역할 연결로 확장한다. |
| 위젯 데이터 선택 | `frontend/src/features/results/AnalysisWidgets.tsx` | 일부 이름·그룹 필터와 미디어 대체 선택을 확인했다. 새 명시적 연결에서는 데이터 계약으로 선택하고 결과가 없을 때 다른 항목으로 대체하지 않는다. |

이 표는 제한적으로 읽은 구현 근거다. 구현 시 각 모듈의 호출 경로·테스트·최신 migration head를 추가 확인한다. 현재 import schema 저장 기능이 곧 범용 자동 포맷 판별 기능인 것은 아니다.

## 3. 핵심 모델: 개념·대상·위치를 분리

### 3.1 기준 개념과 관계

- 개념: 프로젝트, 해석 의뢰, 하중 경우, 실행, 입력 자료, 결과 자료, 보고서, 측정량.
- 속성: 표시명, 설명, 자료형, 단위 차원, 선택 가능한 역할, 적용 범위.
- 관계: 프로젝트에 속한 의뢰, 의뢰에 속한 하중 경우, 하중 경우에서 수행한 실행, 실행에서 얻은 결과.
- 모든 개념은 고정 ID와 개정 이력을 가진다. 표시명 변경은 ID 변경이 아니다.
- 사용자는 기존 지원 유형 안에서 개념·속성·별칭을 추가할 수 있다. 새 개념을 추가했다고 DB 업무 엔터티나 전용 화면이 자동 생성되지는 않는다.
- 물리적인 폴더 깊이는 업무 관계를 결정하지 않는다. 기준 관계의 순환과 잘못된 대상 유형을 검증한다.

### 3.2 실제 업무 대상

실제 프로젝트 P001, 의뢰 R003, 하중 경우 C082는 기존 업무 테이블의 ID로 식별한다. 폴더 연결을 위해 같은 업무 대상을 새로운 테이블에 복제하지 않는다. 개념 `PROJECT`와 실제 프로젝트 `P001`은 다르다.

### 3.3 저장 위치와 역할

| 물리적 위치 예시 | 분류/역할 | 연결 대상 |
|---|---|---|
| `Eagle_2026` | 프로젝트 자료 | P001 |
| `외부결과/ABC` | 결과 자료 | P001 |
| `NewPlatform/Customer_A_Test` | 의뢰 자료 | R003, 소속 프로젝트 P001 |
| `try_03` | 실행 자료 | RUN003, 소속 하중 경우 C082 |

- 하나의 대상에 여러 폴더를 연결할 수 있다. 원본을 재배치할 필요가 없다.
- 폴더 종류를 지정하는 것과 어느 대상에 연결하는 것은 UI에서 구분한다.
- 같은 폴더에 여러 자료 역할은 허용할 수 있지만, 결과 적재 시 업무 대상은 하나로 확정되어야 한다.
- MVP에서는 같은 수집 경계를 여러 업무 대상의 자동 적재 경로로 동시에 등록하지 않는다. 공유 참고자료 연결은 조회 전용으로 구분한다.
- 프로젝트 폴더라는 이유만으로 기본 하중 경우나 Run을 추정 생성하지 않는다. 결과 등록 전 필요한 대상 선택 또는 명시적인 생성 단계를 수행한다.

## 4. 폴더 탐색·연결과 변경 처리

### 4.1 탐색 흐름

1. 허용된 저장소 루트 아래 폴더를 지연 탐색한다. 이름 규칙과 무관하게 미분류 폴더도 표시한다.
2. 사용자가 폴더를 선택하고 종류/역할과 기존 업무 대상을 지정한다. 필요할 때 별도 명시적 생성으로 새 업무 대상을 만든다.
3. 상위 연결의 프로젝트 소속을 하위에 적용할 수 있다. 종류·파일 포맷·등록 대상까지 자동 상속하지 않는다.
4. 명시적인 하위 연결은 상속 경계를 만든다. 그 하위 영역은 상위 결과 수집에서 제외해 이중 적재를 막는다.
5. 다른 프로젝트에 연결된 중첩 폴더는 권한과 관계 충돌을 표시한다. MVP에서는 중첩 자동 적재를 거부하고 경계를 분리하게 한다.
6. 연결 영향 미리보기에서 적용되는 하위 폴더, 제외 경계, 기존 연결, 예상 대상 수를 보여준다.
7. 저장 폴더 새로고침은 승인된 연결과 활성 규칙으로만 수집한다. 탐색만으로 결과나 미확인 업무 대상을 만들지 않는다.

### 4.2 매칭 우선순위

`검증된 저장소 내 고정 식별자 → 기존 명시적 연결 → 범위가 맞는 활성 규칙 → 미확정 후보`

- 이름 정규화(대소문자·공백 등)는 비교 키에만 적용하고 원본 경로는 보존한다. 정규화 충돌은 자동 병합하지 않는다.
- 오타·유사어는 추천 근거다. 복수 후보, 같은 우선순위 규칙 충돌, 기존 ID 불일치 시 `NEEDS_REVIEW`로 둔다.
- 사용자가 한 폴더를 프로젝트에 연결한 것을 전역 단어 별칭으로 자동 등록하지 않는다.
- 명시적인 연결을 일반 규칙으로 저장할 때 적용 저장소/프로젝트, 조건, 제외 조건을 별도로 지정한다.
- 규칙의 우선순위가 있어도 기존 확정 연결을 자동 덮어쓰지 않는다. 매칭 결과에 규칙 ID·버전·근거를 표시한다.

### 4.3 안정적 식별자와 이름 변경

- 기본은 DB 연결이며 `(storage_root_id, location_id)`와 현재 상대 경로·이전 경로 이력을 분리한다.
- 이름과 경로가 모두 바뀌고 식별 근거가 없으면 수동 재연결을 지원한다. 내용 해시만으로 동일 업무 대상이라고 단정하지 않는다.
- 선택 기능으로 폴더 안에 고정 식별자 메타데이터 파일을 둘 수 있다. 명시적인 활성화와 쓰기 권한이 있을 때만 작성한다.
- 메타데이터는 locator 정보이며 권한 증명이 아니다. 서버의 저장소 범위·DB 관계·사용자 권한을 다시 검증한다.
- 폴더 복사로 같은 식별자가 두 경로에 나타나면 이동으로 단정하지 않고 충돌을 표시한다. 동일 자료의 복제본인지 새 업무 대상인지 선택하게 한다.
- 루트 경로가 바뀌거나 DB를 복원한 경우 저장소 재연결 검증을 거친다. 예전 서버 경로에 자동 쓰지 않는다.
- 스캔의 경로 이탈·심볼릭 링크/reparse point 차단·페이지 크기·최대 깊이·파일 수·시간/용량 제한을 유지한다. 메타데이터를 이유로 우회하지 않는다.

## 5. 읽기 레시피·결과 항목·위젯 연결

### 5.1 등록 화면과 상태

`샘플 업로드 → 구조 확인 → 기준 필드·단위 연결 → 변환 미리보기 → 검증 → 활성화`

이 흐름으로 레시피만 저장할 수도 있고, 5.8절의 관리자 설정 흐름에서 결과 항목·위젯까지 연결할 수도 있다. 파일 읽기 설정(인코딩·자료형·숫자 해석)과 화면 표시 설정(라벨·소수 자릿수·색상·표시 단위)은 분리한다.

- 최초 범위는 CSV 및 JSON의 scalar/curve 결과다. 입력 원본·보고서·미디어 연결은 기존 분류를 재사용한다.
- 각 프로필은 `DRAFT / VALIDATED / ACTIVE / RETIRED` 상태와 불변 버전을 가진다.
- 새 샘플에서 제안한 프로필은 초안으로 저장한다. 업로드만으로 다른 파일의 처리 규칙을 활성화하지 않는다.
- 미리보기에는 원본 값과 변환 값, 단위, 대상 프로젝트/하중 경우, 오류 위치, 누락/추가 필드, 예상 결과 수를 표시한다.
- 활성화는 검증 결과와 편집 revision이 일치할 때 수행한다. 샘플 검증 이후 정의를 수정하면 다시 검증한다.

### 5.2 저장할 규칙

| 구분 | 저장 내용 |
|---|---|
| 식별 | 프로필 ID/버전, 정의 문서 버전, 필요한 엔진 기능 버전 |
| 적용 범위 | 저장소·프로젝트·공급자/도구·자료 역할, 사용자 명시적 프로필 선택 |
| 판별 조건 | 파일 종류, CSV 필수/금지 헤더, JSON root 구조·필수 경로·상수 버전 값 |
| 읽기 설정 | 인코딩, 구분자, 헤더 행, 숫자·결측 표현, 제한된 JSON 배열/필드 선택 |
| 의미 매핑 | 소스 필드 → 개념/측정량 ID → canonical variable_key, 위치/series 구분 |
| 변환 | 검증된 자료형 변환, trim, 명시적 값 매핑, 단위 변환 등 허용 연산 |
| 검증 | 필수 여부, 자료형, 유한 숫자, 단위 차원, 중복, curve X축 정책, 건수/크기 제한 |
| 이력 | 초안/활성화 작성자, 시각, 샘플 해시, 회귀 fixture, 활성화 근거 |

판별은 파일명이나 확장자만으로 완료하지 않는다. 명시적으로 선택한 프로필도 내용 검증 실패 시 적용하지 않는다. 여러 활성 프로필에 일치하면 선택을 요구하며, 임의의 첫 프로필로 처리하지 않는다.

### 5.3 구체적 예

| 기준 측정량 | CSV 프로필 v1 | JSON 프로필 v2 |
|---|---|---|
| 시간(초) | `Time_ms`, 단위 ms → s | 측정 배열 각 항목의 `time_s` |
| 응력(MPa) | `Stress_MPa` | 측정 배열 각 항목의 `stress_pa`, Pa → MPa |
| 측정 위치 | `Node_ID` | 각 항목의 `node` |

위 두 프로필은 같은 canonical 결과 계약으로 출력한다. 최대값·평균값·특정 위치의 값은 단위가 같아도 서로 다른 의미이므로 자동으로 같은 측정량에 합치지 않는다.

### 5.4 코드 수정 없이 가능한 범위

- 지원 리더 범위의 CSV 열 이름/순서/헤더 위치, JSON 필드/배열 위치 변경.
- 기준 개념의 표시명·별칭, 명시적 폴더 연결, 범위가 정해진 매칭 규칙.
- 지원 연산에 한한 타입·단위·값 변환, 필수 필드·허용 값·결측 검증.
- 기존 지원 결과 유형 안에서 새 측정량과 포맷 프로필 추가.
- 지원 위젯의 입력 역할 연결, 결과 항목 선택, 축·범례·표 열·표시 라벨·단위·자릿수 설정 및 표시 템플릿 적용.

새 독점 바이너리 리더, 새로운 업무 엔터티/화면, 새로운 위젯 렌더러, 복잡한 여러 파일 조인·도메인 계산, 미지원 자료형은 엔진/어댑터 개발과 정상 배포가 필요하다. 사용자 규칙에 Python/JavaScript/SQL 실행문이나 동적 패키지 설치를 넣지 않는다. PKL 실행/역직렬화도 이 기능으로 추가하지 않는다.

### 5.5 결과 항목 사전과 실제 결과

위젯은 원본 필드명이나 레시피 이름 대신 고정 `result_item_id`를 참조한다. 결과 항목은 기준 개념 사전의 측정 의미를 참조하고 기존 canonical variable_key와의 호환 연결을 가진다. 이 ID는 아래 설계안의 신규 개념이며 현재 구현된 필드를 뜻하지 않는다.

| 층 | 예시 | 변경 의미 |
|---|---|---|
| 원본 필드 | `MaxStress`, `Smax`, `peak_stress_pa` | 레시피마다 달라도 같은 기준 항목에 연결 가능 |
| 결과 항목 정의 | 최대 응력 / 고정 ID / 수치 / MPa / 측정 위치 차원 | 의미·자료형·차원·허용 결과 개수를 정의 |
| 실제 결과 | Run A·Node 10의 120 MPa, Run B·Node 10의 115 MPa | 각각의 실행·위치·출처를 보존하는 별도 결과 |
| 표시 설정 | 최대 응력, Peak Stress, 소수 1자리 | 위젯별 표현이며 원본 값·항목 identity는 불변 |

- 레시피 하나는 여러 결과 항목을 출력할 수 있다. 여러 레시피가 같은 결과 항목을 출력할 수도 있다.
- 항목을 통일한다는 것은 의미를 통일한다는 뜻이다. 실행·하중 경우·부품·위치·series별 값을 합치거나 덮어쓰지 않는다. 결과의 grain(한 레코드가 나타내는 대상)을 정의에 명시한다.
- 최대/평균/시간 이력은 별도 의미 또는 명시적인 파생 관계다. 시간 이력을 scalar 위젯에 연결하면서 암묵적으로 최댓값을 계산하지 않는다. 파생 연산은 지원 범위·입력·집계 차원·결측 정책을 별도 정의하고 버전을 남긴다.
- 동일 Run/항목/차원 키에 두 파일이 값을 제공하면 중복 또는 충돌을 표시한다. 기본은 덮어쓰기 금지이며, 원본 우선순위를 허용할 경우 관리자가 명시한 버전 규칙과 선택 근거를 기록한다.
- MVP 수치 적재는 파일별 등록 단위를 유지한다. 여러 파일을 한 Run에 자동 묶으려면 공통 실행 식별자, 필수 파일 목록, 완료 판정, 묶음 멱등성과 원자적 저장 계약이 필요하며 별도 후속 범위로 둔다. 폴더가 같다는 이유로 한 Run에 합치지 않는다.
- 라벨 변경은 참조를 유지한다. 의미/자료형 변경은 호환성 검증을 거쳐 새 항목 또는 새 의미 버전으로 만든다. 사용 중 정의는 물리 삭제하지 않고 폐기 상태로 유지한다.

### 5.6 폴더의 파일 선택과 레시피 적용

1. 관리자가 허용된 폴더 연결에 확장자 목록, 포함/제외 조건, 적용 레시피 후보와 대상 규칙을 저장한다.
2. 스캔은 확장자로 후보를 좁힌 뒤 내용 구조·필수 필드·버전 값으로 실제 레시피를 판별한다. 확장자만 바꾼 파일은 내용 검증을 통과해야 한다.
3. 한 레시피로 확정된 파일만 검증·정규화한다. 미지원 확장자, 미일치, 복수 일치, 작성 중 파일을 서로 다른 상태로 표시한다.
4. 출력 항목과 대상 Run/하중 경우, 예상 건수, 오류를 확인한 뒤 기존 수집 정책에 따라 적재한다. 이미 활성화된 설정의 반복 수집은 매번 대화형 확인을 요구하지 않는다.
5. 영상·이미지는 지원 미디어 등록 경로로 결과 항목에 연결한다. 읽을 수 없는 바이너리를 수치 파서에 넘기지 않는다.

새로고침 한 번이 모든 파일에 동일 레시피를 강제하는 것은 아니다. 폴더별 후보 레시피와 실제 파일별 선택 결과를 표시한다. 최초 범위는 명시적 새로고침이며 자동 감시/스케줄러 추가는 별도 작업이다.

### 5.7 위젯의 입력 역할과 표시 템플릿

| 위젯 | 입력 역할 | 연결 검증 |
|---|---|---|
| 수치 카드·게이지 | 값, 선택적 판정 기준 | 선택 문맥에서 한 값으로 확정, 자료형·단위 일치 |
| 선 그래프 | X축, Y축, series, Run 선택 | 배열/곡선 구조, X/Y 개수와 차원, 순서·중복 정책 |
| 산점도 | X 항목, Y 항목, 짝지을 키 | 같은 Run·위치 등 명시한 키로 유일하게 대응; 행 순서로 짝짓지 않음 |
| 표·막대그래프 | 결과 항목 목록, 행/범주 키, 표시 순서 | 항목의 grain 일치, 결측·중복 표시, 필요한 집계 명시 |
| 이미지·영상 | 미디어 항목, Scene/시점, Run 선택 | media 유형, 권한, 선택 개수, 안전한 asset 참조 |
| 전용 평가 위젯 | 도면 위치·측정 항목·기준 등 선언된 입력 | 기존 전용 계약을 만족할 때만 연결; 범용 지원으로 오인하지 않음 |

- 관리자 화면은 호환되는 결과 항목을 선택 목록으로 제공한다. 표시명은 바꿀 수 있지만 연결은 고정 ID로 저장한다.
- 연결에는 대상 문맥(현재/명시적 Run), 결과 항목 ID·의미 버전, 입력 역할, 위치/series 필터, 지원된 집계 정책, 표시 설정을 저장한다.
- 여러 값인데 단일 값 위젯에 연결한 경우 첫 값/최근 값으로 자동 축약하지 않는다. `AMBIGUOUS_RESULT`로 표시하거나 명시적인 선택/집계 규칙을 요구한다. 자동 최신 선택을 지원하면 완료 상태·정렬·동률 정책을 정의한다.
- 연결된 결과가 없으면 `MISSING_RESULT`, 자료형/단위가 맞지 않으면 `INCOMPATIBLE_RESULT` 등 원인을 표시한다. 무관한 첫 scalar/영상으로 대체하지 않는다.
- 같은 결과를 여러 위젯이 소비하고, 한 위젯이 여러 항목을 소비할 수 있다. 같은 위젯 타입도 다른 항목을 연결해 여러 인스턴스로 배치할 수 있게 한다.
- 표시 템플릿은 위젯 인스턴스·입력 연결·표시 설정의 묶음이다. 프로젝트/해석 유형별 기본 적용과 명시적 개별 재정의를 지원하며 적용 범위·우선순위 충돌을 검증한다.
- 표/산점도의 연결은 정규화된 결과 키의 대응이다. 복잡한 원본 파일 조인 기능을 위젯 설정에 숨겨 추가하지 않는다.
- 기존 전용 위젯과 배치를 보존한다. 기존 variable_key 설정은 확정 가능한 항목만 변환하고, 불명확한 연결은 legacy로 유지하며 사용자에게 해결 대상을 표시한다.

### 5.8 관리자 설정 흐름과 버전 경계

1. 결과 샘플 파일을 올려 원본 구조와 값을 확인한다.
2. 필드에 기준 의미·자료형·단위를 지정하고 기존 결과 항목을 선택하거나 새로 정의한다.
3. 레시피가 만든 결과 목록에서 한 파일의 여러 출력과 실행·측정 위치별 값을 확인한다.
4. 위젯을 추가하고 값·축·열·미디어 입력 역할을 결과 항목에 연결한다.
5. 실제 위젯과 변환 데이터를 함께 미리 본다. 파싱만 성공해도 위젯 입력이 맞지 않으면 연결 검증 실패로 표시한다.
6. 적용 폴더·확장자·레시피 선택 규칙 및 프로젝트/해석 유형별 표시 템플릿 범위를 지정한다.
7. 레시피·결과 정의·표시 템플릿을 각각 불변 버전으로 저장하고, 검증된 참조 버전 묶음을 활성화한다. 한 번의 설정 흐름이므로 실패 시 일부 참조만 활성화되지 않도록 트랜잭션 경계를 둔다.
8. 다음 파일의 새로고침에서 같은 레시피와 결과 항목 연결이 재사용되는지 확인한다.

- 레시피를 새 버전으로 바꾸어도 출력 의미 계약이 유지되면 기존 표시 템플릿을 재사용한다. 계약이 달라지면 영향을 받는 위젯을 보여주고 수정·검증 전 활성화를 막는다.
- 제목·색상·자릿수·레이아웃 같은 표시 변경은 재적재/새 Run을 만들지 않는다. 값 해석·단위 변환·측정 의미 변경은 레시피/의미 버전 변경이며 기존 재처리 정책을 따른다.
- 템플릿 버전 변경은 기존 대시보드에 자동 덮어쓰지 않는다. 기본값 갱신과 기존 배치 적용을 구분하고 변경 미리보기를 제공한다.
- 일반 화면은 선택한 템플릿 버전과 현재 Run 문맥을 사용한다. 저장/공유한 결과 뷰는 템플릿·연결 버전과 실제 Run/결과 ID를 고정하여 이후 기본값 변경과 구분한다.
- 관리자 권한은 기존 프로젝트 범위를 따른다. 템플릿 공유는 결과 데이터 조회 권한을 확대하지 않는다. 읽기 레시피와 위젯 바인딩도 업로드/조회 시 서버에서 검증한다.
- 활성화 전 대표 정상/오류 샘플과 적용 범위의 기존 파일 fixture, 영향을 받는 위젯을 다시 검증한다. 전체 저장소를 매번 무제한 스캔하지 않고 검증한 대상과 미검증 범위를 보고한다. 이전 정의로 되돌릴 때도 참조 호환성을 검사하며 과거 결과는 재작성하지 않는다.

### 5.9 제안 기능 포함 목록과 후속 확장

아래 목록은 대화에서 제안한 기능의 추적표다. 초기 범위 밖인 기능도 계획에서 제거하지 않고 선행 조건과 후속 단계로 남긴다. 관리자의 일상적인 설정에는 코드 작성이나 외부 AI 연결이 필요하지 않다.

| 제안 기능 | 계획 위치/단계 | 포함 방식 |
|---|---|---|
| 임의 폴더 태그·실제 대상 연결, 한 대상의 여러 위치 | 3~4절, 단계 1~2 | 기본 기능 |
| 범위별 별칭·오타 후보·재사용 매칭 규칙 | 4.2절, 단계 5 | 확정 연결 우선, 후보는 검토함에서 처리 |
| 이름 변경·이동·복제 충돌, 선택적 식별자 파일 | 4.3절, 단계 2/5 | DB 연결 기본, 메타데이터 쓰기는 선택 기능 |
| 샘플 기반 레시피와 단위/라벨/필드 매핑 | 5.1~5.6절, 단계 3 | CSV/JSON부터 시작, 내용 판별·버전 재사용 |
| 결과 항목 사전과 다중 출력·다중 원본 | 5.5절, 단계 1/3 | 의미 통일, Run/위치별 관측값 보존 |
| 카드·그래프·표·이미지·영상 입력 연결 | 5.7절, 단계 4 | 기존 지원 위젯의 입력 계약과 호환 항목 선택 |
| 같은 항목의 여러 위젯, 같은 타입의 여러 인스턴스 | 5.7절, 단계 4 | 고유 widget instance ID로 구분 |
| 프로젝트/해석 유형별 표시 템플릿·개별 재정의 | 5.7~5.8절, 단계 4 | 결과 사전/레시피와 별도 버전·적용 범위 |
| 변환 결과와 위젯 통합 미리보기·영향 분석 | 5.8절, 단계 3~5 | 활성화 전 데이터/화면/기존 fixture 확인 |
| 규칙 이력·재처리·저장 뷰 재현·이전 정의 복원 | 5.8절/6절, 단계 5 | 참조 버전 고정, 데이터/표시 변경 구분 |
| 레시피/템플릿 내보내기·반입 | 8.2절, 단계 5 | 정의 패키지로 재사용, 초안 반입·참조 재연결 |
| AI 기반 필드 의미·매핑 초안 제안 | 단계 7, 선택 확장 | 수동 설정 완성 후 검토하며 확정 규칙을 대체하지 않음 |
| 지원 집계·파생 항목 및 여러 파일의 Run 묶음 | 5.5절, 단계 7 | 연산·차원·출처·완료/원자성 계약을 먼저 확정 |

AI 제안은 이름/샘플로 후보와 근거를 생성하는 보조 기능이다. AI가 제안한 레시피도 초안이며 동일한 검증·활성화 절차를 따른다. 폐쇄망 기본 설치와 기본 기능은 AI 없이 완결한다. 외부 전송을 기본값으로 켜지 않으며, 도입 시 조직이 허용한 실행 위치와 데이터 범위·로컬 모델의 패키징/라이선스를 별도 확인한다. 현재 계획은 AI 런타임의 설치나 서비스 추가를 승인·실행하는 것이 아니다.

## 6. 저장·재현·권한 계약

- 기준 사전, 결과 항목, 연결, 규칙, 프로필, 위젯 입력 계약/바인딩, 표시 템플릿과 버전은 영구 DB 상태로 저장한다. 신규 개념/포맷/표시 연결 등록은 데이터 쓰기이며 DDL이 아니다.
- 원본 샘플/필요 원본은 기존 관리형 첨부파일 저장 추상화를 우선 사용한다. 외부 원본 링크만 남긴 경우 원본 삭제 후 재처리를 보장한다고 표시하지 않는다.
- import 기록에는 대상 ID, 저장소/location ID, 원본 해시, 개념 개정·연결·규칙·포맷·엔진 버전, 정규화 결과 해시, 실행자·시간을 보존한다.
- import에는 결과 항목의 의미 버전까지 보존하고, 저장된 결과 뷰에는 widget 입력 계약/바인딩/템플릿 버전과 실제 결과 ID를 보존한다. 표시 버전은 적재 멱등 키에 넣지 않는다. 화면 제목 변경만으로 새 Run을 만들지 않으며 입력 의미가 바뀐 재처리와 구분한다.
- 멱등성은 파일 경로 하나로 판단하지 않는다. 대상 + 원본 해시 + 프로필/규칙 의미 버전으로 동일 재시도를 판정한다. 기존 수집의 멱등 키와 공존 adapter로 연결해 이중 Run을 방지한다.
- 현행 `canonical_result_ingestion_sources`의 PK는 `(source_type, source_name, source_checksum)`이며 `domains/results/models.py`의 `source_key_for`는 `source_run_id`가 없으면 `name:{source_name}`을 사용한다. 새 location identity로 전환할 때 기존 source reservation/Run과의 대응을 보존하는 호환 명세·fixture를 먼저 작성한다. rename 후 신규 source_name만 발급하는 방식은 채택하지 않는다. 모든 rename을 새 Run으로 처리하거나 과거 source 기록을 일괄 재작성하지 않는다.
- 규칙/단위 변경은 과거 Run을 덮어쓰지 않는다. 재처리는 명시적 실행으로 새 Run 및 이전 실행 관계를 기록한다.
- 초안도 저장소/프로젝트 권한을 적용한다. 미리보기·샘플·규칙 후보에서 다른 프로젝트의 경로·데이터를 노출하지 않는다.
- 프로젝트 관리자는 허용된 프로젝트의 연결/규칙을 관리하고, 전역 기준 사전 및 전체 저장소 설정은 관리자 권한으로 관리한다. 최종 역할 매핑은 기존 권한 정책을 재사용한다.
- 동시에 수정된 정의는 revision 충돌을 반환한다. 시작 시 고정한 규칙 버전으로 import를 완료하고 중간 변경을 섞지 않는다.
- 백업에는 사용자 정의와 모든 참조 버전, 감사 이력, 관리형 샘플/원본을 포함한다. 조직 공유 원본 폴더 전체를 자동 백업한다고 가정하지 않는다.

## 7. 모듈·데이터·API 설계안

다음 이름은 구현 시 확정할 제안이며 현재 존재하는 API/테이블을 뜻하지 않는다.

| 모듈 | 책임 | 제안 위치 |
|---|---|---|
| 기준 정의 | 개념·관계·속성·범위별 별칭 검증 | `domains/semantic_catalog`, `application/semantic_catalog` |
| 의미 연결 | 위치 identity·역할·상속·충돌·변경 이력 | `domains/storage_mapping`, `application/storage_mapping` |
| 저장소 어댑터 | 제한된 탐색, 기존 SPDM 연결 호환 | `adapters/storage` |
| 포맷 프로필 | 판별·상태·버전·검증 fixture | 기존 `domains/import_schemas` 확장 |
| 변환 엔진 | bounded CSV/JSON 읽기, 허용 변환, canonical 출력 | `services/profile_result_ingestion_adapter.py` 등 |
| 결과 항목 사전 | 의미·자료형·단위·grain·canonical 호환 연결 | `domains/result_catalog`, `application/result_catalog` |
| 위젯 연결 | 입력 역할·개수·차원 검증, 문맥별 결과 선택 | `domains/widget_bindings`, `application/widget_bindings` |
| 표시 템플릿 | 인스턴스·바인딩·표시 설정·범위·버전 관리 | 기존 workspace 설정 persistence와 호환 adapter |
| 결과 저장 | 기존 트랜잭션·권한·중복·감사 | 기존 `ResultIngestionUnitOfWork` |
| 웹 기능 | 탐색·연결, 기준 사전, 포맷 등록, 검토함, 입력 연결·통합 미리보기 | `frontend/src/features/storageMapping`, `importProfiles`, `resultBindings` |

논리 데이터 집합:

1. `semantic_concepts`, 불변 `semantic_concept_versions`, 범위별 `semantic_aliases`, `semantic_relations`.
2. 저장소 identity, `storage_locations`, location 경로 이력, 업무 대상별 연결과 역할, 불변 연결 revision.
3. `mapping_rules`와 버전/상태/적용 범위, 충돌 및 검토 기록.
4. 기존 `import_schemas`/`import_schema_versions` 확장, sample 참조, 검증 실행/fixture 및 provenance.
5. `result_item_definitions`와 불변 의미 버전, 개념·canonical 변수 연결, 결과 관측값의 grain/출처 연결. 기존 결과 테이블과 값을 불필요하게 복제하지 않는다.
6. `widget_input_contracts`, 위젯 instance별 `widget_bindings`와 버전, `presentation_templates`와 버전/범위, 고정 결과 뷰 참조. 기존 레이아웃 저장과 별도의 이중 정본을 만들지 않는다.

정확한 물리 테이블은 기존 schema와 데이터베이스별 제약을 조사한 후 확정한다. target_type/target_id 문자열만 두고 존재·관계 검증을 생략하지 않는다. 가능하면 유형별 FK로 기존 업무 대상에 연결하고, 공통 타입 표현이 필요해도 트랜잭션 안에서 관계를 검증한다.

API 책임: 저장소 폴더 페이지 조회, 연결 미리보기/저장/재연결, 개념·별칭 관리, 프로필 초안/검증/활성화, 미인식·충돌 목록, 명시적 결과 등록·재처리. 절대 경로를 클라이언트 입력으로 받지 않고 허용 루트 ID와 상대 경로를 사용한다. 오류는 `UNMAPPED`, `AMBIGUOUS`, `SCHEMA_MISMATCH`, `UNIT_MISMATCH`, `SOURCE_BUSY`, `VERSION_UNSUPPORTED`처럼 구분하되 기존 오류 계약과 정합성을 검토한다.

확장 API 책임: 결과 항목/호환 위젯 입력 조회, 입력 바인딩 검증, 변환+위젯 통합 미리보기, 참조 의존성/영향 조회, 템플릿 버전 활성화·적용·복원, 정의 패키지 반입/내보내기. `MISSING_RESULT`, `AMBIGUOUS_RESULT`, `INCOMPATIBLE_RESULT`를 구분한다. 브라우저의 필터만 신뢰하지 않고 서버에서 결과 접근 권한과 연결 참조를 검증한다.

## 8. 배포 정책을 그대로 유지하는 도입 방법

### 8.1 최초 기반 도입

1. 배포 작업의 기준 revision·정책·검증 상태를 확정한다. 별도 checkout에서 구현하고 적용 대상 migration head를 다시 확인한다.
2. 기존 데이터/계정/Run ID를 보존하는 additive migration을 준비한다. migration 번호는 지금 선점하지 않는다.
   - 통합 시 단일 Alembic head와 기존 revision의 조상 관계를 유지한다. 새 테이블의 app-role CRUD 권한과 시작 catalog 검사도 확인하며, 이를 위해 앱 실행 계정에 DDL 권한을 주지 않는다.
3. 최초 설치와 기존 DB 업데이트에서 같은 기존 배포 도구로 스키마를 적용한다. 앱 시작·첫 접속·프로필 업로드에 DDL을 넣지 않는다.
4. 기존 binding을 새 위치/의미 모델로 backfill할 때 원래 업무 ID를 유지한다. 기존 연결 수·대상·경로·고아 참조 검증 및 재실행 멱등성을 기록한다.
5. 초기 기본 개념만 충돌 없는 고정 ID로 제공한다. 업데이트가 사용자 별칭·정의·활성 프로필을 덮어쓰지 않도록 시스템 기본과 사용자 개정을 구분한다.
   - 기존 위젯의 ID/타입/배치/제목과 사용자가 지정한 변수 키를 보존한다. 결과 항목을 유일하게 해석할 수 있는 연결만 새 바인딩으로 이관한다. 전용 위젯의 기존 동작은 legacy adapter로 유지하고 명시적 신규 연결부터 이름 추측/무관한 결과 fallback을 제거한다.
6. 처음에는 신규 기능을 비활성 상태로 배포할 수 있다. 단, 기능 비활성화는 스키마 gate 우회나 구버전 바이너리 호환의 보장이 아니다.
7. 검증된 저장소부터 명시적으로 활성화한다. 기존 legacy adapter와 새 adapter는 단일 수집 소유권을 갖게 하여 같은 경로를 동시에 처리하지 않는다.

### 8.2 이후 사용자 규칙 변경

화면에서 별칭/연결/포맷/결과 항목/위젯 바인딩/표시 템플릿을 저장하는 것은 지원된 엔진 안의 DB 데이터 변경이다. migration·패키지 설치·인터넷 연결·서버 재시작 없이 처리한다. 엔진이나 위젯이 이해하지 못하는 계약 버전은 비활성 또는 거부 상태로 유지한다.

정의 반입/내보내기는 파일 레시피·결과 항목·표시 템플릿의 의존 버전 목록을 함께 다룬다. 원본 샘플/업무 데이터/자격 증명은 기본 내보내기에 포함하지 않는다. 반입 시 지원 버전·크기·참조·권한·ID 충돌을 검사하고 초안으로 저장한다. 다른 설치의 경로·프로젝트 ID는 자동 연결하지 않고 대상 저장소/업무 객체에 명시적으로 재연결한다. 백업 복구와 설정 패키지 반입은 별개다.

### 8.3 패키지·라이브러리

- 기본은 기존 DB와 CSV/JSON 도구를 사용한다. 별도 그래프 서버나 외부 AI API를 필수로 추가하지 않는다.
- JSON Schema 검증/단위 변환 등에 오픈소스를 도입할 경우 현재 lock과 실제 지원 범위를 조사하고 선정한다. 이 문서만으로 특정 신규 패키지를 채택했다고 간주하지 않는다.
- 신규 패키지는 Windows x64 wheel·고정 버전·라이선스·오프라인 설치/import 검사를 함께 제공한다. 대상 서버에서 다운로드하지 않는다.
- 웹 편집기는 기존 정적 frontend build에 포함한다. 별도 Vite/Node 서비스가 필요하지 않게 한다.
- 샘플·사용자 정의·결과 항목·위젯 바인딩·표시 템플릿은 영구 상태로 보존한다. 릴리스 소스에 저장하지 않으며 개발 PC의 실데이터를 패키지에 넣지 않는다.
- Windows 서비스 계정이 실제 UNC 공유에 접근할 수 있는지 별도 확인한다. 개발자의 로그인 세션 드라이브 매핑을 전제하지 않는다.
- 기존 Windows canonical Master Refresh의 POSIX snapshot 제한은 유지한다. SPDM/의미 연결 지원을 그 제한 해소로 표현하지 않는다.

### 8.4 복구

- 기능 중지는 새 수집만 막고 기존 연결·프로필·결과는 보존한다.
- 구버전 앱이 새 DB revision을 받아들이는지는 기존 gate와 실제 호환 검증으로 판단한다. 이전 실행 파일만 돌려 복구 완료로 표시하지 않는다.
- DB 및 관리형 파일의 일관된 백업 복원과 앱 복구는 기존 배포 복구 절차를 사용한다. 기능을 위해 자동 schema downgrade/drop을 추가하지 않는다.
- 설치/업데이트 실패 주입 시 계정·인증 키·원본·매핑 이력을 보존하고 복구 필요 상태를 유지한다.

API DTO, 오류 코드, revision/권한 규칙을 먼저 합의한 후 기능별 구현을 분리한다. 에이전트는 담당 경로만 수정하고 공통 라우터·migration 통합은 지휘자가 조정한다. 문서와 필요한 코드/테스트만 읽으며 다른 작업의 큰 로그나 산출물을 일괄 로드하지 않는다.

단위/통합 검사는 임시 DB·샘플 저장소에서 실행한다. 프런트엔드는 실제 브라우저로 대표 등록·재연결·충돌 처리와 정적 빌드를 검사한다. 운영 DB나 실행 중 서비스를 시험 대상으로 사용하지 않는다. 모의 설치·개발 PC 검사·실제 Server 2022 실기 검증을 별도로 기록한다.

## 11. 구현 전 확정할 세부 사항

아래는 이번 문서 작성을 막는 질문이 아니라 다음 구현 단계에서 샘플/현재 정책을 확인할 항목이다.

- 최초 도입할 대표 CSV/JSON 샘플과 기준 측정량·단위 목록. 준비 전에는 합성 fixture로 엔진 계약을 검증한다.
- 관리형 원본의 현재 저장 추상화와 백업 포함 증거, 보존 기간/용량. 별도 영구 디렉터리를 임의 추가하지 않는다.
- 실제 공유 폴더의 읽기/쓰기 권한과 서비스 계정 접근. 기본은 DB 연결, 메타데이터 쓰기는 선택 기능이다.
- 새 테이블의 PostgreSQL/DuckDB 지원 방식과 최신 migration head. 기존 두 profile 계약을 깨지 않도록 검증한다.
- 기존 import schema의 실제 호출자·활성 사용량, schema_id/버전 호환. 기존 형식 의미를 조용히 바꾸지 않는다.
- 기존 위젯별 실제 입력 계약, variable_key/variableId 전달 경로, 이름 필터/fallback, 동일 타입 중복 제한과 저장 배치 호환. 순수 범용 위젯과 전용 평가 위젯을 구분해 지원 목록을 확정한다.
- 기존 결과 조회의 Run 선택·grain·scalar/curve/media 출처, 표/산점도의 대응 키와 허용 집계. 위젯에서 데이터 해석 규칙을 임의 추정하지 않는다.
- 저장된 결과 뷰의 현재 구현 여부와 정적 렌더러 버전 호환. 의미/표시 재현과 픽셀 단위 동일 화면 보장은 구분하고 후자를 자동 보장한다고 표현하지 않는다.

## 12. 이번 작업의 확인 기록

### 12.1 최초 계획 작성

- 배포 정책, ADR 0005, 배포 시나리오, 시작 schema gate 및 현재 SPDM/import schema 코드를 읽기 전용으로 확인했다.
- 같은 작업 폴더에서 진행 중인 배포 작업의 상태를 확인했다. 해당 작업을 중단하거나 코드를 수정하도록 메시지를 보내지 않았다.
- Sol이 배포 충돌 근거 및 본 문서를 독립 검수했다. 중대 누락은 발견하지 않았으며 단일 Alembic head, app-role CRUD/catalog 확인, 기존 source 멱등 키와의 호환 명세 요구를 반영했다.
- 문서의 상대 링크 대상, 12개 본문 절, 문서 지도와 작업 기록 등록을 확인했다. 수정 문서의 `git diff --check`를 통과했다. 미추적 새 문서는 별도 파일 내용 검사 대상으로 확인했다.
- 구현/DB migration/배포/서비스 조작은 수행하지 않았다. 실행 코드 변경이 없는 문서 작업이므로 기능 테스트·실제 패키지 설치·Server 2022 검증은 수행하지 않았다.

### 12.2 읽기 레시피·결과 항목·위젯 연결 확장

- 후속 사용자 요청과 제안 기능 전체를 반영했다. 5.5~5.9절에 결과 항목/grain, 확장자+내용 판별, 위젯 입력 역할, 관리자 통합 흐름, 기능 추적표와 선택 확장을 추가했다.
- 저장/권한/버전, 모듈·데이터·API, 배포/백업/legacy 이관, 단계별 담당, 수락 시나리오를 같은 범위로 갱신했다. 제안 기능을 설명에만 두지 않고 실행 단계와 검증 항목에 연결했다.
- 초기 개발에 포함할 기능과 AI 초안·파생 연산·다중 파일 Run 묶음의 후속 범위를 구분했다. 신규 기능과 배포 정책의 구현 보류 상태는 유지한다.
- Sol이 완성본을 읽기 전용으로 독립 검수해 중대 누락이나 내부 충돌을 발견하지 않았다. 다중 파일 원본 조인의 후속 범위 구분, 표시 변경과 적재의 분리, 기존 배포 계약 유지를 확인했다.
- 상대 링크 대상, 추가 절/실행 단계/수락 항목의 필수 내용, 후행 공백 및 `git diff --check`를 확인했다. 문서만 변경하여 앱 기능 테스트·DB migration·실제 배포 검증은 수행하지 않았다.

### 12.3 배포 개발 완료 후 기본 흐름 구현과 검증

최신 사용자 요청으로 구현 보류를 해제했다. 완료된 배포 변경을 포함한 소스 사본에서 Astra가 설계·통합, Terra가 저장/API, Luna가 관리자 화면 초안, Sol이 배포·무결성·화면 검수를 담당했다. 사용자 상태를 복사하거나 실제 DB·서비스에 적용하지 않고, 기준 파일 해시를 대조하여 기능 소스만 통합한다.

| 범위 | 이번 상태 |
|---|---|
| 임의 폴더→기준 업무 대상 | 프로젝트/의뢰/하중 경우/입력/결과 역할과 실제 대상 ID를 명시적으로 연결한다. 올바른 소속의 부모/자식 연결, 경로 재연결 revision, SPDM과 상호 배타적인 경로 소유권을 검사한다. |
| 샘플→레시피→항목 | CSV/JSON 샘플 검사, 필드 경로·단위·측정 차원·결측·집계·곡선 축 설정, 버전 저장과 재사용을 구현했다. 서로 다른 포맷을 동일 항목 ID에 매핑할 수 있다. |
| 항목→위젯 | 카드·게이지·표·막대·선·산점도 입력과 표시 단위·필터·자릿수를 관리자가 정의한다. 샘플을 읽은 실제 위젯으로 검증하고 레시피/템플릿을 원자적으로 활성화한다. |
| 폴더 수집과 결과 | 확장자와 실제 파싱으로 단일 레시피를 판별한다. 미매핑/다중 일치/오류는 파일별로 표시한다. 재시도와 이름만 바뀐 동일 파일은 같은 Run, 변경 내용은 새 Run으로 보존한다. |
| 버전·운영 보호 | 과거 실행의 항목/레시피/템플릿 스냅샷, 원본 해시, 활성 포인터 동시성, 관리자 권한과 입력 크기 제한, 최신 정의의 초안 반입/내보내기를 구현했다. 결과 조회는 선택 Run과 응답을 격리한다. |
| 배포 호환 | `0023_voc_posts` 다음 단일 head `0024_semantic_mapping`, 기존 앱 역할 CRUD/DDL 분리, 앱 시작 시 읽기 전용 schema gate를 유지한다. 새 런타임 의존성·영구 파일 경로·배포 진입점은 없다. |
| 아직 구현하지 않은 초기 계획 항목 | 범용 개념/별칭 사전 편집기와 범위별 규칙 상속, 자동 후보 검토함, 정의 변경 영향 분석 UI, 이동/복제 자동 식별과 복잡한 다중 루트 상속, 사용자별 저장 뷰의 전면 이관은 후속이다. 현재 명시적 폴더 연결을 완전한 온톨로지 추론 엔진으로 표현하지 않는다. |
| 선택 확장·실기 | AI 초안·파생 연산·여러 파일 Run 조인·새 미디어 파서는 후속이다. 새 설치 패키지 제작/반입 및 깨끗한 폐쇄망 Server 2022 VM의 설치·업데이트·재부팅 검증은 이번 기능 소스 작업에 포함하지 않았다. |

검증 기록:

- 새 엔진/API/활성화/SPDM 경로 소유권 검사 46개와 기존 ingestion 경계/멱등성 검사 12개를 통과했다. 생성 OpenAPI의 Windows 줄바꿈 차이를 수정하여 같은 계약 바이트가 생성되도록 했다.
- 배포·프로필·미디어 백업·스키마 시작 검사·계정 준비·Windows 접근·PostgreSQL 이전 관련 검사 206개 통과, 실행 조건이 없는 5개 건너뜀. 해당 결과를 전체 저장소 테스트 통과로 표현하지 않는다.
- 폐기 가능한 PostgreSQL 클러스터에서 신규 설치, 데이터가 있는 0023→0024 업그레이드, 반복 migration, 기본/사용자 지정 앱 역할 CRUD·DDL 차단 및 경로 소유권 잠금, dump/restore 후 항목·버전·샘플·provenance·기존 프로젝트 보존을 확인했다. Alembic head는 하나다.
- 브라우저에서 실제 관리자 샘플 정의/저장/활성화/등록/선택 Run 조회, 조회 전용 계정의 설정 변경 차단, 예제 6종 위젯 표시를 확인했다. 관리자 결과 선택을 바꿀 때 늦은 응답이 다른 대상에 표시되는 문제를 수정하고 회귀 시나리오를 추가했다.
- 프런트엔드 아키텍처 검사, TypeScript, 정적 빌드를 통과했다. 격리 사본의 의존성 junction 때문에 Vite는 검사 시 `--configLoader runner`를 사용했으며 실제 배포 실행기를 변경하지 않았다.
- 확대 검사 중 기존 Windows POSIX 권한 전제 및 viewer 로그인 fixture의 실패가 있었다. 실제 비밀번호 로그인 권한 검사는 별도 브라우저 검사로 확인했다. 기존 문제를 새 기능 통과 수에 포함하거나 해결된 것으로 기록하지 않는다.

관리자 사용 순서와 정확한 지원 한도는 [사용 안내](semantic-mapping-guide.md), 재현 샘플은 [예제](../examples/semantic-mapping/README.md)에 있다. 기존 오프라인 EXE에는 이 소스 변경이 포함되지 않으므로 다음 릴리스는 기존 배포 정책대로 새로 빌드해야 한다.

### 12.4 기준 정의·별칭 관리 확장 (2026-09-15)

사용자가 남은 작업 중 1번을 구현하도록 요청했다. 12.3절의 당시 미구현 목록 중 기준 정의·별칭 관리와 기존 폴더/필드 편집에서의 재사용을 이번 변경으로 구현한다. 규칙 검토함·영향 분석·자동 이동 추적·AI·파생 연산·다중 파일 조인은 그대로 후속이다.

- 고정 키·표시명·설명·실제 대상 ID·전역/프로젝트 범위·다중 별칭·활성 여부·revision을 별도 사전에 보존한다. 기준 종류는 폴더 역할, 프로젝트, 의뢰, 하중 경우, 결과 항목이다.
- NFKC/casefold/공백 정규화 후 정확 매칭, 종류·범위별 활성 용어 고유 제약, 프로젝트 후보 우선과 전역 fallback, 다른 프로젝트의 실제 대상 제외를 구현한다. 단어가 여러 종류와 일치하면 후보를 구분하여 관리자가 고른다.
- 사전 CRUD와 폴더 이름/원본 필드의 추천 적용을 연결한다. 적용 직전 후보 revision을 다시 확인하며, 검색/비활성화로 기존 레시피·폴더 연결·과거 실행을 자동 수정하지 않는다.
- 0024 다음 additive 0025 migration, 새로운 영구 DB 테이블 두 개, 기존 앱 역할 CRUD 및 읽기 전용 시작 검사를 유지한다. 최신 schema.sql과 migration 제약을 맞춰 신규 설치와 기존 업데이트가 같은 스키마가 되도록 한다. 새 의존성·외부 서비스·영구 파일 경로가 없다.
- Astra 설계/통합, 독립 Terra 백엔드·DB, Luna 프런트 구현, Sol 1차 및 별도 Astra 최종 검수를 적용한다. 검증된 구현 범위와 실제 검사 기록은 [사전 안내](semantic-vocabulary.md)에 기록한다.

### 12.5 다음 단계: 변경 영향 분석·검토함 (2026-09-15)

사용자가 선행 기능을 먼저 푸시한 뒤 다음 단계를 진행하도록 요청했다. 선행 기능은 `133e821`에 커밋했다. 사용자 목적지 승인 후 원격 브랜치의 해시 일치를 확인했다. 후속 기능은 사용자 상태 없는 격리 소스에서 구현·검증했으며, 기존 미커밋 변경을 보존하여 통합했다.

[후속 구현 설계](semantic-review-impact-plan.md)의 폴더별 검토함, 명시적 레시피 선택·재검증·등록·다시 검토, 저장 샘플 기반 영향 미리보기와 활성화 차단을 구현했다. 고정 버전·원본 해시·개정 CAS, 결과/provenance/감사/검토 전이의 원자 저장, 재연결 대상별 이력 분리, 0026 additive migration과 읽기 전용 시작 검사를 적용했다. 기존 정상 파일의 자동 등록과 과거 Run을 유지한다.

최종 검토함 API 15개, 관련 기존 회귀, 실제 API 브라우저 신규 2개·기존 9개, 임시 PostgreSQL 신규/0025 업데이트/동시성/복원, 배포 계약 회귀와 정적 빌드를 검증했다. Sol 1차·독립 Astra 최종 검수 지적을 반영했다. 세부 지원 범위·검증·배포 미실기 구분은 [운영 기능 안내](semantic-review-guide.md)에 기록한다. 프로젝트 전체 통합 검토함·오류 유형 필터, AI 추론·새 포맷 파서·다중 파일 Run 조인은 후속 범위다.
