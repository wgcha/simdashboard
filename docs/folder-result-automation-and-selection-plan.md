# 폴더 확정 후 결과 조회 자동화와 코드·이름 선택 표시

기준일: 2026-09-16. 상태: 구현·격리 환경 통합 검증 완료. 검증 결과는 `log/work-log.md`에 기록한다. 실제 사내 서버 운영 검증은 별도다.

## 1. 목표와 현행 차이

1. 폴더 조사에서 확정한 업무·경로를 재입력하지 않고 결과 조회까지 연결한다.
2. 업무 선택 목록에서 코드와 이름을 함께 보여 동명이거나 코드가 없는 항목도 구분한다.

변경 전에는 `folder_discovery.apply`가 업무와 `folder_discovery_registry`만 저장하고, 읽기 레시피를 사용하는 `semantic_folder_bindings`는 별도 연결 화면에서 생성했다. 이번 구현은 업무 확정과 결과 연결 저장을 함께 처리한다. 폴더에서 추출한 코드도 일반 업무 목록의 `selection_metadata`로 제공하며 설명 문구에서 재파싱하지 않는다.

실제 구현 경계: `backend/app/services/folder_discovery_plan.py`, `backend/app/services/semantic_result_refresh.py`, 폴더 조사/의미 매핑 라우터, `backend/app/domains/selection_metadata.py`, `frontend/src/features/data/FolderDiscoveryWorkspace.tsx`, `frontend/src/features/results/refreshCurrentLoadCaseResults.ts`, `frontend/src/shared/components/selectionLabels.tsx`. 기존 JSON 설정과 연결 테이블을 재사용하며 DB migration·신규 의존성은 없다. 재귀 파일 수집은 이번 범위에 포함하지 않는다.

## 2. 개선 A — 폴더 확정 → 결과 조회 → 위젯 검토

### 사용자 흐름

1. 최상위 폴더 조사와 깊이·키워드·구분자·업무 역할 규칙은 유지한다.
2. 결과 역할 규칙에 **결과 읽기 설정**을 추가한다. 활성 레시피 하나 이상을 선택하고 표시 템플릿은 각 레시피에 저장된 버전을 기본 적용한다. 관리자는 해석 종류별 기본 설정을 저장해 이후 규칙 작성 때 재사용한다.
3. 생성 미리보기에 결과 폴더, 소유 프로젝트/의뢰/하중 경우, 적용 레시피와 템플릿, 설정 출처, 준비 상태를 함께 표시한다. 적용에서 제외한 행은 자동 연결 대상에서도 제외한다.
4. 업무 생성 확정 시 결과 폴더 연결까지 함께 저장한다. 같은 업무·경로를 다시 선택하는 화면으로 이동하지 않는다. 설정 없는 업무도 생성할 수 있으나 결과 상태를 **읽기 설정 필요**로 명확히 표시한다.
5. 생성 완료 목록·저장된 연결 목록·하중 경우 화면의 **결과 조회**가 같은 기능을 호출한다. 파일 확인 → 신규/변경 파일 처리 → 실제 Run 선택 → 연결된 템플릿의 위젯 표시를 한 흐름으로 실행한다.
6. 기존 **폴더 연결**은 **고급 연결 관리**로 남긴다. 개별 재지정·경로 이동·오류 복구가 필요할 때 사용한다.

### 설정 우선순위와 보존

- 기존 개별 수동 설정 > 해당 폴더 규칙의 명시 설정 > 해석 종류 기본 설정 순으로 제안한다. 같은 우선순위에서 다른 설정이 겹치면 충돌을 표시하며 첫 번째 규칙을 임의 선택하지 않는다.
- 기본 설정은 규칙을 작성·확정할 때 적용 내용을 저장한다. 기본 설정을 수정했다고 이미 연결된 폴더가 조용히 변경되지 않도록 영향 미리보기와 명시적 재적용을 제공한다.
- 기존 결과 binding이 동일 대상·경로에 있으면 재사용한다. 관리자가 재정의한 레시피/템플릿은 자동으로 덮어쓰지 않는다. 다른 업무가 소유한 경로는 충돌로 표시한다.
- 확정 응답/적용 이력에 생성·재사용 binding ID와 정책 스냅샷을 저장한다. apply 재시도는 이를 반환하며 binding이나 개정을 중복 생성하지 않는다. 수동 재연결로 registry와 현재 소유자가 어긋났으면 자동 처리하지 않고 충돌로 안내한다.
- 이미 조사·생성된 업무는 저장된 연결 목록에서 결과 읽기 설정을 일괄 적용할 수 있게 한다. 업무 재생성이나 경로 재입력 없이 기존 registry를 이용한다.
- 레시피는 활성 버전으로 읽고, 템플릿은 해당 레시피가 연결한 정확한 게시 버전 또는 명시적 override를 사용한다. 실제 사용 버전은 Run에 기록한다. 초안은 자동 적용하지 않는다.
- 저장한 레시피가 비활성/삭제되거나 필요한 게시 버전이 없으면 다른 설정으로 대체하지 않고 **읽기 설정 재확인**을 표시한다. 자동 연결의 설정 재적용도 현재 개정 확인과 영향 미리보기 후 진행한다.

### 조회·파일·Run 계약

- 자동 처리 대상은 확정된 하중 경우 소속 결과 폴더들이다. 프로젝트·의뢰 수준 결과 폴더는 소유 하중 경우가 정해지기 전까지 가져오지 않는다. INPUT·제외 행·다른 업무의 경로를 흡수하지 않는다.
- 1차 구현은 기존의 결과 폴더 직접 자식 파일 처리 범위를 유지하고, 해당 업무의 확정 결과 폴더를 빠짐없이 순회한다. 전체 트리 조사가 모든 하위 파일의 동일 업무 소유를 뜻하지는 않는다. 미연결 하위 폴더가 있으면 이를 표시한다. 재귀 수집이 필요하면 자식 업무 경계·별도 결과 연결·입력 역할을 제외하는 별도 옵션으로 후속 확장한다.
- 파일마다 확장자와 실제 내용 검증으로 레시피를 판별한다. 하나만 일치하면 처리하고, 0개/여러 개는 이유와 해결 동작을 표시한다. 확장자만 같다고 성공 처리하지 않는다.
- 동일 내용·레시피 버전·표시 설정은 기존 Run을 재사용한다. 내용이나 표시 설정이 달라지면 기존 Run을 보존하고 새 Run을 만든다. 반복 클릭·동시 호출도 중복 등록을 만들지 않는다.
- 여러 파일이 여러 Run을 만들면 파일별 처리 결과와 Run 선택 목록을 제공한다. 기본 화면은 해당 하중 경우의 최신 표시 가능 Run이며, 선택한 파일/Run의 위젯만 보여준다. 서로 다른 파일의 값을 임의로 합쳐 하나의 결과로 표시하지 않는다.
- 처리 POST 응답에서 표시할 `display_run_id`와 파일별 Run ID를 확정하고 화면은 그 ID로 위젯을 조회한다. 처리 후 다시 최신 Run을 찾다가 동시 처리된 다른 결과로 바뀌지 않도록 한다.
- 새 결과가 없으면 기존 결과와 마지막 확인 시점을 표시한다. 파일 없음, 설정 없음, 읽기 실패, 일부 성공을 구분한다. 위젯이 없으면 빈 화면 대신 설정 안내를 제공한다.
- 기존 검토함의 보류·충돌·명시적 등록 절차를 유지한다. 조회 버튼이 관리자의 보류 결정을 해제하지 않는다.
- 결과 조회는 파일 처리 중임을 표시하고 중복 클릭을 제한한다. 일부 파일 실패가 이미 성공한 파일이나 업무 생성 결과를 취소하지 않는다. 중단 후 재시도할 수 있어야 한다.
- 조회 과정에서 데이터 등록이 발생하므로 변경 동작은 POST 서비스로 분리하고 가져오기 권한을 검사한다. 조회 전용 사용자는 저장된 결과만 조회하며 자동 등록을 수행하지 않는다. 일반 결과 GET에 쓰기 동작을 넣지 않는다.
- 기존 의뢰 대시보드 구성은 보존한다. 레시피 위젯은 기존 공통 결과 패널을 사용하며 관리자 편집 위치는 표시 템플릿으로 일원화한다.
- 자동 연결·정책 재적용·파일 처리는 경로, 업무/연결 ID, 개정, 실제 레시피·템플릿 버전과 Run ID를 감사 기록에 남긴다. 파일별 성공·보류·실패 목록은 경로 기준의 안정된 순서로 반환한다.

### 구현 경계

- 백엔드: folder discovery 규칙/미리보기/확정 계약 확장, 결과 정책 해석 서비스, 자동 binding 생성/재사용, 업무별 결과 갱신 서비스.
- 기존 `semantic_mapping` 읽기·중복 방지·provenance와 `semantic_review`를 재사용한다. 라우터 간 직접 호출 대신 공통 서비스 경계로 필요한 기능을 분리한다.
- 업무/자동 연결 저장은 같은 트랜잭션으로 처리하되 파일 파싱·결과 생성은 업무 확정 이후 실행한다. 장시간 파일 처리를 업무 생성 잠금 안에서 수행하지 않는다.
- 프런트엔드: 조사 규칙의 결과 설정, 미리보기의 적용 정보, 기존 연결 일괄 설정, 공통 결과 조회 동작과 처리 요약/파일·Run 선택.
- 기존 규칙 JSON을 우선 확장하고 새 키 없는 구형 규칙은 미설정으로 해석한다. 정책 출처·재정의 여부 등 영구 데이터에 스키마 확장이 필요하면 정상 migration으로 처리하며 임시 파일이나 브라우저 저장만으로 대체하지 않는다.

## 3. 개선 B — 코드와 이름을 함께 표시하는 공통 선택 목록

### 표시·검색 규칙

| 데이터 | 기본 표시 |
|---|---|
| 코드와 이름 있음 | `REQ-2026-015 · 낙하 시험` |
| 코드 없음 | `낙하 시험` |
| 코드와 이름이 같음 | 동일 문자열을 한 번만 표시 |
| 같은 표시가 여러 개 | 상위 업무·해석 종류 추가, 그래도 같으면 상대 경로 추가 |

- 프로젝트는 코드·이름, 의뢰는 코드·이름과 필요한 상위 프로젝트, 하중 경우는 코드·이름과 필요한 상위 의뢰/해석 종류를 표시한다.
- 코드의 선행 0과 원문을 보존한다. 코드가 없는 업무에 가짜 업무 코드를 만들지 않는다.
- 경로도 없는 기존 수동 업무가 여전히 중복되면 내부 ID의 짧은 식별 표시를 보조 정보로 사용하되 충돌 시 길이를 늘려 실제 선택 목록에서 구분되게 한다.
- option value, API 요청, URL 및 저장 연결에는 항상 실제 내부 ID를 사용한다. 표시 문자열은 업무 식별자가 아니다.
- 코드·이름·표시된 상위 정보·경로로 검색할 수 있게 한다. 일치 항목을 자동 선택하거나 동명 업무를 병합하지 않는다. 긴 텍스트는 펼침/보조 정보로 확인할 수 있어야 한다.

### 데이터·적용 범위

- 공통 업무 선택 응답에 `id`, 업무 코드, 현재 이름, 부모 문맥, 해석 종류 및 필요한 경로 정보를 제공한다. 폴더 유래 코드는 registry와 target ID의 관계로 조회하고, 이름은 현재 업무 데이터를 사용한다.
- 여러 registry 행이 같은 대상을 가리킬 때 업무 행을 중복 생성하지 않는다. 업무 생성 역할의 코드를 우선하고 결과/입력 폴더 이름을 업무 코드로 잘못 쓰지 않는다.
- 코드 메타데이터는 권한 필터가 적용된 업무 조회에서 제공한다. 코드 표시를 위해 일반 조회자에게 관리자용 폴더 조사 API 권한을 주거나 다른 프로젝트 경로를 노출하지 않는다.
- 공통 표시 함수와 선택 컴포넌트를 만들어 폴더 조사/연결, 프로젝트·의뢰·하중 경우 선택, 작업대 문맥 선택, 결과 조회/검토의 관련 선택 목록에 적용한다. 새 목록도 같은 계약을 사용하도록 검증한다.
- 기존 수동 업무는 코드가 없어도 그대로 조회·선택되어야 한다. 과거 업무를 자동 재명명하지 않는다.

## 4. 개발 순서와 완료 기준

1. 공통 업무 코드 응답·선택 표시를 먼저 구현하여 이후 자동 연결의 대상 식별 기반을 마련한다.
2. 결과 읽기 정책과 미리보기, 업무 확정 시 자동 연결, 기존 연결 일괄 설정을 구현한다.
3. 공통 결과 조회 서비스와 파일별 상태·Run 선택·위젯 이동을 연결한다.
4. 기존 데이터 회귀·브라우저 실사용·독립 검수를 마치고 사용 가이드를 실제 화면 기준으로 갱신한다.

필수 검증:

- 새 폴더와 이미 등록된 폴더 모두 경로 재입력 없이 결과 조회까지 이어진다.
- 동일 이름/코드, 코드 없음, 선행 0, 동일 해석 종류, 중복 경로 표시에 대해 선택한 내부 ID와 실제 처리 대상이 일치한다.
- 레시피 0/1/복수 일치, 템플릿 미설정/초안/게시 버전, 예제 CSV/JSON의 벡터·값 없음과 실제 위젯 표시를 확인한다.
- 중복 클릭·동시 등록·일부 실패·기존 수동 override·KEEP·EXCLUDED·검토함 보류·과거 Run 재현을 확인한다.
- 결과 폴더 여러 개와 다른 업무 하위 경계, 기존 SPDM 경로 소유권, 접근 권한과 읽기 전용 사용자 동작을 확인한다.
- API/OpenAPI, 관련 backend tests, frontend build, 실제 브라우저와 모바일·키보드 선택 동작을 검증한다. 운영 DB·설정·실행 서비스를 테스트하지 않는다.

## 5. 배포·협업

`deploy.bat`, `update.bat`, Windows 오프라인 패키지 및 데이터 보존 정책을 유지한다. 신규 의존성 없이 기존 라이브러리와 컴포넌트를 우선 재사용한다. migration이 필요하면 기존 데이터가 있는 업데이트와 빈 설치 모두 검증하고 앱 시작 시 migration을 실행하지 않는다.

Astra가 설계·통합, Terra가 백엔드/영구 데이터, Luna가 화면/공통 선택 표시를 담당하고 Sol 1차·Astra 최종 검수로 진행한다. 구현 완료와 실제 Server 2022 운영 검증은 구분해 기록한다.
