## 목적과 현재 차이

선행 구현의 폴더 새로고침은 파일의 확장자와 실제 내용을 검사하고, 레시피가 하나만 맞으면 결과를 등록했다. 미인식·다중 일치·읽기/검증 오류는 응답에만 남았다. 레시피/템플릿 활성화는 저장 샘플의 위젯 호환성과 동시 수정 여부를 검사했지만, 다른 폴더·위젯에 대한 영향 목록은 제공하지 않았다.

이 단계에서는 해결하지 못한 파일을 나중에도 다시 확인할 수 있도록 저장하고, 관리자가 레시피를 선택해 재검증한 후 명시적으로 등록한다. 정의를 활성화하기 전에는 영향을 받는 참조와 검증 범위를 보여준다.

## 유지할 동작

- 기존 새로고침의 단일 레시피 일치 시 등록 동작과 단일 파일 업로드를 유지한다. 새로고침 전체를 묵시적으로 수동 승인 방식으로 바꾸지 않는다.
- 여러 레시피가 맞으면 첫 레시피를 임의로 선택하지 않는다. 별칭은 후보 선택을 도울 뿐 파싱·단위·위젯 검증을 대체하지 않는다.
- 기존 Run과 항목·레시피·템플릿 스냅샷은 변경하지 않는다. 동일 원본 해시와 동일 레시피 버전의 재시도는 기존 Run을 재사용한다.
- 표시 제목·색상·자릿수·레이아웃 변경만으로 새 Run을 만들지 않는다.
- 실제 사용자 DB·설정·서비스는 개발·검증에 사용하지 않는다.

## 변경 영향 분석

저장된 레시피/템플릿의 후보 버전과 현재 활성 버전을 비교한다. 아직 저장하지 않은 화면 편집 내용과 저장된 버전을 혼동하지 않도록 저장을 먼저 요구한다.

| 보고 항목 | 내용 |
|---|---|
| 정의 변경 | 원본 필드·해석·단위·출력 항목 변경과 표시 변경을 구분한다. 판단할 수 없는 변경은 수동 검토 대상으로 표시한다. |
| 폴더 참조 | 해당 정의를 사용하는 폴더, 대상 프로젝트/의뢰/하중 경우, 바인딩 개정 |
| 위젯 참조 | 연결된 템플릿 버전과 위젯, 필요한 항목·단위·측정 차원, 누락/비호환 이유 |
| 검토 중인 파일 | 선택/검증 시 고정된 정의 버전을 사용 중이거나 영향을 받는 바인딩의 대기 항목 수. 개별 목록은 폴더 검토함에서 조회한다. |
| 과거 결과 | 참조 Run 수와 조회 가능한 목록. 과거 결과가 자동으로 변경되지 않음을 표시한다. |
| 검증 범위 | 저장된 샘플로 검증한 조합, 샘플 없음/오류/미검증 조합, 목록 한도와 잘림 여부 |

영향 조회는 DB의 저장 정의·샘플·참조를 읽는다. 전체 저장소를 스캔하거나 활성화·재적재·검토함 상태 변경을 수행하지 않는다. 원본 파일 전체를 검증한 것으로 표시하지 않는다.

활성화 시 현재 원자적 레시피/템플릿 검증을 유지한다. 새 레시피로 영향을 받는 다른 활성 템플릿의 명백한 입력 비호환도 검사한다. 조회 후 정의 포인터나 바인딩이 바뀌었다면 서버에서 재검증 또는 충돌 응답을 반환하며, 브라우저의 이전 미리보기만 신뢰하지 않는다. 현재 활성 폴더에 연결된 조합의 샘플 누락·검증 실패·검사 한도 초과는 활성화를 차단한다. 과거 Run과 사용하지 않는 정의는 참고 정보이며 기존 결과를 변경하지 않는다.

## 검토함과 처리 순서

1. 기존 새로고침 중 `UNMAPPED`, `AMBIGUOUS`, `INVALID`, 재시도 가능한 `PENDING`을 파일별 검토 항목으로 저장한다. 파일마다 실패 이유와 맞는 레시피 후보의 불변 버전을 기록한다.
2. 관리자는 폴더별 검토함에서 상태를 필터링하고 항목 상세에서 원본 경로, 대상 업무, 판별 이유와 후보를 확인한다. 프로젝트 전체 통합 조회·오류 유형 필터는 후속 확장으로 남긴다.
3. 레시피를 수정·활성화한 경우 파일을 다시 판별한다. 과거 후보 목록에 없는 신규 레시피도 현재 폴더 설정에 포함되면 내용 검증을 거쳐 선택할 수 있다.
4. 선택한 레시피·템플릿 버전, 파일 해시, 바인딩 개정을 고정하고 재검증한다. 파싱 결과와 위젯을 미리 보여준다. 이 단계는 Run을 만들지 않는다.
5. 검증 완료 항목에서 명시적으로 등록한다. 서버가 권한·원본·경로·고정 버전·개정을 다시 검사하고 결과와 처리 이력을 함께 저장한다.
6. 파일 내용 또는 폴더 연결이 바뀌면 이전 검증을 만료시키고 재판별을 요구한다. 중복 클릭·재시도·동시 확정은 Run 중복이나 검토 상태 불일치를 만들지 않는다.
7. 처리 완료 항목은 레시피 활성 버전 변경만으로 다시 열리지 않는다. 관리자가 `다시 검토`를 명시적으로 실행한 뒤 선택 버전으로 재검증·등록하며, 과거 Run과 전이 이력을 보존한다.

검색 목록은 페이지 단위로 조회한다. 현재 새로고침의 디렉터리 항목 5,000개, 대상 파일 500개, 파일당 5 MiB, 합계 128 MiB 한도를 유지한다. 한도 초과·부분 완료를 화면에 명확히 표시한다. 검토함에는 원본 전체를 중복 저장하지 않으며, 원본 삭제 후 재처리를 보장하지 않는다.

## 데이터와 API 계약

다음 계약은 Terra/Luna 인터페이스 협의로 확정했으며 생성 OpenAPI와 함께 관리한다.

- 추가 테이블 `semantic_import_review_items`: 항목 ID, 바인딩 ID·개정, 대상 하중 경우, 정규화된 상대 경로, 원본 해시·크기, 판별 상태, 검토 상태, 후보 버전 목록, 선택/검증 버전, 검증 해시, 오류, 개정, 처리자·시간, 확정 Run ID.
- 추가 테이블 `semantic_import_review_events`: 항목별 이전/이후 상태, 개정, 이전/현재 Run, 상세 원인, 처리자와 시간의 append-only 이력.
- 항목 유일 키는 `(binding_id, load_case_id, relative_path)`다. 폴더의 대상을 재연결하면 새 대상 항목을 분리하고 과거 대상의 항목·이력·Run 링크를 다시 이름 붙이지 않는다. 목록은 현재 대상만 보여주며 과거 항목 직접 조회는 관련 대상 권한을 모두 확인한다.
- 판별 상태와 검토 상태를 분리한다. 검토 상태는 미처리/검증 가능/검증 만료/등록 완료/중복 재사용을 구분한다. 동일 파일의 반복 탐색은 무한히 새 항목을 만들지 않는다.
- 과거 처리 이력과 새로운 파일 내용을 구별한다. 검토 항목을 갱신할 때 감사 이력을 남기고 이전 확정 Run 연결을 소실시키지 않는다. 다른 레시피 버전으로 재처리하면 이전 실행 관계도 기록한다.
- 영향 조회: `POST /api/semantic-mapping/impact-bundle`에 기존 묶음 활성화와 같은 저장된 레시피/템플릿 ID·버전·예상 활성 버전을 지정한다. 서버 상태를 변경하지 않는 조회다.
- 검토 목록/상세: 폴더의 현재 하중 경우 범위에서 상태별 페이지 조회. 조회 전에 접근 권한을 서버에서 적용한다.
- 선택/재검증/확정: 검토 항목별 명령과 `expected_revision`. 선택 직후 자동 저장·자동 import를 수행하지 않는다.
- 정의 영향 조회·변경은 기존 카탈로그 관리자 권한, 파일 검토·확정은 해당 하중 경우의 결과 등록 권한을 적용한다. 화면에서 숨기는 것만으로 권한을 대신하지 않는다.

현재 `persist_semantic_import`는 자체 트랜잭션을 시작한다. 기존 호출 계약은 유지하면서 내부 저장 함수를 분리하여 검토 확정의 행 잠금·CAS·결과 저장·provenance·검토 상태·감사 기록을 하나의 트랜잭션으로 묶는다. 현재 활성 포인터를 다시 읽는 `_import`를 검토 확정에 그대로 재사용하지 않는다.

경로는 서버의 허용 루트와 저장된 바인딩으로 계산한다. 클라이언트의 절대 경로나 임의 파일 경로를 받지 않는다. 기존 SPDM의 경로 이탈·재분석 지점·안정 읽기 검사를 재사용한다.

## 개발 분담과 검증

| 역할 | 담당 |
|---|---|
| Astra 지휘·설계 | 범위·상태 전이·API 계약 확정, 격리 소스 준비, 문서·통합 |
| Terra 백엔드·DB | 영향 분석 서비스, 검토함 저장/API, 원자적 확정, migration과 서버 테스트 |
| Luna 프런트엔드 | 영향 패널, 검토함 목록/상세, 재검증·명시적 등록, 문맥 변경 시 늦은 응답 차단 |
| 독립 Sol 1차 검수 | 무결성·권한·동시성·배포 계약과 사용자 흐름 검수 |
| 독립 Astra 최종 검수 | Sol 지적 수정 및 실제 검증 증거 확인 |

필수 검증은 미인식→규칙 수정→재판별→등록, 다중 일치 명시 선택, 스키마/단위 오류, 검증 후 원본 변경·삭제·잠김, 폴더 재연결, 동시 확정, 감사 실패 rollback, 권한 없는 조회/실행, 반복 새로고침, 기존 Run 보존, 표시 변경 무재적재, 다른 활성 템플릿 비호환, 늦은 UI 응답이다.

PostgreSQL은 `0025_semantic_vocabulary` 다음 additive `0026_semantic_import_review` migration을 적용한다. 신규 설치의 최신 스키마와 기존 데이터가 있는 0025 업데이트의 컬럼·CHECK·FK·인덱스가 같아야 한다. 기본/사용자 지정 앱 역할 CRUD와 DDL 차단, 반복 migration, 백업/복원, 읽기 전용 시작 schema gate를 검증한다.

새 런타임 의존성·외부 서비스·영구 파일 경로는 추가하지 않는다. `deploy.bat`, `update.bat`, 폐쇄망 패키지 흐름과 상태 보존 계약을 유지한다. 정적 빌드·OpenAPI·관련 배포 계약 검사를 수행한다. 실제 폐쇄망 Server 2022 신규 설치·업데이트·재부팅을 수행하지 않았다면 별도 미검증으로 기록한다.

## 후속 범위

AI 의미 추론, 이동/복제 자동 추적, 다중 파일의 한 Run 묶음, 새 포맷 파서, 일반 파생 연산 엔진은 이 단계에 섞지 않는다. 기존 전체 계획의 후속 항목으로 유지한다.
