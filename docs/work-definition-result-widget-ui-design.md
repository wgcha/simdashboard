## 1. 결론

상세분석 화면은 모든 의뢰에서 열 수 있어야 하지만, 업무 유형과 무관한 분석 위젯을 임의로 표시해서는 안 된다. 특히 단계 진행만 정의된 레거시 의뢰에 `Open Cell 평가 분석`과 Open Cell 위젯을 기본으로 노출하는 것은 업무 의미가 맞지 않는다.

권고 구조는 다음과 같다.

```text
관리자 위젯 카탈로그
  → 분석 템플릿 버전과 기본 레이아웃 관리
  → 업무 유형 버전에서 원하는 결과 템플릿·위젯 선택
  → 의뢰 생성 시 결과 화면 구성을 변경 불가 snapshot으로 저장
  → 상세분석에서 snapshot에 정의된 페이지·위젯 렌더링
  → 결과가 없으면 화면 오류 대신 위젯별 대기 상태 표시
```

관리자는 모든 의뢰의 대시보드를 건별로 직접 배치하지 않는다. 관리자는 재사용 가능한 위젯과 분석 템플릿을 관리하고, 업무정의 작성자는 해당 업무에서 기대하는 결과 위젯을 선택한다. 실제 의뢰는 생성 당시의 결과 화면 구성을 보존한다.

## 2. 문제 정의

현재 의뢰 진행 화면과 상세분석 화면 사이에는 다음 의미 충돌이 있다.

- `레거시 단계 의뢰`처럼 실행 단계만 있고 해석 결과 유형이 없는 의뢰도 존재한다.
- 하중 경우와 결과가 없더라도 상세분석 진입 자체는 가능해야 한다.
- 결과가 없다는 이유로 전체 오류 페이지를 표시하면 사용자는 의뢰가 잘못 생성된 것으로 오해한다.
- 업무 유형이 Open Cell이 아닌데 Open Cell 전용 제목과 위젯을 표시하면 결과의 의미를 잘못 전달한다.
- 관리자가 상세분석 페이지를 편집할 수 있어도 어떤 업무에서 어떤 페이지를 사용해야 하는지가 업무정의와 연결되어 있지 않다.
- 업무 유형이 나중에 바뀌어도 이미 생성된 의뢰의 결과 화면은 재현 가능해야 한다.

따라서 `업무 진행 단계`, `기대 결과 구성`, `실제 결과 데이터`를 서로 다른 개념으로 분리해야 한다.

| 개념 | 책임 | 변경 시점 |
|---|---|---|
| 작업계획 | 어떤 세부 작업을 어떤 순서로 수행하는가 | 업무 유형 버전 저장 시 |
| 결과 화면 구성 | 완료 과정에서 어떤 결과를 어떤 위젯으로 확인하는가 | 업무 유형 버전 저장 시 |
| 결과 데이터 | 실행 후 생성된 수치·표·미디어·판정 | 실행/수집 시 |
| 의뢰 snapshot | 해당 의뢰가 참조하는 작업계획과 결과 화면 구성 | 의뢰 생성 시 고정 |

## 3. 제품 원칙

### 3.1 상세분석은 항상 열리되 업무 의미를 추측하지 않는다

- 하중 경우, 실행, 결과 데이터가 없어도 `상세 분석 열기`는 사용할 수 있다.
- 업무 유형에 결과 템플릿이 지정되었으면 해당 템플릿의 위젯을 대기 상태로 먼저 표시한다.
- 결과 템플릿이 없는 레거시 의뢰는 중립적인 `상세 분석` 빈 캔버스를 표시한다.
- Open Cell, Chassis, DOE 등 도메인 명칭은 선택된 분석 템플릿에 포함된 경우에만 노출한다.
- 데이터 미존재는 페이지 오류가 아니라 정상적인 업무 상태다.

### 3.2 업무정의가 기대 결과를 선언한다

- 업무 유형의 불변 버전에 `결과 구성` 단계를 추가한다.
- 업무정의 작성자는 분석 템플릿을 선택하고, 허용된 범위에서 페이지와 위젯을 포함·제외하거나 순서를 조정한다.
- 선택한 위젯이 요구하는 데이터와 작업계획이 산출하는 데이터를 저장 전에 비교한다.
- 의뢰 접수자는 선택한 업무 유형의 작업 단계와 기대 결과를 읽기 전용으로 미리 확인한다.

### 3.3 관리자는 재사용 기반을 관리한다

- 시스템 관리자는 `/workspace/admin/work-types`의 `WorkbenchTypeAdmin`에서 시스템 업무 유형 버전과 시스템 기본 결과 프로필을 함께 관리한다.
- 프로젝트 관리자는 시스템 업무 유형을 수정하지 않고 `/workspace/project/result-layouts`의 `ProjectResultProfileBinding`에서 선택한 프로젝트의 결과 프로필 override를 업무 유형 버전에 연결한다.
- 분석 템플릿 버전 저장 API와 템플릿 선택 UI는 구현되어 있으나, 프로젝트/시스템 템플릿의 전체 authoring·drag-resize UI는 후속 범위다.
- 관리자 권한이 있더라도 일반 의뢰의 레이아웃을 조용히 덮어쓰지 않는다.
- 레거시 의뢰에 템플릿을 사후 지정해야 한다면 명시적 `결과 구성 지정` 동작과 감사 이력을 남긴다.

### 3.4 의뢰 생성 시점의 구성을 보존한다

- 업무 유형의 새 버전이나 분석 템플릿의 새 버전은 기존 의뢰에 자동 적용하지 않는다.
- 의뢰 생성 시 템플릿 ID/버전, 페이지, 위젯, 배치, 설정, 데이터 바인딩을 snapshot으로 저장한다.
- snapshot이 없는 기존 의뢰는 자동 추정하지 않고 `미지정` 상태로 마이그레이션한다.

## 5. 핵심 사용자 시나리오

### 5.1 시스템 관리자가 업무 유형과 기본 결과 프로필을 정의한다

1. `/workspace/admin/work-types`에서 기본 정보와 세부 작업 순서를 구성한다.
2. `결과 구성` 단계에서 분석 템플릿을 선택한다.
3. 템플릿이 제공하는 페이지와 위젯을 미리 본다.
4. 업무에 불필요한 선택 위젯은 제외하고 필수 위젯은 유지한다.
5. 현재 MVP에서는 필수 위젯을 유지하면서 선택 위젯을 포함·제외한다. 위젯 이동·크기 변경 authoring은 후속이다.
6. 데이터 요구 조건 검사를 확인한다.
7. 작업계획과 결과 구성을 하나의 업무 유형 새 버전으로 저장한다.

### 5.1.1 프로젝트 관리자가 결과 프로필 override를 지정한다

1. `/workspace/project/result-layouts`에서 시스템 업무 유형과 버전을 선택한다.
2. 해당 프로젝트에서 사용할 템플릿 버전과 포함 위젯을 선택한다.
3. `ProjectResultProfileBinding`이 프로젝트 ID·업무 유형 ID·업무 유형 버전을 키로 override를 새 버전 저장한다.
4. 시스템 업무 유형과 기본 결과 프로필은 변경하지 않으며, 저장된 override는 새 의뢰의 snapshot부터 적용한다.

### 5.2 의뢰자가 업무 유형을 선택한다

1. `의뢰 접수`에서 업무 유형을 선택한다.
2. 작업 단계 옆의 `기대 결과` 미리보기를 확인한다.
3. 분석 페이지 이름, 선택된 위젯, 필요한 하중 경우/입력, 결과 제공 시점을 확인한다.
4. 의뢰를 생성하면 작업계획 snapshot과 결과 화면 snapshot이 함께 저장된다.

### 5.3 수행자가 결과가 없는 의뢰를 연다

1. `의뢰 진행 상태`에서 단계와 진행률을 확인한다.
2. `상세 분석 열기`를 누른다.
3. 결과 템플릿이 있으면 선택된 위젯이 즉시 렌더링되고 각각 `결과 대기 중`을 표시한다.
4. 하중 경우가 필요한 위젯은 `하중 경우 설정`, 실행이 필요한 위젯은 `작업 실행` 안내를 표시한다.
5. 결과가 들어오면 동일 위젯이 새 페이지로 전환되지 않고 실제 값으로 갱신된다.

### 5.4 레거시 단계 의뢰를 연다

1. 진행 화면에는 정의된 단계만 표시한다.
2. `상세 분석 열기`를 누르면 제목이 `상세 분석`인 중립 화면을 연다.
3. Open Cell 등 특정 도메인 위젯을 자동 표시하지 않는다.
4. 결과 구성 snapshot이 없으면 빈 캔버스에 `이 의뢰에는 결과 화면 구성이 지정되지 않았습니다`를 표시한다.
5. 권한 보유자에게만 `결과 구성 지정` CTA를 표시한다.
6. 일반 사용자는 단계 현황과 첨부/실행 결과 존재 여부만 읽을 수 있다.

## 6. 화면 설계

### 6.1 업무 유형 편집 — 결과 구성 단계

```text
┌ 업무 유형: 레거시 신뢰성 검토 · 새 버전 ──────────────────────┐
│ 01 기본 정보  02 작업 흐름  [03 결과 구성]  04 검토 및 저장 │
├───────────────────────────────────────────────────────────────┤
│ 분석 템플릿                                                   │
│ [일반 해석 결과 v3                         ▾] [미리보기]      │
│ 설명: 범용 수치·그래프·결과표를 표시합니다.                   │
├──────────────────┬────────────────────────────────────────────┤
│ 페이지/위젯       │ 12열 레이아웃 미리보기                     │
│ ☑ 결과 요약 필수  │ ┌──────── 판정 요약 ────────┐             │
│ ☑ 주요 지표 필수  │ └───────────────────────────┘             │
│ ☑ 결과 그래프     │ ┌──── 주요 지표 ───┐┌─ 결과 그래프 ───┐ │
│ ☐ 컨투어          │ └───────────────────┘└─────────────────┘ │
│ ☑ 상세 결과표     │ ┌──────── 상세 결과표 ──────┐             │
│                   │ └────────────────────────────┘             │
├──────────────────┴────────────────────────────────────────────┤
│ 데이터 요구 검사: 하중 경우 선택 필요 · scalar 결과 필요     │
│ [이전]                          [초안 저장] [검토 및 버전 저장]│
└───────────────────────────────────────────────────────────────┘
```

상호작용 규칙:

- 먼저 템플릿을 고르고 해당 템플릿이 허용한 위젯만 조정한다.
- 필수 위젯은 체크 해제할 수 없으며 이유를 도움말로 표시한다.
- 선택 위젯은 포함 여부를 바꿀 수 있다.
- 고급 권한이 있는 사용자는 12열 캔버스에서 이동·크기 변경을 할 수 있다.
- 위젯을 선택하면 우측 속성 패널에서 제목, 변수 바인딩, 집계 방식, 기준선, 단위, 보고서 포함 여부를 설정한다.
- 템플릿 변경 시 현재 편집 내용이 사라질 수 있음을 확인한 뒤 교체한다.

### 6.2 분석 템플릿 관리

기존 상세분석 대시보드 편집 경험과 `DashboardDefinition`의 12열 레이아웃을 재사용한다.

```text
┌ 분석 템플릿 ───────────┬ 편집 캔버스 ─────────────┬ 속성 ──────┐
│ 시스템                  │ 페이지: 결과 요약         │ 위젯 제목  │
│ · 일반 해석 결과 v3     │ [12열 drag/resize canvas] │ 결과 변수  │
│ · Open Cell 평가 v2     │                           │ 빈 상태    │
│ 프로젝트                │                           │ 보고서 포함│
│ · 레거시 단계 결과 v1   │                           │            │
│ [+ 새 템플릿]           │                           │ [적용]     │
└─────────────────────────┴───────────────────────────┴────────────┘
```

- 템플릿은 `초안 → 게시 → 보관` 생명주기와 불변 버전을 갖는다.
- 업무 유형의 새 버전에는 게시된 템플릿 버전만 연결할 수 있다.
- 시스템 템플릿은 시스템 관리자가, 프로젝트 템플릿은 프로젝트 관리자가 관리한다.
- 템플릿에는 하나 이상의 분석 페이지와 페이지별 위젯 정의가 포함된다.
- 특화 위젯은 지원하는 데이터 계약을 템플릿에 명시한다.

### 6.3 의뢰 접수 — 기대 결과 미리보기

기존 `작업 유형 선택` 카드 아래에 읽기 전용 영역을 추가한다.

```text
기대 결과
일반 해석 결과 · v3 · 2개 페이지 · 5개 위젯

[결과 요약] 판정 요약 · 주요 지표 · 결과 그래프
[상세 결과] 상세 결과표 · 컨투어

필요 입력: 하중 경우
결과 제공: 해석 결과 수집 완료 후
```

- 의뢰 접수 화면에서는 위젯을 변경하지 않는다.
- 변경이 필요하면 업무 유형의 새 버전을 작성하도록 `업무 유형 편집` 링크를 제공한다.
- 접수자는 선택 결과를 확인할 뿐이며, 저장 시 선택된 버전이 snapshot으로 고정된다는 안내를 본다.

### 6.4 의뢰 진행 상태

- 진행 화면은 작업 단계와 실행 상태를 중심으로 유지한다.
- `상세 분석 열기`는 결과가 없어도 활성화한다.
- 버튼 옆에는 다음 중 하나의 배지를 표시한다.

| 배지 | 조건 |
|---|---|
| `구성 미지정` | 결과 화면 snapshot 없음 |
| `입력 필요` | 위젯에 필요한 하중 경우/변수 설정 없음 |
| `결과 대기` | 입력은 있지만 결과 실행/수집 미완료 |
| `부분 결과` | 일부 위젯만 데이터 존재 |
| `결과 준비` | 모든 필수 위젯 데이터 존재 |
| `결과 오류` | 실행 또는 수집 실패가 위젯에 영향을 줌 |

### 6.5 상세분석 런타임

헤더는 특정 분석 유형을 하드코딩하지 않는다.

```text
상세 분석
레거시 단계 의뢰 · 일반 해석 결과 v3             [결과 대기 중]

[결과 요약] [상세 결과]

┌ 판정 요약 ────────────────────────────────────────────────┐
│ 결과 대기 중 · 해석 결과가 연결되면 자동 표시됩니다.     │
└───────────────────────────────────────────────────────────┘
┌ 주요 지표 ────────────┐ ┌ 결과 그래프 ──────────────────┐
│ —                     │ │ 데이터가 아직 없습니다.        │
└───────────────────────┘ └─────────────────────────────────┘

필요한 입력이 없습니다. [하중 경우 설정] [작업 실행]
```

헤더 규칙:

- 1행 제목은 항상 `상세 분석`이다.
- 2행에 의뢰 제목과 선택된 분석 템플릿명을 표시한다.
- `Open Cell 평가 분석` 같은 도메인 제목은 분석 페이지 또는 템플릿 이름으로만 표시한다.
- 템플릿이 없으면 `결과 구성 미지정`을 표시하고 분석 유형명을 추측하지 않는다.

## 7. 위젯 상태 설계

전체 페이지를 오류 화면으로 교체하지 않고 각 위젯이 자신의 상태를 표현한다.

| 상태 | 위젯 표시 | 사용자 동작 |
|---|---|---|
| `UNCONFIGURED` | `필요한 입력이 설정되지 않았습니다` | 하중 경우/변수 설정 |
| `WAITING` | skeleton 또는 `결과 대기 중` | 작업 진행 확인 |
| `PARTIAL` | 존재하는 값과 `일부 결과 미수집` 배지 | 누락 결과 확인 |
| `READY` | 실제 차트·표·미디어·판정 | 상세 보기/보고서 |
| `FAILED` | 실패 요약과 실패한 Run 정보 | 실행 로그/재시도 |
| `NOT_APPLICABLE` | `이 의뢰에는 적용되지 않는 결과입니다` | 없음 |
| `UNSUPPORTED` | `현재 결과 형식을 표시할 수 없습니다` | 관리자 문의 |

공통 빈 상태 규칙:

- `0`, `—`, 빈 배열을 실제 결과처럼 오해하지 않도록 상태 문구를 함께 표시한다.
- 위젯 제목과 예상 단위는 결과가 없어도 유지한다.
- 필요한 입력과 다음 동작을 한 문장으로 안내한다.
- 빈 상태에도 캔버스 배치와 위젯 크기를 유지해 결과 유입 시 레이아웃이 움직이지 않게 한다.
- 위젯 하나의 실패가 다른 위젯과 전체 페이지를 숨기지 않게 한다.

## 8. 위젯 카탈로그 설계

### 8.1 공통 위젯

| 위젯 | 용도 | 대표 데이터 요구 |
|---|---|---|
| 결과 상태 요약 | 준비/대기/부분/실패 상태 | request/run 상태 |
| KPI | 주요 단일 수치 | scalar 결과 |
| 판정 | 기준 대비 PASS/FAIL | scalar + threshold |
| 게이지 | 목표·한계 대비 현재값 | scalar + 범위 |
| 막대/시계열/산점도 | 비교와 추이 | series 결과 |
| 결과표 | 변수별 세부 값 | scalar/row 결과 |
| 조건 요약 | 하중·경계·입력 조건 | load case metadata |
| 컨투어/이미지/영상 | 공간·미디어 결과 | media metadata |
| 의견/검토 | 검토 내용과 상태 | review 데이터 |
| Run 비교 | 기준/대상 실행 비교 | baseline/target run |

### 8.2 도메인 특화 위젯

- Open Cell 맵과 판정 요약
- Chassis 위치도·요약·상세표
- Drop video grid
- 도메인 특화 위젯은 공통 카탈로그에 등록하되 `지원 데이터 계약`을 만족하는 템플릿에서만 선택할 수 있다.
- 업무 유형 이름이나 라벨만 보고 특화 위젯을 자동 선택하지 않는다.

### 8.3 필수 메타데이터

각 위젯 타입은 다음 정보를 선언한다.

- 안정적인 `widget_type`
- 표시 이름과 설명
- 공통/도메인 범위
- 요구 데이터 종류와 필수 바인딩
- 지원 단위와 집계 방식
- 최소/기본/최대 크기
- 빈 상태 문구와 권고 CTA
- 보고서 변환 지원 여부
- 지원 역할과 편집 가능한 설정

## 9. 권한과 변경 정책

| 행위 | viewer | editor | project admin | system admin |
|---|---:|---:|---:|---:|
| 결과 화면 조회 | 허용 | 허용 | 허용 | 허용 |
| 게시 템플릿 위젯 편집 | 불가 | 정책에 따라 허용 | 허용 | 허용 |
| 프로젝트 템플릿 생성/버전업 | 불가 | 불가 | 허용 | 허용 |
| 시스템 템플릿 관리 | 불가 | 불가 | 불가 | 허용 |
| 시스템 업무 유형·기본 결과 프로필 버전 저장 | 불가 | 불가 | 불가 | 허용 |
| 프로젝트 결과 프로필 override 바인딩 | 불가 | 불가 | 허용 | 허용 |
| 레거시 의뢰 결과 구성 사후 지정 | 불가 | 불가 | 허용, 감사 필수 | 허용, 감사 필수 |

- 목표 정책은 결과 구성 저장·게시·업무 유형 연결·레거시 의뢰 사후 지정을 도메인 감사 로그에 남기는 것이다.
- 현재 `ANALYSIS_TEMPLATE_VERSION_CREATED`와 `PROJECT_RESULT_PROFILE_BOUND` 감사 이벤트는 구현되어 있다. 반면 시스템 업무 유형 create/update/deactivate에는 행위별 도메인 감사 이벤트가 아직 없으며, 공통 `API_MUTATION` 기록은 이를 대체하는 완료 근거로 보지 않는다.
- snapshot이 생성된 뒤에는 기존 행을 덮어쓰지 않고 새 revision을 생성한다.
- 결과가 이미 존재하는 의뢰의 결과 구성 변경은 기본적으로 금지하고, 필요하면 복제 의뢰 또는 명시적 마이그레이션 절차를 사용한다.

## 10. 데이터 계약 제안

기존 `DashboardDefinition`과 분석 페이지 메타데이터를 재사용하고, 업무 유형과 의뢰 snapshot 연결만 추가한다.

```text
analysis_template_versions
- template_id, version
- scope_kind, project_id
- display_name, description
- lifecycle_status: DRAFT | PUBLISHED | ARCHIVED
- page_definitions_json
- created_by, created_at

request_type_result_profiles
- request_type_id, request_type_version
- template_id, template_version
- overrides_json
- required_data_contracts_json

request_result_layout_snapshots
- request_id
- source_request_type_id, source_request_type_version
- source_template_id, source_template_version
- snapshot_json
- snapshot_reason: REQUEST_CREATED | LEGACY_ASSIGNED | MIGRATED
- created_by, created_at
```

`snapshot_json`에는 다음을 포함한다.

- 분석 페이지 ID, 제목, 설명, 표시 순서
- 위젯 ID, 타입, 제목, `x/y/w/h`
- 변수/결과/미디어 바인딩
- 필수/선택 여부
- 빈 상태와 CTA 정책
- 보고서 포함 여부
- 템플릿 및 업무 유형 출처 버전

### 10.1 snapshot 우선순위

```text
의뢰 snapshot 존재
  → snapshot 렌더링
의뢰 snapshot 없음 + 명시적 legacy assignment 존재
  → assignment snapshot 렌더링
둘 다 없음
  → 중립 빈 상세분석 화면
```

업무 유형 라벨, 제목, 폴더명, 하중 경우 이름으로 템플릿을 추론하지 않는다.

## 11. 기존 설계와의 결합

### 11.1 사용자 정의 상세분석 페이지

`docs/custom-analysis-pages-plan.md`의 다음 구조를 그대로 재사용한다.

- 12열 위젯 캔버스
- `DashboardDefinition`과 페이지 메타데이터
- 위젯 추가·삭제·이동·크기 변경·속성 편집
- 대시보드 불변 버전과 복구
- 위젯별 보고서 콘텐츠 변환
- 데이터가 없는 위젯의 개별 빈 상태

이번 설계가 추가하는 것은 분석 페이지를 **업무 유형의 기대 결과 구성**으로 선택하고 의뢰에 snapshot하는 흐름이다.

### 11.2 업무 유형·의뢰 접수

`docs/work-type-request-intake-spdm-plan.md`의 작업계획 snapshot과 같은 원칙으로 결과 화면 snapshot을 함께 생성한다.

- 업무 유형 새 버전 저장 시 작업계획과 결과 프로필을 함께 확정한다.
- 의뢰 생성 트랜잭션에서 작업계획과 결과 화면 snapshot을 함께 저장한다.
- 접수 후 업무 유형이 새 버전으로 바뀌어도 기존 의뢰는 영향을 받지 않는다.

### 11.3 현재 Pending 화면 교체 방향

현재 `PendingAnalysisWorkspace`의 전체 구조와 `결과 대기 중` 패턴은 재사용할 수 있지만, Open Cell 제목과 위젯을 하드코딩하지 않는다.

목표 구성은 다음과 같다.

```text
PendingAnalysisWorkspace
  → GenericAnalysisWorkspaceShell
      ├─ snapshot 기반 페이지/위젯 renderer
      ├─ widget state resolver
      └─ no-profile empty state
```

## 12. 예외와 경계 조건

- 업무 유형에 템플릿이 연결되어 있지만 게시 후 보관되더라도 기존 의뢰 snapshot은 계속 렌더링한다.
- 템플릿 위젯이 요구하는 데이터 바인딩이 없으면 업무 유형 버전 저장 전에 경고하고 필수 바인딩이면 저장을 막는다.
- 선택 위젯만 데이터가 없으면 해당 위젯만 대기 상태로 남긴다.
- 하중 경우가 없는 업무도 허용한다. 하중 경우가 필요하지 않은 위젯은 정상적으로 결과를 표시한다.
- 하중 경우 필수 위젯이 포함된 업무 유형은 접수 또는 실행 준비 단계에서 설정 필요를 안내한다.
- 결과 파일이 먼저 들어오고 snapshot이 없는 레거시 의뢰는 자동으로 위젯을 추정하지 않는다.
- snapshot에 현재 클라이언트가 지원하지 않는 위젯 타입이 있으면 해당 위젯 위치에 `지원되지 않는 위젯`을 표시하고 나머지는 유지한다.
- 템플릿을 사후 지정해도 원래 업무 유형과 작업계획 이력은 변경하지 않는다.

## 13. 반응형·접근성·테마

- 데스크톱에서는 12열 캔버스와 좌우 편집 패널을 제공한다.
- 태블릿에서는 캔버스를 6열로 재배치하고 속성 패널은 drawer로 연다.
- 모바일 조회 화면은 위젯을 한 열로 쌓고 편집 기능을 제공하지 않는다.
- 위젯 상태는 색상만으로 구분하지 않고 아이콘, 상태명, 안내 문장을 함께 사용한다.
- 차트에는 표 대체 보기 또는 요약 텍스트를 제공한다.
- 키보드로 템플릿 선택, 위젯 포함/제외, 탭 이동, 저장을 수행할 수 있어야 한다.
- 라이트 테마는 밝은 surface/text/border 토큰만, 다크 테마는 어두운 토큰만 사용한다.
- 빈 위젯과 오류 위젯도 테마 토큰을 사용하고 하드코딩한 다크 배경을 쓰지 않는다.

## 14. 권고 기본값

### 14.1 템플릿이 없는 레거시 의뢰

- 헤더: `상세 분석`
- 상태: `결과 구성 미지정`
- 본문: 빈 캔버스 안내
- 일반 사용자 CTA: 없음 또는 `의뢰 진행 상태로 돌아가기`
- 관리자 CTA: `결과 구성 지정`
- Open Cell 위젯 자동 표시: 하지 않음

### 14.2 범용 분석 템플릿

업무정의 작성자가 빠르게 시작할 수 있도록 다음 위젯을 권고하되 자동 강제하지 않는다.

- 결과 상태 요약
- 주요 지표
- 결과 그래프
- 상세 결과표
- 조건 요약

### 14.3 특화 템플릿

- Open Cell 업무: Open Cell 판정 요약, 엣지 맵, 엣지별 최대 응력, 상세 결과
- Drop 업무: 판정 요약, 영상 그리드, 주요 시계열, 상세 결과
- 비교 업무: Run 비교, 신뢰도, 검토 의견

특화 템플릿은 업무 유형 결과 구성에서 명시적으로 선택한 경우에만 적용한다.

## 15. 구현 단계 제안

### Phase 1. 중립 상세분석 shell

- 현재 Open Cell 하드코딩 Pending 화면을 generic shell로 전환한다.
- snapshot이 없는 의뢰에 `결과 구성 미지정` 빈 화면을 제공한다.
- 전체 오류 대신 위젯별 상태를 표시하는 공통 컴포넌트를 정의한다.

### Phase 2. 템플릿·snapshot 서버 계약

- 완료: 분석 템플릿 버전과 시스템/프로젝트 결과 프로필을 저장한다.
- 완료: 의뢰 생성 시 결과 레이아웃 snapshot을 원자적으로 저장한다.
- 후속: 레거시 사후 지정 운영 도구와 시스템 업무 유형 create/update/deactivate의 도메인 감사 이력을 추가한다.

### Phase 3. 업무 유형 결과 구성 UI

- 완료: 시스템 관리자용 `WorkbenchTypeAdmin`에서 업무 유형 버전과 기본 결과 프로필을 함께 편집한다.
- 완료: 프로젝트 관리자용 `ProjectResultProfileBinding`에서 시스템 정의를 변경하지 않고 프로젝트 override를 바인딩한다.
- 완료: 템플릿 선택, 위젯 포함/제외, 레이아웃 미리보기, 데이터 요구 검사를 구현한다.
- 의뢰 접수에 읽기 전용 기대 결과 미리보기를 추가한다.

- snapshot 페이지와 위젯을 기존 결과 renderer에 연결한다.
- 위젯별 `UNCONFIGURED/WAITING/PARTIAL/READY/FAILED` 상태를 적용한다.
- 하중 경우 없는 업무와 부분 결과를 검증한다.

### Phase 5. 관리자 템플릿 관리·마이그레이션

- 기존 시스템 분석 페이지를 시스템 템플릿으로 등록한다.

- 기존 대시보드 편집/보고서/복구 기능을 회귀 검증한다.

## 16. 인수 기준

### 16.1 업무 유형 관리

- 시스템 관리자는 `/workspace/admin/work-types`에서 게시된 시스템 분석 템플릿을 업무 유형 새 버전의 기본 결과 프로필로 선택·저장할 수 있다.
- 프로젝트 관리자는 `/workspace/project/result-layouts`에서 기존 업무 유형 버전을 선택하고, 시스템 기본 프로필을 변경하거나 업무 유형 새 버전을 만들지 않은 채 프로젝트 결과 프로필 override를 별도 바인딩할 수 있다.
- 필수 위젯은 제거할 수 없고 선택 위젯은 포함/제외할 수 있다.
- 위젯 요구 데이터와 작업계획의 산출 계약이 맞지 않으면 구체적인 경고를 표시한다.
- 저장 후 새로고침해도 시스템 기본 프로필은 같은 업무 유형 버전에, 프로젝트 override는 같은 프로젝트·업무 유형·버전 조합에 유지된다.

### 16.2 의뢰 생성과 재현성

- 새 의뢰 생성 시 작업계획과 결과 화면 snapshot이 함께 저장된다.
- 템플릿이나 업무 유형을 새 버전으로 변경해도 기존 의뢰의 상세분석 레이아웃은 변하지 않는다.
- 의뢰 상세에서 어떤 업무 유형/템플릿 버전으로 생성됐는지 확인할 수 있다.

### 16.3 상세분석

- 하중 경우와 결과가 없어도 상세분석 화면이 열린다.
- 템플릿이 있으면 선택된 위젯이 배치된 상태로 보이고 각 위젯은 결과 대기 상태를 표시한다.
- 템플릿이 없는 레거시 의뢰는 Open Cell 위젯 없이 중립 빈 캔버스를 표시한다.
- 위젯 하나가 실패하거나 데이터가 없어도 전체 페이지 오류가 나타나지 않는다.
- 결과가 유입되면 같은 레이아웃에서 빈 상태가 실제 결과로 바뀐다.
- viewer는 레이아웃을 변경할 수 없고 권한 보유자만 명시적 편집 동작을 사용할 수 있다.

### 16.4 회귀

- 기존 Open Cell, Chassis, Drop video, Run 비교 페이지가 대응 템플릿으로 동일하게 렌더링된다.
- 기존 대시보드 버전 저장·복구와 PPT 보고서 내보내기가 유지된다.
- 의뢰 단계와 운영 대시보드의 monitoring projection이 변하지 않는다.
- 라이트/다크 테마 모두에서 위젯, 빈 상태, 설정 패널의 surface와 텍스트가 일관된다.

## 17. 확정 권고와 추후 결정

### 17.1 이번 설계에서 권고 확정할 항목

- 관리자 건별 배치가 아니라 `관리자 템플릿 관리 + 업무정의 결과 선택` 구조를 사용한다.
- 상세분석은 결과 유무와 관계없이 열 수 있다.
- 레거시 의뢰는 중립 빈 상세분석 화면을 사용한다.
- Open Cell 위젯은 Open Cell 템플릿이 명시적으로 선택된 경우에만 표시한다.
- 의뢰 생성 시 결과 레이아웃을 snapshot으로 고정한다.
- 데이터 부족과 결과 대기는 전체 오류가 아니라 위젯별 상태로 표시한다.

### 17.2 구현 전에 추가로 확정할 항목

- 업무 유형 작성자가 템플릿 레이아웃을 어느 범위까지 수정할 수 있는지: 위젯 포함/제외만 허용할지, 이동·크기 변경도 허용할지
- 결과 템플릿 없이 업무 유형 버전을 게시할 수 있는지: 기본 허용을 권고하되 `결과 없음`을 명시하도록 함
- 결과가 존재하는 레거시 의뢰의 템플릿 사후 지정 정책: 건별 지정, 프로젝트 일괄 지정, 마이그레이션 전용 중 선택
- 위젯 요구 데이터와 세부 작업 산출물의 계약을 처음부터 강제할지, 경고부터 시작해 단계적으로 강화할지

이 문서는 UI와 제품 계약 및 구현 완료 범위를 함께 기록한다. API·저장 모델의 후속 변경은 이 문서의 구현 매핑과 OpenAPI를 함께 갱신한다.

### 18.2 현재 런타임 규칙

1. 의뢰 snapshot이 있으면 snapshot의 페이지·위젯·배치가 상세분석의 권위 있는 레이아웃이다.
2. snapshot이 없으면 특정 하중 경우나 제목으로 Open Cell/Chassis 화면을 추정하지 않는다.
3. 단, 해당 하중 경우에 이미 저장된 분석 페이지는 명시적으로 관리된 페이지이므로 기존 하위 탭·페이지 관리 진입을 유지한다.
4. 결과가 아직 없으면 전체 오류가 아니라 위젯별 `WAITING`, `PARTIAL`, `FAILED` 등의 상태를 유지하고, 필요한 경우 bounded polling으로 갱신한다.
5. 결과 실행 실패는 헤더에서도 `RESULT FAILED`로 표시한다.
6. 사용자가 다른 컨텍스트나 작업공간으로 이동하면 통합 intent gate가 이전 워크플로/모니터링 응답을 무효화하여 최신 선택만 상태를 확정한다.
