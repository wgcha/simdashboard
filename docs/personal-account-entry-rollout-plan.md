# 개인 계정 첫 화면과 사내 전환 개발 계획

- 기준일: 2026-09-09
- 최초 검토 기준: `0f8407b` 소스. 아래 계획은 착수 당시 기록이며 현재 구현 결과는 실행 안내에 정리했다.
- 사용자 요청: 현재 기능을 다시 검토하고, 첫 접속에 회원 로그인·회원가입이 표시되는 개인용 사용 흐름과 개발 계획을 제시한다.
- 개발 상태: 사용자 승인에 따라 첫 화면·서버 최초 관리자·도우미 배포 연동·계정 백업 복원 검증을 구현했다. 적용 절차와 남은 운영 범위는 [현재 실행 안내](personal-account-rollout-runbook.md)를 따른다. 아래 조사 표는 착수 시점의 상태를 기록한 것이다.
- 아이디 최종 요구: 영문·숫자·마침표(`.`)·대시(`-`)·밑줄(`_`) 허용. 한글·공백은 허용하지 않으며 기존 3~80자 길이와 대소문자 정규화를 유지한다.
- 판정: 계정 API와 도우미 설치 구성 요소는 구현되어 있으나, 기본 설치·기존 설치 업데이트부터 이어지는 사내 사용 흐름은 미완료다.

## 1. 현재 확인된 사실

| 영역 | 현재 코드 | 남은 문제 |
|---|---|---|
| 첫 화면 | `App.tsx`는 `authentication_required`가 참이고 미로그인일 때 LoginScreen을 표시 | `.env.example`와 `config.py` 기본값은 disabled. 화면을 건너뛴다 |
| 서버 인증 | disabled는 `security.py`에서 로컬 관리자 principal을 제공 | UI만 로그인 화면으로 바꿔도 서버 API 인증은 활성화되지 않는다 |
| 회원가입 | password 모드에서 가입 버튼/API, PENDING 계정 생성, 관리자 승인 후 로그인 | 설치 시 password 모드 전환 및 최초 관리자 준비가 연결되지 않았다 |
| 개인 사용 | 프로젝트 미배정 ACTIVE 계정은 내 PC 설정으로 진입 | 기존 설치에서 실제 개인 계정으로 진입하기 전 단계가 누락됐다 |
| 업데이트 | Git updater는 `.env`, DB와 배포 파일을 보존 | 기존 disabled 설정이 남고, Git에 없는 도우미 ZIP도 자동으로 도착하지 않는다 |
| Windows 프로필 | `check_deployment_profile.py`의 windows-vm-intranet은 OIDC·PostgreSQL·HTTP directory 요구 | 자체 비밀번호 계정용 사내 Windows 프로필이 없다 |
| Windows 실행 | `start.ps1:239-251`은 backend와 Vite를 127.0.0.1 HTTP로 실행 | 사내 HTTPS 공개 주소·인증서·프록시는 이 시작 스크립트만으로 준비되지 않는다 |
| 도우미 | Windows 런타임 포함 ZIP, 배포 API, 설치·연결·복구 구현 | 신뢰되는 HTTPS와 서버의 ZIP/manifest 배치가 실제 사용의 선행조건이다 |
| 검증 | password 환경의 가입·승인·PC 흐름 검증 기록 존재 | 실제 계정 E2E는 가입 비활성 시 skip하므로 기본 배포 실패를 놓친다 |

근거 파일: `.env.example:59`, `backend/app/config.py:262`, `backend/app/security.py:154`, `backend/app/routers/security.py:196`, `frontend/src/App.tsx:203`, `frontend/src/App.tsx:867`, `frontend/e2e/account-auth.spec.ts:40`, `backend/scripts/check_deployment_profile.py:21`, `scripts/windows/GitUpdate.psm1:174`, `frontend/src/features/local-pc/setupLauncher.ts:37`.

사내 서버의 실제 운영체제, 접속 URL, 실행 커밋, 유효 환경변수, 인증서와 DB 상태는 아직 확인하지 않았다. 위 내용은 소스로 확인한 원인 후보와 구조적 누락이며, 특정 사내 서버 상태를 확정한 것은 아니다.

## 2. 목표 사용자 흐름

1. 계정 사용 준비가 끝난 사내 서버에 미로그인으로 접속하면 `회원 로그인`과 `회원가입`을 첫 화면에 표시한다.
2. 가입은 기존 승인 정책을 유지한다. 가입 완료 안내 → 관리자 승인 → 로그인 순서다. 최초 가입자에게 관리자 권한을 자동 부여하지 않는다.
3. 로그인한 일반 사용자는 프로젝트가 없어도 `내 PC 설정`을 사용할 수 있다. 프로젝트 데이터·실행 권한은 별도로 검사한다.
4. 도우미 미설치 → 설치 → 로컬 승인 → 연결됨 → 프로그램 등록 흐름을 안내한다.
5. 세션이 유효하면 업무 화면으로 진입하고, 로그아웃·만료 후에는 로그인 첫 화면으로 돌아온다.
6. 인증 조회 실패 시 재시도 화면을 보여 준다. 준비가 안 된 사내 설치는 서버 준비 안내를 표시하고 업무/API 접근을 허용하지 않는다.
7. OIDC 설치는 기존 회사 SSO 흐름을 유지한다. 인증 없는 개발 실행은 명시적으로 선택한 개발 용도로 구분한다.

## 3. 개발 순서와 완료 조건

### P0-A. 인증 상태와 첫 화면 통합

- `features/auth`가 확인 중 / 서버 준비 필요 / 미로그인 / 로그인 완료 / 승인 대기 / 오류 상태를 소유하도록 분리한다. App의 조합 역할을 유지하고, 미사용 `useAuthSession`과 중복 로직은 한 경로로 정리한다.
- 로그인·가입 진입을 첫 화면에서 명확히 보여 주고 현재 계정 API를 재사용한다. 단순 UI 추가로 disabled 서버를 로그인 서버처럼 보이게 만들지 않는다.
- 서버 준비 상태 API 계약을 정한다. 공개 응답은 사용자에게 필요한 상태만 제공하고 비밀키·경로·계정 목록 등 관리 정보는 노출하지 않는다.
- `auth/status` 실패와 세션 확인 실패를 구분한다. 인증 미확정 상태에서 업무 bootstrap을 시작하지 않고 오류·재시도를 제공한다.
- 완료: 첫 접속·새로고침·깊은 업무 URL·로그아웃·세션 만료·인증 API 실패에서 올바른 첫 화면 및 서버 접근 제한 확인.

### P0-B. 서버 최초 설정과 기존 설치 전환

- 신규 사내 설치는 개인 비밀번호 계정을 기본 사용 흐름으로 제공한다. disabled는 개발 실행 선택으로 제한하고 `.env.example`만 바꾸는 것으로 끝내지 않는다.
- 서버에서 실행하는 계정 설정 진입점을 설치·업데이트에 연결한다. 유효 설정과 환경변수 우선순위를 확인하고, 비밀키 준비·기존 ACTIVE 비밀번호 관리자 확인·관리자 생성·검증을 한 절차로 묶는다.
- 관리자는 서버의 로컬 설정 절차에서 생성한다. 비밀번호는 비표시 입력, 비밀키는 충분한 난수로 생성한다. 공용 비밀번호나 공개 웹의 무인 최초 관리자 생성은 사용하지 않는다.
- 기존 DB와 프로젝트·사용자 ID·권한을 보존한다. 가상 local-admin이 DB의 실제 비밀번호 관리자인 것으로 간주하지 않는다. 기존 OIDC 계정이나 관리자 비밀번호를 덮어쓰지 않는다.
- 기존 disabled 사내 설치는 업데이트에서 계정 설정 필요를 검출하여 서버 운영자가 전환을 완료하도록 안내한다. 무인 업데이트가 이 단계를 생략하면 계정 전환 완료로 보고하지 않는다.
- Windows 비밀번호용 사내 프로필을 별도로 추가하고 OIDC 전용 프로필 계약을 유지한다. PostgreSQL·HTTPS·secure cookie 조건을 검증하고, 기존 Windows 기능 제한을 해소한 것으로 과장하지 않는다.
- 설정 파일은 백업 후 원자적으로 반영한다. 실패 단계와 복구 방법을 기록하고, 인증 전환 실패를 자동으로 무인증 운영으로 되돌려 성공 처리하지 않는다.
- 완료: 기존 disabled 설치 전환 및 새 설치 후 실제 관리자 로그인 가능, 가입 가능, DB/권한 보존, 재실행 중복 없음. 기존 password/OIDC 설정도 보존.

### P0-C. 도우미 배포와 사내 접속 준비

- 코드 버전과 대응하는 Windows ZIP·해시·manifest를 릴리스 산출물로 함께 준비한다. 서버 updater에서 배포본 반영 단계를 연결한다.
- 온라인 서버는 지정 릴리스에서 취득하고, 폐쇄망은 같은 산출물을 담은 반입 패키지에서 적용하도록 한다. 실행 서버에 빌드 도구가 있어야 하는 구조는 피한다.
- 새 버전 ZIP을 검증한 후 manifest를 마지막에 원자 교체한다. 실패하면 기존 배포본을 보존한다. Git 업데이트 성공과 도우미 배포 준비 성공을 구별한다.
- HTTPS·클라이언트 인증서 신뢰·공개 서버 URL·도우미 배포 상태를 설치 전에 확인한다. HTTP 원격 주소를 그대로 허용하도록 보안 조건을 완화하지 않는다.
- Windows 사내 서버라면 기존 회사 HTTPS 프록시를 우선 재사용한다. 없는 경우 인증서 발급·갱신 주체를 확인하고 정적 frontend 빌드와 API를 제공하는 프록시/서비스 설치를 별도 배포 모듈로 준비한다. 단순 CORS 설정이나 Vite 외부 바인딩으로 완료 처리하지 않는다. Rocky는 기존 설치기의 HTTPS/password 검증을 재사용한다.
- 사용자에게 설치 필요 / 실행 필요 / 연결 승인 필요 / 연결됨 / 서버 준비 필요를 행동 중심으로 구분해 안내한다.
- 완료: Python·Git 없는 별도 Windows PC에서 사내 HTTPS 접속 → 가입·승인 → 다운로드·설치 → 연결·프로그램 등록 성공.

### P0-D. 배포 경로 통합 검증

- password 모드·관리자·배포본을 실제 설정 절차로 준비하는 배포 전용 테스트를 만든다. 이 테스트에서 가입 비활성은 skip이 아닌 실패다. OIDC 전용 검증은 별도로 유지한다.
- 기존 disabled 설치의 데이터 보존 → 업데이트 → 최초 설정 → 새 브라우저 로그인·가입 흐름을 검사한다.
- API를 직접 호출해 미로그인 차단, 승인 전 차단, 일반 계정의 관리자/타인 PC 접근 차단을 확인한다.
- 실제 PostgreSQL에서 가입·중복·승인·비밀번호 변경을 검증한다. 브라우저만 통과한 결과로 서버 배포 완료를 판정하지 않는다.
- 배포 파일 누락·해시 오류·네트워크 실패·설정 재실행·도우미 재설치 실패를 포함한다.
- 완료 보고에 소스 커밋, 서버 설정 준비, 도우미 산출물, 새 PC 검증 결과를 각각 기록한다.

### P1. 계정 운영 보완

- 비밀번호 변경·관리자 재설정 후 기존 세션을 무효화할 정책과 구현을 추가한다. 현재 토큰에는 sub/iat/exp만 있고 비밀번호 변경에 따른 폐기 검사가 없다. 사용자 세션과 도우미 연결 자격 증명의 수명은 별도로 설계한다.
- 로그인·가입 요청 제한과 프록시를 통과한 클라이언트 식별을 검토한다. 여러 worker와 사내 NAT 환경에서 한 사용자의 요청이 전체 직원을 막지 않도록 검증한다.
- 승인 대기 목록과 승인 후 다음 행동 안내, 관리자에 의한 계정 복구 절차를 정리한다.
- 이메일 인증·메일 비밀번호 복구·SSO 계정 이관·도우미 자동 업데이트·코드 서명은 별도 후속 범위로 유지한다.

## 4. 구현 배정과 검수

- Astra: 인증/준비 상태 계약, 신규·기존 배포의 기본 동작, 데이터 보존과 실패 복구 설계.
- Luna: 확정된 계약에 맞춘 첫 화면·가입·오류/준비 안내, 인증 feature 상태 정리.
- Terra: 서버 계정 설정, Windows 프로필, 업데이트·릴리스 도우미 배포 연동. 파일 경계를 나누어 구현한다.
- Sol: 서버 권한 경계, 관리자 초기화, 기존 설치 보존, 실제 배포 경로 검수.
- 기존 React, Pydantic, 암호 해시 및 표준 라이브러리·설치 모듈을 재사용한다. 계약 변경에 맞춰 OpenAPI·테스트·배포 문서를 함께 갱신한다.

## 5. 이번 검토의 범위

처음에는 읽기 전용 검토로 작성했으며, 이후 사용자 요청으로 구현·검증을 진행했다. 실제 사내 서버의 설정과 인증서·서비스 배치는 아직 변경하지 않았다. P1 후속 기능 및 실제 직원 PC 검증은 현재 실행 안내에 남은 범위로 명시했다.
